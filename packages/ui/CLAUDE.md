# packages/ui

- shadcn 컴포넌트는 `components.json` 설정으로 `npx shadcn@latest add <name> -c packages/ui`(또는 이 패키지 안에서 `-c .`)로 추가한다. CLI가 이 패키지 스코프(`@ai-character-chat/ui`)의 alias를 그대로 써서 `src/components/*.tsx`에 생성한다.
- Tailwind는 v4(CSS-first)라 `tailwind.config.js`가 없다. 색상/타이포/spacing/radius 토큰은 전부 `src/styles/globals.css`의 `:root`/`@theme inline` 블록 하나에만 정의한다(DESIGN.md와 동일 소스 유지). 새 앱(`apps/admin` 등)이 이 패키지를 쓰려면 `@tailwindcss/vite` 플러그인만 추가하고 진입점에서 `@ai-character-chat/ui/globals.css`를 import하면 된다.
- `globals.css`의 `@source` 경로는 CSS 파일 실제 위치(`packages/ui/src/styles/`) 기준 상대경로다. 새 앱을 추가할 때 그 앱의 `src`가 이미 `../../../../apps/**/*.{ts,tsx}` 글롭에 걸리는지 확인하고, 걸리지 않으면 새 `@source` 줄을 추가한다.
- 다크모드는 `.dark` 클래스 기반이다: `globals.css`에 `.dark` 토큰 블록과 `@custom-variant dark (&:is(.dark *))`가 정의되어 있어 `html`에 `dark` 클래스를 붙이면 전환된다(`:root`/`.dark`에 `color-scheme`도 선언되어 네이티브 컨트롤·스크롤바가 따라온다). 유채색 토큰 둘(핑크-레드 `primary`, 레드 `destructive`)은 다크에서 **밝은 채움 + 어두운 텍스트**로 반전된다 — 라이트는 `primary` `oklch(0.5 0.19 0)` / `destructive` `oklch(0.55 0.19 25)`에 흰 `*-foreground`(`oklch(1 0 0)`), 다크는 `oklch(0.72 0.18 0)` / `oklch(0.64 0.19 25)`에 어두운 `*-foreground`(`oklch(0.16 0 0)`)다. 밝힌 색 위 흰 텍스트가 AA 미달이라 foreground를 함께 뒤집은 것이므로 **토큰을 조정할 때 이 쌍을 함께 움직일 것.** primary의 명도 폭이 destructive보다 큰 것(0.5↔0.72 대 0.55↔0.64)은 primary만 솔리드 채움이라 채움 자체가 자기 텍스트와 4.5:1을 져야 하기 때문이다(destructive는 언제나 `/10` 틴트라 채움 자체가 텍스트를 질 일이 없다 — 그래서 **destructive의 텍스트 대비는 `--destructive`가 아니라 별도 토큰 `--destructive-text`가 진다**, 아래 항목). `sonner.tsx`의 `Toaster`는 `theme` prop을 받는다(기본 `"light"`) — web은 `apps/web/src/app/toaster.tsx`의 `AppToaster`가 현재 테마를 전달하고, admin은 prop 없이 light 고정이다.
- 유채색 토큰을 바꿀 때 **정지 상태 대비만 재면 부족하다** — `button`의 default variant는 hover에서 `bg-primary/80`이라 채움이 배경 쪽으로 20% 옅어진다(Tailwind v4는 이걸 `color-mix(in oklab, ...)`로 컴파일한다). 정지 6.7:1이던 조합이 hover에서 4.77:1까지 떨어지므로 **hover 값까지 4.5:1을 넘는 명도를 골라야 한다.** 브라우저에서 재려면 1×1 canvas에 배경을 칠하고 그 위에 `color-mix(in oklab, <token> 80%, transparent)`를 덧칠해 `getImageData`로 읽는다.
- **`Button`의 `size="lg"`는 단독으로 쓰지 않는다.** `lg`는 `default`와 패딩(`px-2.5`)·타이포가 같고 높이만 `h-8`→`h-9`(+4px)라, 같은 라벨의 두 버튼에 걸면 **폭이 완전히 동일**해져 위계가 아니라 정렬 오차로 읽힌다. `apps/web`의 `size="lg"` 호출부는 전부 `className="h-10"`(폼 제출) 또는 `h-12`(플레이 버튼)로 높이를 덮어쓴다 — 실제 출하 어휘는 **32 / 40 / 48px**이고 36px 티어는 없다. 크기로 위계를 만들려면 오버라이드까지 함께 쓰고, 아니면 라벨·배치로 가른다.
- 유채색 토큰의 chroma는 취향이 아니라 **sRGB 게멋 상한에 걸린다**(hue 0에서 L 0.5 → 최대 C 0.203, L 0.72 → 0.191). 상한을 넘긴 값을 적으면 브라우저가 조용히 클리핑해서 의도한 색이 안 나온다. 새 값을 정할 땐 oklch→linear sRGB로 변환해 세 채널이 0~1 안에 있는지 먼저 확인할 것.
- **`destructive`는 토큰이 둘이다 — 채움은 `--destructive`, 글자·글리프는 `--destructive-text`다(US-003).** `text-destructive-text`(라이트 `oklch(0.49 0.19 25)` / 다크 `oklch(0.69 0.19 25)`)는 **텍스트와 아이콘에만** 쓰고, `bg-destructive/5`·`/10`·`/20`, `border-destructive/30`, `ring-destructive/20`, 그리고 솔리드 채움 위의 `bg-destructive` + `destructive-foreground` 반전 쌍(위 항목)은 **`--destructive` 그대로** 둔다. 새로 destructive 텍스트를 쓸 때 `text-destructive`를 적으면 그 유틸리티는 존재하지만 **AA 미달인 옛 값**이 나온다 — 저장소의 호출부 64곳은 전부 `-text`다.
  - 왜 갈랐나: 한 토큰이 둘을 겸하면 텍스트 대비를 올리는 순간 틴트 색도 함께 움직인다. 갈라 두면 틴트 픽셀을 1비트도 안 건드리고 텍스트만 겨냥할 수 있다(A/B 실측: `/5`·`/10` 합성 결과와 `border-destructive/30`의 computed 값이 라이트·다크 모두 전후 동일).
  - **고치기 전(`text-destructive` = `--destructive`)의 실측치** — 평평한 `background` 위에서만 아슬아슬하게 AA를 넘겼다(라이트 **4.5672**(이번 런 재현) / 다크 4.8402(공표값), 여유 0.1 미만). 표면이 명도 사다리 한 칸만 안쪽으로 들어가면 깨졌다: `bg-popover`(= `card`·`muted`와 같은 값) 위 rest **라이트 4.2059 / 다크 4.3824**, hover `/20`에서 **3.6035 / 3.8252**. `bg-destructive/5` 배너 안의 destructive 버튼도 같은 계열이라 라이트 4.24였다(공표값 — 실패 상태를 만들어야 해서 이번 런에서는 재현하지 않았다).
  - **고친 뒤 실측(canvas `getImageData`, 전이 정착 후 · 라이트/다크)** — `/20` over `popover`(최악) **4.6907 / 4.6346**, `/10` over `popover` 5.4748 / 5.3097, `/20` over `background` 5.0692 / 5.1877, `/10` over `background` 5.9451 / 5.9024, `bg-destructive/5` 배너 문구 6.4120 / 6.1847·그 안의 버튼 rest 5.5097 / 5.5977·hover 4.7165 / 4.9021. **최악값이 4.63이라 여유가 0.13밖에 없다** — `--destructive`(채움)를 밝히거나 popover를 더 안쪽으로 미는 변경은 이 값을 다시 깎는다.
  - 명도를 더 못 미는 이유: hue 25에서 sRGB 게멋 상한 chroma가 라이트 L 0.49에서 0.1986, 다크 L 0.69에서 0.1995라 현재 chroma 0.19가 이미 상한 바로 아래다. 더 어둡게/밝게 가려면 chroma를 깎아야 하고 그러면 빨강이 회색으로 죽는다.
  - 적용 범위는 **호출부가 아니라 프리미티브·토큰**이다: `Button` `variant="destructive"`(web+admin 16곳, `DialogFooter` 소비처만 6곳 — `WithdrawAccountDialog`, `ConfirmChatRoomActionModal`, `GeneratedImageDetailModal`, `DeleteContentDraftModal`, `ResetContentDraftModal`, admin의 `act-on-report/ui/DeleteConfirmModal`)와 `DropdownMenuItem variant="destructive"`(3파일 4항목 — `MyWorkCardMenu` 둘, `ChatRoomListItemRow`, `MessageBubble`; 라벨과 글리프가 같은 토큰을 물어야 색이 안 갈린다)가 한 번에 따라온다. **admin은 `.dark`를 절대 붙이지 않아 라이트 값이 그대로 적용된다**(`main.tsx`가 `globals.css`만 import한다) — 문서는 web·admin 공용이니 목록에서 빼지 말 것. 한 곳만 `outline`으로 바꾸는 호출부 처방은 쓰지 않는다: 되돌릴 수 없는 확인 버튼의 시각 언어가 앱 안에서 갈린다.
  - **`ProfileMenu`(로그아웃)가 `variant="destructive"`를 안 쓰는 근거는 대비가 아니라 의미다(US-012).** DESIGN.md §Destructive가 이 토큰의 뜻을 삭제·탈퇴·거부·이용제한 넷으로 못박았는데 로그아웃은 넷 중 아무것도 아니다. **US-003 이후 대비 근거는 더 이상 성립하지 않는다** — destructive 행 focus가 5.3097 / 5.4748로 AA를 넘겼다(중립 행은 12.6689 / 14.0576로 여전히 더 높지만, 그건 위계 논거지 접근성 논거가 아니다). `destructive`를 새로 붙이기 전에 "이게 정말 저 넷 중 하나인가"를 먼저 볼 것. 심각도는 색이 아니라 아이콘과 카피가 진다.
  - Radix는 `pointermove`에도 focus를 걸므로 `DropdownMenuItem`의 focus 값은 **키보드 사용자만의 상태가 아니다**(실측) — 가리키는 순간 모든 사용자의 상태다.
- **`--input`은 `--border`와 값이 다르다 — 컨트롤 식별 보더 전용이다(US-004).** 라이트 `oklch(0.62 0 0)` / 다크 `oklch(0.52 0 0)`이고 구분선 `--border`(0.89 / 0.3)와 갈라져 있다. **인터랙티브하면 `border-input`, 구조면 `border-border`.** 인풋·텍스트에어리어·셀렉트 트리거·체크박스·outline 버튼·선택 안 된 토글은 내부 채움이 페이지 배경과 `1.0000`이라 이 한 줄이 컨트롤의 **유일한 식별 신호**이고, 그래서 WCAG 1.4.11(3:1)을 진다 — 사다리 값으로는 **1.4312 다크 / 1.3845 라이트**로 절반도 안 됐다. `--border`가 그리는 카드 테두리·구분선·점선 빈 상태는 장식이라 그 요건이 없으므로 사다리에 남겨 뒀다.
  - 고친 값의 실측(스크린샷 픽셀 디코드, 인풋 실물): `background` 위 **3.5403 다크 / 3.6408 라이트**, `card`(=`popover`·`muted`) 위 **3.2344 / 3.3395**. **`secondary`·`accent` 위는 2.8276 / 2.9714로 여전히 미달**이니 그 표면에 보더만으로 식별되는 컨트롤을 올리지 말 것.
  - `--input`은 보더만이 아니라 **채움으로도** 쓰인다(`switch`의 off 트랙 `bg-input`, 인풋·텍스트에어리어의 `disabled:bg-input/50`, `tabs`의 `dark:data-active:bg-input/30`). 스위치는 이 변경으로 함께 고쳐졌다 — off 트랙 대 페이지 배경, 그리고 그 위 썸(`bg-background`) 대 트랙이 모두 1.4312 → **3.5403**이 된다. `tabs`의 `bg-input/30`은 `variant="default"` 전용이고 이 앱의 `TabsList` 3곳이 전부 `variant="line"`이라 렌더가 바뀌지 않는다.
  - **호출부에 손으로 복사된 컨트롤 셸을 잊지 말 것.** `button` outline variant를 베낀 셸이 `border-border`로 새고 있었다(US-004에서 `GeneratedImageField` 2곳, `IconPicker`, `ColorPicker`, `ChangeStartingSetupModal`을 `border-input`으로 옮겼다). **예외는 클릭 카드**(`ContentCard`, `BuilderTypeSelectPage`) — 썸네일·제목·hover·포커스 링이 함께 식별을 지므로 `border-border`를 유지한다(그리드에 24장이 깔리는 자리라 무게 문제도 있다).
- **`primary` 솔리드 채움 위에서는 하우스 포커스 레시피(`focus-visible:border-ring` + `ring-ring/50`)가 통째로 무너진다.** `--ring`이 `--primary`와 같은 값이라 보더가 채움과 **같은 색**(1.0000:1)이 되어 rest의 1px 윤곽을 지우고, 남는 50% 링은 페이지 배경 대비 **2.5757(다크) / 2.5511(라이트)**로 WCAG 1.4.11의 3:1에 미달한다(US-009 `toggle.tsx`와 US-011 `button.tsx`에서 각각 독립 측정해 소수점까지 일치). 처방은 해당 variant에 **불투명 링**(`focus-visible:ring-ring`) — **7.1768 / 6.7011**로 올라간다. 지금 적용된 곳: `toggle.tsx`의 `default`/`outline` 선택 상태, `button.tsx`의 `default` variant. **base 문자열이 아니라 채움이 있는 variant에만 붙인다** — 무채색·`/10` 틴트 variant는 측정된 결함이 없고, base에 넣으면 문제 없던 곳의 렌더까지 바뀐다. 새로 `primary` 솔리드를 쓰는 프리미티브를 만들면 같은 처방을 함께 넣을 것(안 넣으면 같은 채움인데 포커스 표시만 갈린다).
  - **하우스 레시피에서 3:1을 지는 건 50% 링이 아니라 불투명 1px 보더다**(US-004에서 `로그아웃` 버튼을 픽셀 스캔해 확정). 실제 픽셀 배열은 `페이지배경 | 50%링 3px | 불투명보더 1px | 채움`이고, 링 대 페이지 배경은 **2.5757 다크 / 2.5511 라이트**로 3:1에 못 미치는 반면 보더 대 채움은 **7.1768 / 6.7011**이다. 그래서 판정 기준은 **"보더가 살아 있는가"** 하나다 — `primary` 솔리드는 보더가 채움에 먹혀 죽고, `/10` 틴트는 산다. 이 문장을 인용할 때 "불투명 링이 필요하다"를 `/10` 틴트에까지 확대하지 말 것.
- **[US-004에서 해결됨 — 아래 수치는 전부 *고치기 전* 값이다]** **`DropdownMenuItem`의 포커스 표시는 배경 하나뿐이라 WCAG 1.4.11(3:1)에 크게 미달했다.** item 클래스에 `outline-hidden`이 있어 링이 지워지고 남는 신호가 `focus:bg-accent` 변화뿐이다 — 스크린샷 픽셀 실측 **중립 항목 다크 1.1439 / 라이트 1.1239**, **destructive 항목 다크 1.1119 / 라이트 1.1598**(포커스된 항목 박스와 팝오버 가장자리 사이가 순수 popover 색임을 픽셀로 확인 — 아웃라인도 링도 없다). DESIGN.md §Toggles가 2.5757:1짜리 토글 링을 미달로 판정하고 불투명 링을 요구한 바로 그 기준으로 재면 메뉴는 **그 절반도 안 된다**. 명도 사다리로는 못 고친다(사다리 최상단 `border`를 채움으로 써도 popover 대비 ~1.3). **채움이 아니라 링이어야 한다** — item에 `focus:ring-1 focus:ring-ring focus:ring-inset` 계열을 더하고 `bg-accent`는 보조로 남긴다. 앱의 모든 드롭다운(`/my`·프로필 카드 메뉴, 헤더 프로필, 알림, 대화방 목록, `MessageBubble`)이 함께 걸린다. **이 배치의 우선순위는 헤더 프로필 메뉴가 정한다** — US-012가 그 메뉴를 창작/활동/계정 3그룹 8항목으로 키웠고, DESIGN.md가 탭바·사이드레일·푸터를 금지하므로 **그 메뉴가 앱의 유일한 내비게이션 표면**이다. US-012의 2차 계측이 그 메뉴에서 **1.1439 / 1.1239를 독립 재현**했고(같은 스크린샷 픽셀 방식, 소수점 4자리 일치), 포커스된 항목의 computed가 `outlineStyle: "none"` · `boxShadow: "none"` · `border: 0px`라 **배경 말고는 그릴 게 하나도 없다**는 것도 함께 확인했다(`outlineColor`에 값은 있지만 `outline-hidden`이 style을 none으로 만들어 그려지지 않는다). 처방 수치도 재 뒀다: `ring`(=`primary`) 대 `popover` **다크 6.5567 / 라이트 6.1465**, 대 `accent`(포커스 배경) **5.7320 / 5.4691**.
  - **적용된 처방(US-004)**: item 클래스에 `focus:inset-ring-1 focus:inset-ring-ring`. `Item`(default·destructive)·`CheckboxItem`·`RadioItem`·`SubTrigger` 넷 전부와 **`select.tsx`의 `SelectItem`**, 그리고 손으로 만든 옵션 리스트(`ShortcutAutocomplete`)까지 같이 옮겼다 — `outline-hidden focus:bg-accent`를 grep하면 이 여섯이 전부 나오고, 하나만 고치면 같은 모양의 목록에서 포커스 표시가 갈린다. **링 색은 variant별로 안 가른다**: 하나로 중립(5.7320 / 5.4691)과 destructive(**5.8968 / 5.2997** — 이번에 실측)를 둘 다 넘긴다.
  - `inset-ring-*`는 Tailwind v4 유틸리티다(v3의 `ring-inset`도 아직 컴파일되지만 v4 표기를 쓴다). item base에 `ring-*` 키가 없어 `cn()`으로 충돌 없이 얹힌다.
  - **비활성 항목은 `data-disabled:opacity-65`다**(상류 `opacity-50`에서 올림, `SelectItem`도 같이). 50%면 항목 글자가 popover 위에서 **3.2515 라이트 / 4.4959 다크**로 AA 미달인데(US-004에서 처음 측정) 65%면 **5.1882 / 6.7086**이다(US-008에서 스크린샷 픽셀로 소수 넷째 자리까지 재현). Radix는 비활성 항목을 키보드 이동에서 건너뛰고(`End`가 마지막 *활성* 항목에 착지하는 것으로 실측) `data-disabled:pointer-events-none`이 pointermove focus도 막아, **링은 `disabled` 항목에 그려지지 않는다**.
  - **사유를 읽혀야 하는 비활성 항목은 `disabled`가 아니라 `aria-disabled`로 만든다(US-008).** Radix의 `disabled`는 `RovingFocusGroup.Item`의 `focusable: !disabled`로 항목을 **포커스 순회와 타입어헤드에서 통째로 뺀다** — 실측: `disabled`면 ArrowDown이 `수정하기` → `편집한 내용 버리기`로 두 항목을 건너뛰고 타입어헤드 `링`도 안 걸린다. 그러면 "왜 못 누르는지"가 키보드·스크린리더에 **영원히 닿지 않는다**(사유를 항목 이름에 넣든 옆에 두든 마찬가지다). `aria-disabled` + `onSelect`의 `preventDefault`면 항목이 순회에 남고(실측: 네 항목이 순서대로 잡힌다) 눌러도 모달이 안 열리며 메뉴도 안 닫혀 사유가 그 자리에 남는다. 그래서 item 클래스에 **`aria-disabled:opacity-65`가 `data-disabled:opacity-65`와 같은 값으로 함께** 걸려 있다.
  - **`aria-disabled` 항목에는 링이 그려지고, 그 링도 65%로 흐려진다 — 그래도 3:1을 넘는다.** 실측(스크린샷 픽셀, 390px 다크/라이트): 링 대 포커스 채움 **3.1861 다크 / 3.1257 라이트**, 링 대 popover 3.4722 / 3.3565. 흐리지 않은 활성 항목의 5.7320 / 5.4691(US-004 값, 같은 프로브로 재현)에서 내려온 값이라 **여유가 0.13~0.19밖에 없다** — `--ring`을 어둡게 하거나 opacity를 더 내리면 이 값이 먼저 깨진다. 흐림 안의 글자는 여유가 더 있다: 비활성 글자 대 포커스 채움 **6.1558 다크 / 4.7879 라이트**(AA 4.5:1).
  - **이 항목을 미루는 근거로 "base 문자열이라 전역이다"를 쓰지 말 것 — 여기서는 그 규칙이 오적용된다(US-012 3라운드에서 반증됨).** 아래 `button`/`toggle` 항목의 근거는 "무채색·`/10` variant는 **측정된 결함이 없는데** base에 넣으면 문제 없던 곳의 렌더까지 바뀐다"인데, 드롭다운 item에는 **결함 없는 소비처가 0개**다(`Item` default·destructive, `CheckboxItem`, `RadioItem`, `SubTrigger`가 전부 같은 `outline-hidden focus:bg-accent`를 물고 1.1119~1.1598로 전원 미달). 7곳이 함께 바뀌는 건 리스크가 아니라 **목표**다. 호출부 처방이 불가능한 것도 아니다 — base에 `ring-*` 키가 없어 `focus:ring-1 focus:ring-ring focus:ring-inset`이 `cn()`으로 충돌 없이 얹힌다. **진짜 근거는 "한 곳만 고치면 시각 언어가 앱 안에서 갈린다"(destructive 항목이 이미 못박은 그것) 하나뿐이고, 그래서 고칠 때는 base에서 한 번에 고치는 게 맞다.** 키보드·확대 사용자는 앱의 모든 이동을 1.1439:1짜리 표시에 의존해 한다. 나머지 다섯 드롭다운은 국소 액션 메뉴라 같은 수치라도 노출 빈도가 다르다. 참고: 같은 1.1439/1.1239가 `apps/web/CLAUDE.md`에서 ⋯ 트리거의 hover 칩에 대해 "살아남는다"로 판정돼 있는데 **모순이 아니다** — hover는 WCAG 대비 요건이 없는 임의 affordance이고 `:focus`는 규범이 걸린 자리라 같은 숫자에 다른 판정이 붙는다.
- **확인 모달의 순서는 언제나 `취소` 먼저, 실행 나중이다 — DOM·시각·탭 셋이 같다(US-006).** `DialogFooter`·`AlertDialogFooter`가 `sm` 미만에서 상류 shadcn의 `flex-col-reverse`가 아니라 **`flex-col`**이고, `DialogContent`의 닫기(X) 버튼이 `{children}` **앞**에 렌더된다. 고치기 전엔 y좌표가 단조 **감소**했다(320px 실측: 초기 포커스 `취소` y475 → Tab → 실행 버튼 y435 → Tab → `닫기` y330 — WCAG 1.3.2/2.4.3). 고친 뒤 `닫기` y330 → `취소` y435 → 실행 y475로 단조 증가한다(320·390·1280 전부, 확인 모달 4곳에서 실측).

- **`AlertDialogContent`의 폭은 `w-full`이 아니라 `w-[calc(100%-2rem)]`이다(US-006).** `max-w-*`로는 못 막는다 — `max-w-xs`를 물고 있는 쪽이 `data-[size=…]:` 변형이라 특이도가 (0,2,0)이고 평평한 `max-w-[calc(100%-2rem)]`(0,1,0)을 언제나 이겨서 320px 뷰포트에서 좌우 여백이 **0**이 됐다(실측 left=0 right=320). 폭을 깎으면 352px 미만에서만 달라지고(320px: left=16 right=304) 390px·`sm` 이상은 전후 동일하다. `DialogContent`가 `max-w-`로 같은 여백을 얻는 건 거기엔 경쟁하는 `data-*` 변형이 없기 때문이다.

- **`packages/ui`의 모션은 전부 `motion-safe:`로 게이팅돼 있다(US-005) — 새 프리미티브에도 반드시 붙인다.** `prefers-reduced-motion: reduce`에서 `animation-name: none` · `animation-duration: 0s` · `transition-duration: 0s`가 되는 것이 13개 프로브로 실측됐다. **`animate-*`/`transition-*`뿐 아니라 `duration-*`도 함께 게이팅한다** — `duration-100`은 `transition-duration`도 세팅하는데 CSS의 `transition-property` 초깃값이 `all`이라, 애니메이션만 끄고 duration을 남기면 reduce에서 `transition: all 0.1s`가 살아남는다(고치기 전 dialog·alert-dialog·dropdown·select content가 전부 그 상태였다).

  - `SelectContent`는 같은 결함이 없다 — Radix의 `SelectScrollUpButton`/`ScrollDownButton`이 이미 신호를 진다. 손으로 만든 `ShortcutAutocomplete`(`max-h-60 overflow-y-auto`)에는 아직 신호가 없다(미측정).
- **이 일괄 작업의 착수 근거는 회원탈퇴 확인 경로다 — 미뤄 둔 프리미티브 결함 넷이 거기서 동시에 발화한다.** `/mypage`의 `회원탈퇴` → `탈퇴하기` 한 흐름 안에서 (1) `DialogFooter`의 탭 순서 역전(**US-006에서 해결됨** — 위 항목), (2) destructive 틴트 위 텍스트 AA 미달(**US-003에서 해결됨** — `--destructive-text` 신설로 트리거 hover가 다크 5.1877 / 라이트 5.0692, 모달 `탈퇴하기` rest가 5.3097 / 5.4748·hover가 4.6346 / 4.6907이 됐다. 아래 인용된 미달 수치는 전부 **고치기 전** 값이다), (3) `motion-safe:` 게이트 부재(**US-005에서 해결됨** — 이 화면의 alert-dialog overlay·content·`탈퇴하기`/`취소` 버튼이 reduce ON에서 전부 `animationName: none` · `0s`가 됐다), (4) `/10` 틴트 컨트롤의 포커스 링 부재(**US-004에서 해결됨** — `focus-visible:border-destructive` + `ring-destructive/50`, 보더가 자기 채움 대비 4.8431 / 4.5795)가 전부 걸린다. US-013 계측: 트리거 `회원탈퇴`의 라벨 대비가 rest **다크 4.8402 / 라이트 4.5672**(라이트는 여유 0.0672)인데 **hover에서 다크 4.2817 / 라이트 3.8943으로 AA 아래로 떨어지고**, 그 트리거의 포커스 링은 페이지 배경 대비 **1.2371 / 1.3694**, 자기 채움 대비 **1.1312 / 1.1728**이라 **어느 쪽으로도 보이지 않는다**. 같은 화면의 `로그아웃`·인풋·제출 버튼은 전부 3px 링을 제대로 그리므로 **이 앱에서 포커스가 사실상 안 보이는 컨트롤은 destructive 하나뿐**이다. 대화기록 전체가 삭제되고 발행작이 내려가는 단 하나의 액션이, 미뤄 둔 부채 넷의 교차점에 앉아 있다. 우선순위를 이 흐름이 정한다. **US-013 2차 계측이 더한 것**: 트리거뿐 아니라 **확인 모달의 `탈퇴하기` 라벨 자체가 AA 미달**이고(다크 **4.3459** / 라이트 **4.2059**, 14px 본문이라 large-text 예외 없음) 트리거의 보조 지표인 내부 보더도 **1.5962 / 1.6396**으로 동반 미달이라 **두 지표가 모두 죽어 있다**. `prefers-reduced-motion: reduce`에서 이 화면의 `transition-all 0.15s`·`animate enter 0.1s`(zoom 포함) 수치가 reduce OFF와 **완전히 동일**함도 실측했다(게이트가 아예 없었다 — **US-005에서 해결됨**, 위 항목에 전후 수치가 있다). 320px에서 `AlertDialogContent`가 `left=0 right=320`으로 **좌우 여백 0**(390에선 35px) — **US-006에서 해결됨**(320px에서 left=16 right=304). 그리고 이 묶음에 **`border-input` 1.4312 다크 / 1.3845 라이트**(**US-004에서 해결됨** — 3.5403 / 3.6408)를 더한다 — 인풋·outline 버튼·선택 안 된 토글의 내부 채움이 페이지 배경과 1.0000이라 **저대비 보더가 유일한 식별 수단**인데 1.4.11(3:1)에 미달한다(포커스 시엔 7.1768/6.7011로 올라가므로 rest 상태만의 문제다). **착수 규모**: `variant="destructive"` 호출부가 web+admin 합쳐 **16곳**이고 admin은 라이트 고정이라, 이 묶음은 한 스토리에 끼워 넣을 크기가 아니다 — 그게 US-013이 등재만 하고 미룬 이유다.
- **문장 속 인라인 링크는 쉬는 상태에서 링크로 안 읽힌다 — 색만으로는 주변 본문과 갈리지 않는다.** 저장소 관용구 `font-medium text-primary hover:underline`(`LoginForm`·`SignUpPage`·`/mypage` 설명 문단)은 배경 대비로는 넉넉하지만(7.1768 다크 / 6.7011 라이트) **링크 텍스트 대 주변 본문 대비가 1.0652 / 1.2761**이다(canvas로 oklch→sRGB 변환해 실측 — `getComputedStyle`이 `oklch()` 문자열을 돌려주므로 rgb로 파싱하면 조용히 1.00이 나온다). WCAG G183이 색을 링크 식별자로 쓸 때 요구하는 3:1에 한참 못 미치고, 다크에서는 사실상 *같은 밝기의 다른 hue*라 적록색약 사용자에게 구별되지 않는다. 정지 상태의 비색 단서는 `font-medium`(500 vs 400) 한 단계뿐이라 1.4.1을 간신히 면한다. 처방은 `underline underline-offset-4`(후자는 `button.tsx`의 `link` variant가 이미 정의한 값이라 새 어휘가 아니다)인데, **한 곳만 붙이면 시각 언어가 갈리므로 3파일 4곳을 함께 옮기는 일괄 항목으로 둔다.** hover·focus는 이미 밑줄이 그려지는 것이 픽셀로 확인됐다(1px, 폭 40/40px).
- **`DropdownMenuContent`의 폭은 트리거 폭에 고정돼 있다** — `w-(--radix-dropdown-menu-trigger-width)` + `min-w-32`라, 아이콘 버튼(32px)이 트리거면 메뉴가 **128px에 갇힌다**. 상류 shadcn에는 `min-w-32`만 있고 `w-`는 이 저장소가 더한 것이다(select처럼 필드 폭에 맞추려는 의도). 항목 라벨이 조금만 길어도 두 줄로 깨지므로(실측: "링크공개로 전환") 아이콘 트리거를 쓰는 메뉴는 호출부에서 `className="w-auto"`를 얹어 내용에 맞춘다. 프리미티브를 고치면 헤더 프로필 메뉴·알림 등 기존 메뉴들의 폭이 함께 바뀌므로 call-site 처방을 쓴다.
- **`DialogContent`에는 최대 높이/내부 스크롤이 없다** — 내용이 뷰포트보다 길어질 수 있는 다이얼로그(이미지·목록 포함)는 호출부에서 `className="max-h-[calc(100dvh-2rem)] overflow-y-auto"`를 직접 얹을 것. Radix가 body 스크롤을 잠그기 때문에 이걸 빼먹으면 화면 밖으로 밀린 푸터에 닿을 방법이 없다(실측: 생성 이미지 상세 모달의 삭제 푸터, 높이 577px 뷰포트).
- dialog/sheet/alert-dialog 오버레이의 `bg-black/10`(+`backdrop-blur`) 스크림은 라이트/다크 공통으로 의도된 하드코딩이다(US-131에서 판정 — 다크에서는 블러가 배경 분리를 담당). 하드코딩 색상 정리 시 시맨틱 토큰으로 바꾸지 말 것.
- 컴포넌트들이 쓰는 `data-open:`/`data-active:`/`data-horizontal:` 같은 축약 variant는 Tailwind 내장이 아니라 `globals.css`의 `@import "shadcn/tailwind.css"`가 정의하는 custom variant다(Radix의 `data-state`/`data-orientation` 값 매칭으로 확장). 순수 tailwindcss만으로 컴파일해 보면 `&[data-active]`(불리언 속성 매칭)로 나와 죽은 셀렉터처럼 보이지만 실제 앱에서는 동작하니, 이 import를 빼먹거나 "안 맞는 셀렉터"로 오판해 고치지 말 것. shadcn이 정의 안 한 상태(예: `data-state=inactive`)는 명시 문법 `data-[state=inactive]:`를 쓴다.
- shadcn 컴포넌트 소스를 그대로 가져오되 `dark:` variant 클래스는 제거했고(토큰 기반이라 대부분 `.dark` 블록만으로 동작), 사용자 노출 텍스트("Close" 등)는 한국어로 교체했다 — 새 컴포넌트를 추가할 때도 동일하게 정리하되, 다크에서 토큰만으로 대비가 안 나오는 경우에만 `dark:` 클래스를 선별 복원한다.
- Toast는 shadcn에서 deprecated된 `toast` 대신 `sonner`를 쓴다. `<Toaster />`는 앱 루트에 한 번만 마운트(`apps/web/src/main.tsx`)하고, 실제 호출은 각 기능 코드에서 `import { toast } from "sonner"`로 직접 한다(패키지 재노출 없음) — 그래서 `sonner`를 쓰는 앱은 자신의 `package.json`에도 `sonner`를 직접 의존성으로 추가해야 한다(pnpm 워크스페이스는 간접 의존성을 자동으로 끌어오지 않음).
- 한글 UI이므로 폰트는 Pretendard(`pretendard` npm 패키지의 variable dynamic-subset)를 쓴다. Fontsource 계열이 아니라 `pretendard/dist/web/variable/pretendardvariable-dynamic-subset.css`를 globals.css에서 직접 import한다.
