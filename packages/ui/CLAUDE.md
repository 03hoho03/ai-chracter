# packages/ui

- shadcn 컴포넌트는 `components.json` 설정으로 `npx shadcn@latest add <name> -c packages/ui`(또는 이 패키지 안에서 `-c .`)로 추가한다. CLI가 이 패키지 스코프(`@ai-character-chat/ui`)의 alias를 그대로 써서 `src/components/*.tsx`에 생성한다.
- Tailwind는 v4(CSS-first)라 `tailwind.config.js`가 없다. 색상/타이포/spacing/radius 토큰은 전부 `src/styles/globals.css`의 `:root`/`@theme inline` 블록 하나에만 정의한다(DESIGN.md와 동일 소스 유지). 새 앱(`apps/admin` 등)이 이 패키지를 쓰려면 `@tailwindcss/vite` 플러그인만 추가하고 진입점에서 `@ai-character-chat/ui/globals.css`를 import하면 된다.
- `globals.css`의 `@source` 경로는 CSS 파일 실제 위치(`packages/ui/src/styles/`) 기준 상대경로다. 새 앱을 추가할 때 그 앱의 `src`가 이미 `../../../../apps/**/*.{ts,tsx}` 글롭에 걸리는지 확인하고, 걸리지 않으면 새 `@source` 줄을 추가한다.
- 다크모드는 `.dark` 클래스 기반이다: `globals.css`에 `.dark` 토큰 블록과 `@custom-variant dark (&:is(.dark *))`가 정의되어 있어 `html`에 `dark` 클래스를 붙이면 전환된다(`:root`/`.dark`에 `color-scheme`도 선언되어 네이티브 컨트롤·스크롤바가 따라온다). 유채색 토큰 둘(핑크-레드 `primary`, 레드 `destructive`)은 다크에서 **밝은 채움 + 어두운 텍스트**로 반전된다 — 라이트는 `primary` `oklch(0.5 0.19 0)` / `destructive` `oklch(0.55 0.19 25)`에 흰 `*-foreground`(`oklch(1 0 0)`), 다크는 `oklch(0.72 0.18 0)` / `oklch(0.64 0.19 25)`에 어두운 `*-foreground`(`oklch(0.16 0 0)`)다. 밝힌 색 위 흰 텍스트가 AA 미달이라 foreground를 함께 뒤집은 것이므로 **토큰을 조정할 때 이 쌍을 함께 움직일 것.** primary의 명도 폭이 destructive보다 큰 것(0.5↔0.72 대 0.55↔0.64)은 primary만 솔리드 채움이라 채움 자체가 자기 텍스트와 4.5:1을 져야 하기 때문이다(destructive는 언제나 `/10` 틴트라 텍스트 대비만 맞추면 된다). `sonner.tsx`의 `Toaster`는 `theme` prop을 받는다(기본 `"light"`) — web은 `apps/web/src/app/toaster.tsx`의 `AppToaster`가 현재 테마를 전달하고, admin은 prop 없이 light 고정이다.
- 유채색 토큰을 바꿀 때 **정지 상태 대비만 재면 부족하다** — `button`의 default variant는 hover에서 `bg-primary/80`이라 채움이 배경 쪽으로 20% 옅어진다(Tailwind v4는 이걸 `color-mix(in oklab, ...)`로 컴파일한다). 정지 6.7:1이던 조합이 hover에서 4.77:1까지 떨어지므로 **hover 값까지 4.5:1을 넘는 명도를 골라야 한다.** 브라우저에서 재려면 1×1 canvas에 배경을 칠하고 그 위에 `color-mix(in oklab, <token> 80%, transparent)`를 덧칠해 `getImageData`로 읽는다.
- **`Button`의 `size="lg"`는 단독으로 쓰지 않는다.** `lg`는 `default`와 패딩(`px-2.5`)·타이포가 같고 높이만 `h-8`→`h-9`(+4px)라, 같은 라벨의 두 버튼에 걸면 **폭이 완전히 동일**해져 위계가 아니라 정렬 오차로 읽힌다. `apps/web`의 `size="lg"` 호출부는 전부 `className="h-10"`(폼 제출) 또는 `h-12`(플레이 버튼)로 높이를 덮어쓴다 — 실제 출하 어휘는 **32 / 40 / 48px**이고 36px 티어는 없다. 크기로 위계를 만들려면 오버라이드까지 함께 쓰고, 아니면 라벨·배치로 가른다.
- 유채색 토큰의 chroma는 취향이 아니라 **sRGB 게멋 상한에 걸린다**(hue 0에서 L 0.5 → 최대 C 0.203, L 0.72 → 0.191). 상한을 넘긴 값을 적으면 브라우저가 조용히 클리핑해서 의도한 색이 안 나온다. 새 값을 정할 땐 oklch→linear sRGB로 변환해 세 채널이 0~1 안에 있는지 먼저 확인할 것.
- **`bg-destructive/10 text-destructive` 조합은 `background`(가장 밝은/어두운 끝) 위에서만 AA를 넘긴다.** 평평한 `background` 위 라이트 4.57:1 / 다크 4.58:1로 4.5:1을 아슬아슬하게 넘길 뿐이라 여유가 0.1도 안 되고, 표면이 한 칸만 안쪽으로 들어가도 깨진다.
  - `bg-card` 위(명도 사다리 한 칸): **라이트 4.21:1 / 다크 4.35:1 — 양쪽 다 AA 미달**. 실측 사례는 `apps/web` 로그인 실패 배너와 `apps/admin` 로그인 실패 배너(둘 다 카드 안의 오류 문구).
  - 같은 계열 틴트 위(`bg-destructive/5` 배너 안의 destructive 버튼): 라이트 4.24:1 — `ChatRoomView`의 응답 실패 배너 + "다시 시도"가 실측 사례.
  - **`DialogFooter` 안의 `Button variant="destructive"`도 같은 경우다** — `DialogContent`가 `bg-popover`(= `card`와 같은 명도)라 확인 버튼이 사다리 한 칸 안쪽에 앉는다. 실측 **다크 4.3492 / 라이트 4.2176**(footer의 `bg-muted/50`은 `--muted`가 `--popover`와 같은 값이라 표면을 더 어둡게 만들지 않는다). 소비처가 6곳이다 — web의 `WithdrawAccountDialog`(회원탈퇴), `ConfirmChatRoomActionModal`(대화방 초기화·삭제), `GeneratedImageDetailModal`, `DeleteContentDraftModal`, `ResetContentDraftModal`, 그리고 **admin의 `act-on-report/ui/DeleteConfirmModal`**(라이트 고정이라 4.2176 그대로다 — 이 문서는 web·admin 공용이니 목록에서 빠뜨리지 말 것). **한 곳만 `outline`으로 바꾸지 말 것**: 되돌릴 수 없는 확인 버튼의 시각 언어가 앱 안에서 갈리고, 남은 넷(특히 회원탈퇴)이 그대로 미달로 남는다. 고치려면 다섯 곳을 한 번에 옮기거나 프리미티브/토큰 쪽에서 잡는 별도 작업으로.
  - **`DropdownMenuItem variant="destructive"`의 focus 상태도 정확히 같은 조합이다** — 메뉴 표면이 `bg-popover`(다크 `oklch(0.21 0 0)`, `--card`와 문자열까지 같은 값)인데 focus에서 `bg-destructive/10`이 얹힌다. 스크린샷 픽셀 실측: **rest는 다크 4.8359 / 라이트 4.8914로 AA 통과인데, focus에서 다크 4.3492 / 라이트 4.2176으로 떨어져 미달**한다(`DialogFooter` 버튼과 소수점까지 같은 값 — 같은 표면 위 같은 틴트라 당연하다). **키보드 사용자만의 문제가 아니다** — Radix는 `pointermove`에도 focus를 걸므로(실측) 가리키는 순간 모든 사용자의 상태다. 소비처 **3파일 4항목**: `MyWorkCardMenu`(`/my` 카드의 `삭제하기`·`편집한 내용 버리기`), `ChatRoomListItemRow`, `MessageBubble` — 글리프는 `Trash2` 셋에 `RotateCcw` 하나다(넷 다 사용자 데이터를 지운다). 위의 `DialogFooter` 6곳과 합쳐 **한 번에** 옮기거나 프리미티브/토큰에서 잡을 것.
    - **`ProfileMenu`(로그아웃)는 이 목록에서 빠졌다(US-012).** `variant="destructive"`를 떼서 중립 항목으로 돌렸더니 focus 텍스트가 위의 미달값에서 **12.6689 / 14.0576**으로 올라갔다(중립 항목은 focus 배경이 `accent`라 `accent-foreground`와의 대비가 그대로 남는다). 근거는 대비만이 아니다 — DESIGN.md §Destructive가 이 토큰의 뜻을 삭제·탈퇴·거부·이용제한 넷으로 못박았는데 로그아웃은 넷 중 아무것도 아니다(지우는 게 없고 다시 로그인하면 되돌아온다). 남은 소비처 3파일 4항목은 전부 사용자 데이터를 지운다. **`destructive`를 새로 붙이기 전에 "이게 정말 저 넷 중 하나인가"를 먼저 볼 것** — 아니면 대비 부채를 하나 더 만드는 것이다. 심각도는 색이 아니라 아이콘과 카피가 진다(`MyWorkCardMenu`가 쓴 규칙).
  - 즉 이 틴트를 카드·팝오버·시트 같은 안쪽 표면에 얹으려면 텍스트 대비를 따로 확보해야 한다(문구를 `foreground`로 두고 색은 아이콘·보더에만 쓰거나, 배너 배경을 무채색으로 둘 것). 경고 배너 안에 액션이 필요하면 destructive 버튼을 겹치지 말고 `ghost`/`outline`을 쓴다.
- **`primary` 솔리드 채움 위에서는 하우스 포커스 레시피(`focus-visible:border-ring` + `ring-ring/50`)가 통째로 무너진다.** `--ring`이 `--primary`와 같은 값이라 보더가 채움과 **같은 색**(1.0000:1)이 되어 rest의 1px 윤곽을 지우고, 남는 50% 링은 페이지 배경 대비 **2.5757(다크) / 2.5511(라이트)**로 WCAG 1.4.11의 3:1에 미달한다(US-009 `toggle.tsx`와 US-011 `button.tsx`에서 각각 독립 측정해 소수점까지 일치). 처방은 해당 variant에 **불투명 링**(`focus-visible:ring-ring`) — **7.1768 / 6.7011**로 올라간다. 지금 적용된 곳: `toggle.tsx`의 `default`/`outline` 선택 상태, `button.tsx`의 `default` variant. **base 문자열이 아니라 채움이 있는 variant에만 붙인다** — 무채색·`/10` 틴트 variant는 측정된 결함이 없고, base에 넣으면 문제 없던 곳의 렌더까지 바뀐다. 새로 `primary` 솔리드를 쓰는 프리미티브를 만들면 같은 처방을 함께 넣을 것(안 넣으면 같은 채움인데 포커스 표시만 갈린다).
- **`DropdownMenuItem`의 포커스 표시는 배경 하나뿐이라 WCAG 1.4.11(3:1)에 크게 미달한다.** item 클래스에 `outline-hidden`이 있어 링이 지워지고 남는 신호가 `focus:bg-accent` 변화뿐이다 — 스크린샷 픽셀 실측 **중립 항목 다크 1.1439 / 라이트 1.1239**, **destructive 항목 다크 1.1119 / 라이트 1.1598**(포커스된 항목 박스와 팝오버 가장자리 사이가 순수 popover 색임을 픽셀로 확인 — 아웃라인도 링도 없다). DESIGN.md §Toggles가 2.5757:1짜리 토글 링을 미달로 판정하고 불투명 링을 요구한 바로 그 기준으로 재면 메뉴는 **그 절반도 안 된다**. 명도 사다리로는 못 고친다(사다리 최상단 `border`를 채움으로 써도 popover 대비 ~1.3). **채움이 아니라 링이어야 한다** — item에 `focus:ring-1 focus:ring-ring focus:ring-inset` 계열을 더하고 `bg-accent`는 보조로 남긴다. 앱의 모든 드롭다운(`/my`·프로필 카드 메뉴, 헤더 프로필, 알림, 대화방 목록, `MessageBubble`)이 함께 걸린다. **이 배치의 우선순위는 헤더 프로필 메뉴가 정한다** — US-012가 그 메뉴를 창작/활동/계정 3그룹 8항목으로 키웠고, DESIGN.md가 탭바·사이드레일·푸터를 금지하므로 **그 메뉴가 앱의 유일한 내비게이션 표면**이다. US-012의 2차 계측이 그 메뉴에서 **1.1439 / 1.1239를 독립 재현**했고(같은 스크린샷 픽셀 방식, 소수점 4자리 일치), 포커스된 항목의 computed가 `outlineStyle: "none"` · `boxShadow: "none"` · `border: 0px`라 **배경 말고는 그릴 게 하나도 없다**는 것도 함께 확인했다(`outlineColor`에 값은 있지만 `outline-hidden`이 style을 none으로 만들어 그려지지 않는다). 처방 수치도 재 뒀다: `ring`(=`primary`) 대 `popover` **다크 6.5567 / 라이트 6.1465**, 대 `accent`(포커스 배경) **5.7320 / 5.4691**.
  - **이 항목을 미루는 근거로 "base 문자열이라 전역이다"를 쓰지 말 것 — 여기서는 그 규칙이 오적용된다(US-012 3라운드에서 반증됨).** 아래 `button`/`toggle` 항목의 근거는 "무채색·`/10` variant는 **측정된 결함이 없는데** base에 넣으면 문제 없던 곳의 렌더까지 바뀐다"인데, 드롭다운 item에는 **결함 없는 소비처가 0개**다(`Item` default·destructive, `CheckboxItem`, `RadioItem`, `SubTrigger`가 전부 같은 `outline-hidden focus:bg-accent`를 물고 1.1119~1.1598로 전원 미달). 7곳이 함께 바뀌는 건 리스크가 아니라 **목표**다. 호출부 처방이 불가능한 것도 아니다 — base에 `ring-*` 키가 없어 `focus:ring-1 focus:ring-ring focus:ring-inset`이 `cn()`으로 충돌 없이 얹힌다. **진짜 근거는 "한 곳만 고치면 시각 언어가 앱 안에서 갈린다"(destructive 항목이 이미 못박은 그것) 하나뿐이고, 그래서 고칠 때는 base에서 한 번에 고치는 게 맞다.** 키보드·확대 사용자는 앱의 모든 이동을 1.1439:1짜리 표시에 의존해 한다. 나머지 다섯 드롭다운은 국소 액션 메뉴라 같은 수치라도 노출 빈도가 다르다. 참고: 같은 1.1439/1.1239가 `apps/web/CLAUDE.md`에서 ⋯ 트리거의 hover 칩에 대해 "살아남는다"로 판정돼 있는데 **모순이 아니다** — hover는 WCAG 대비 요건이 없는 임의 affordance이고 `:focus`는 규범이 걸린 자리라 같은 숫자에 다른 판정이 붙는다.
- **`DialogFooter`는 `sm` 미만에서 `flex-col-reverse` 전폭으로 접힌다 — 시각 순서만 뒤집고 DOM 순서는 그대로다.** 그래서 (1) 확인 버튼 폭을 `취소`와 다르게 만들어 형태로 가르는 호출부 처방이 좁은 화면에서 **무효가 되고**(390px 326×32 / 320px 256×32로 Δ0 — 실측), (2) **탭 순서가 시각 순서와 어긋난다**(320px 실측: 초기 포커스 `취소` y453 → Tab → 실행 버튼 y413 → Tab → `닫기` y308 — WCAG 1.3.2). shadcn 기본값이라 이 저장소 확인 모달 6곳이 전부 같다. 위의 destructive 대비·motion-safe 항목과 **같은 일괄 작업**으로 묶을 것.
- **`DialogDescription`에 `break-keep`이 없다.** 한국어 본문은 이게 없으면 어절 중간에서 끊기는데(실측: `되` / `돌릴 수 없어요.`), **넓은 폭에서만 나타나는 게 함정이다** — 확인 모달 본문 폭이 `sm:max-w-sm` 안에서 1280px일 때 352px, 390px일 때 326px이라 좁은 쪽이 우연히 문장 경계로 접힌다. 지금은 호출부에서 `className="break-keep"`을 주는 게 저장소 관습이다(한국어 본문 7곳 전부 호출부).
- **dialog/sheet/`dropdown-menu`의 enter/exit 애니메이션과 `button`의 `transition-all`에는 `prefers-reduced-motion` 게이트가 없다**(`data-open:animate-in ...`이 무조건 걸린다 — `set media reduced-motion`에서도 `animationName: "enter"` + 시작 키프레임 `scale .95 / translateY -8px / opacity 0`이 적용된 것으로 실측됨. `button`은 `transition: all 0.15s`가 그대로 남는다. 같은 화면의 `ContentCard`가 `motion-safe:transition-colors`로 올바르게 게이팅돼 `transition-duration: 0s`가 되는 것과 대조된다). 호출부에서 `className="motion-reduce:animate-none"`으로 끄려 해도 소용없다: `data-open:` 변형이 속성 선택자를 붙여 특이도가 더 높아 진다. 앱 전체에서 이 규칙(DESIGN.md "모든 애니메이션에 motion-safe:")을 지키려면 호출부가 아니라 이 프리미티브들을 함께 고쳐야 한다. **이걸 미루는 근거도 "base 문자열이라 전역 렌더가 바뀐다"가 아니다**(US-012 3라운드 지적) — `motion-safe:` 추가는 reduced-motion을 켜지 않은 사용자의 렌더를 1픽셀도 바꾸지 않고 **지금 결함인 렌더만** 바꾼다. 진짜 근거는 **이 항목이 dialog·sheet·dropdown-menu·button 4개 프리미티브 한 묶음이라는 것**이다 — dropdown만 고치면 같은 화면의 다이얼로그가 여전히 튀어 규칙이 반만 지켜진다.
- **가로로 눕힌 폰에서 긴 메뉴의 마지막 행이 "잘렸다는 표시 없이" 통째로 사라진다.** `DropdownMenuContent`가 `max-h-(--radix-…-available-height)` + `overflow-y-auto`라 뷰포트를 넘지는 않지만, macOS 오버레이 스크롤바에는 상시 표시가 없어 **포인터·터치 사용자에게 스크롤 가능하다는 신호가 하나도 없다**. 헤더 프로필 메뉴(US-012, 368px)를 844×390에서 재면 `max-h`가 342px로 잘라 `로그아웃` 행이 6/28px, **글자는 0/16px**만 남는데 메뉴가 구분선에서 끊겨 **완결된 메뉴처럼 보인다**(`scrollTop: 0` 실측). 키보드 End·스크롤로는 닿는다. 잘림을 보이게 하려면(상시 스크롤바 `[scrollbar-color:…]`나 하단 페이드 마스크) 이 프리미티브를 고쳐야 하므로 위 일괄 작업에 함께 묶는다. **새 메뉴를 만들 때 항목 수를 세지 말고 가로 폰 높이(available-height 342px)에 재 볼 것.**
- **이 일괄 작업의 착수 근거는 회원탈퇴 확인 경로다 — 미뤄 둔 프리미티브 결함 넷이 거기서 동시에 발화한다.** `/mypage`의 `회원탈퇴` → `탈퇴하기` 한 흐름 안에서 (1) `DialogFooter`의 탭 순서 역전, (2) destructive 틴트 위 텍스트 AA 미달, (3) `motion-safe:` 게이트 부재, (4) `/10` 틴트 컨트롤의 포커스 링 부재가 전부 걸린다. US-013 계측: 트리거 `회원탈퇴`의 라벨 대비가 rest **다크 4.8402 / 라이트 4.5672**(라이트는 여유 0.0672)인데 **hover에서 다크 4.2817 / 라이트 3.8943으로 AA 아래로 떨어지고**, 그 트리거의 포커스 링은 페이지 배경 대비 **1.2371 / 1.3694**, 자기 채움 대비 **1.1312 / 1.1728**이라 **어느 쪽으로도 보이지 않는다**. 같은 화면의 `로그아웃`·인풋·제출 버튼은 전부 3px 링을 제대로 그리므로 **이 앱에서 포커스가 사실상 안 보이는 컨트롤은 destructive 하나뿐**이다. 대화기록 전체가 삭제되고 발행작이 내려가는 단 하나의 액션이, 미뤄 둔 부채 넷의 교차점에 앉아 있다. 우선순위를 이 흐름이 정한다. **US-013 2차 계측이 더한 것**: 트리거뿐 아니라 **확인 모달의 `탈퇴하기` 라벨 자체가 AA 미달**이고(다크 **4.3459** / 라이트 **4.2059**, 14px 본문이라 large-text 예외 없음) 트리거의 보조 지표인 내부 보더도 **1.5962 / 1.6396**으로 동반 미달이라 **두 지표가 모두 죽어 있다**. `prefers-reduced-motion: reduce`에서 이 화면의 `transition-all 0.15s`·`animate enter 0.1s`(zoom 포함) 수치가 reduce OFF와 **완전히 동일**함도 실측했다(게이트가 아예 없다). 320px에서 `AlertDialogContent`가 `left=0 right=320`으로 **좌우 여백 0**(390에선 35px). 그리고 이 묶음에 **`border-input` 1.4312 다크 / 1.3845 라이트**를 더한다 — 인풋·outline 버튼·선택 안 된 토글의 내부 채움이 페이지 배경과 1.0000이라 **저대비 보더가 유일한 식별 수단**인데 1.4.11(3:1)에 미달한다(포커스 시엔 7.1768/6.7011로 올라가므로 rest 상태만의 문제다). **착수 규모**: `variant="destructive"` 호출부가 web+admin 합쳐 **16곳**이고 admin은 라이트 고정이라, 이 묶음은 한 스토리에 끼워 넣을 크기가 아니다 — 그게 US-013이 등재만 하고 미룬 이유다.
- **문장 속 인라인 링크는 쉬는 상태에서 링크로 안 읽힌다 — 색만으로는 주변 본문과 갈리지 않는다.** 저장소 관용구 `font-medium text-primary hover:underline`(`LoginForm`·`SignUpPage`·`/mypage` 설명 문단)은 배경 대비로는 넉넉하지만(7.1768 다크 / 6.7011 라이트) **링크 텍스트 대 주변 본문 대비가 1.0652 / 1.2761**이다(canvas로 oklch→sRGB 변환해 실측 — `getComputedStyle`이 `oklch()` 문자열을 돌려주므로 rgb로 파싱하면 조용히 1.00이 나온다). WCAG G183이 색을 링크 식별자로 쓸 때 요구하는 3:1에 한참 못 미치고, 다크에서는 사실상 *같은 밝기의 다른 hue*라 적록색약 사용자에게 구별되지 않는다. 정지 상태의 비색 단서는 `font-medium`(500 vs 400) 한 단계뿐이라 1.4.1을 간신히 면한다. 처방은 `underline underline-offset-4`(후자는 `button.tsx`의 `link` variant가 이미 정의한 값이라 새 어휘가 아니다)인데, **한 곳만 붙이면 시각 언어가 갈리므로 3파일 4곳을 함께 옮기는 일괄 항목으로 둔다.** hover·focus는 이미 밑줄이 그려지는 것이 픽셀로 확인됐다(1px, 폭 40/40px).
- **`DropdownMenuContent`의 폭은 트리거 폭에 고정돼 있다** — `w-(--radix-dropdown-menu-trigger-width)` + `min-w-32`라, 아이콘 버튼(32px)이 트리거면 메뉴가 **128px에 갇힌다**. 상류 shadcn에는 `min-w-32`만 있고 `w-`는 이 저장소가 더한 것이다(select처럼 필드 폭에 맞추려는 의도). 항목 라벨이 조금만 길어도 두 줄로 깨지므로(실측: "링크공개로 전환") 아이콘 트리거를 쓰는 메뉴는 호출부에서 `className="w-auto"`를 얹어 내용에 맞춘다. 프리미티브를 고치면 헤더 프로필 메뉴·알림 등 기존 메뉴들의 폭이 함께 바뀌므로 call-site 처방을 쓴다.
- **`DialogContent`에는 최대 높이/내부 스크롤이 없다** — 내용이 뷰포트보다 길어질 수 있는 다이얼로그(이미지·목록 포함)는 호출부에서 `className="max-h-[calc(100dvh-2rem)] overflow-y-auto"`를 직접 얹을 것. Radix가 body 스크롤을 잠그기 때문에 이걸 빼먹으면 화면 밖으로 밀린 푸터에 닿을 방법이 없다(실측: 생성 이미지 상세 모달의 삭제 푸터, 높이 577px 뷰포트).
- dialog/sheet/alert-dialog 오버레이의 `bg-black/10`(+`backdrop-blur`) 스크림은 라이트/다크 공통으로 의도된 하드코딩이다(US-131에서 판정 — 다크에서는 블러가 배경 분리를 담당). 하드코딩 색상 정리 시 시맨틱 토큰으로 바꾸지 말 것.
- 컴포넌트들이 쓰는 `data-open:`/`data-active:`/`data-horizontal:` 같은 축약 variant는 Tailwind 내장이 아니라 `globals.css`의 `@import "shadcn/tailwind.css"`가 정의하는 custom variant다(Radix의 `data-state`/`data-orientation` 값 매칭으로 확장). 순수 tailwindcss만으로 컴파일해 보면 `&[data-active]`(불리언 속성 매칭)로 나와 죽은 셀렉터처럼 보이지만 실제 앱에서는 동작하니, 이 import를 빼먹거나 "안 맞는 셀렉터"로 오판해 고치지 말 것. shadcn이 정의 안 한 상태(예: `data-state=inactive`)는 명시 문법 `data-[state=inactive]:`를 쓴다.
- shadcn 컴포넌트 소스를 그대로 가져오되 `dark:` variant 클래스는 제거했고(토큰 기반이라 대부분 `.dark` 블록만으로 동작), 사용자 노출 텍스트("Close" 등)는 한국어로 교체했다 — 새 컴포넌트를 추가할 때도 동일하게 정리하되, 다크에서 토큰만으로 대비가 안 나오는 경우에만 `dark:` 클래스를 선별 복원한다.
- Toast는 shadcn에서 deprecated된 `toast` 대신 `sonner`를 쓴다. `<Toaster />`는 앱 루트에 한 번만 마운트(`apps/web/src/main.tsx`)하고, 실제 호출은 각 기능 코드에서 `import { toast } from "sonner"`로 직접 한다(패키지 재노출 없음) — 그래서 `sonner`를 쓰는 앱은 자신의 `package.json`에도 `sonner`를 직접 의존성으로 추가해야 한다(pnpm 워크스페이스는 간접 의존성을 자동으로 끌어오지 않음).
- 한글 UI이므로 폰트는 Pretendard(`pretendard` npm 패키지의 variable dynamic-subset)를 쓴다. Fontsource 계열이 아니라 `pretendard/dist/web/variable/pretendardvariable-dynamic-subset.css`를 globals.css에서 직접 import한다.
