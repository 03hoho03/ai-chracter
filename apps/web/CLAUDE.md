# apps/web

- FSD 레이어 의존 방향: `app → pages → widgets → features → entities → shared` (역방향 import 금지). `routes/*`는 로직 없이 `pages/{page}`를 렌더링만 하는 얇은 어댑터로 유지한다.
- `src/routeTree.gen.ts`는 TanStack Router의 `@tanstack/router-plugin` Vite 플러그인이 `vite dev`/`vite build` 실행 시 자동 생성하는 파일이며, `tsc --noEmit`만으로는 fresh checkout에서 생성되지 않으므로 **git에 커밋**한다. 라우트를 추가/변경했다면 typecheck·커밋 전에 `vite build`(또는 `vite dev` 1회)를 먼저 실행해 이 파일을 최신 상태로 갱신해야 한다. 갱신을 빼먹어도 typecheck는 통과하지만(오래된 트리 기준으로만 검사) 새 라우트가 검증에서 누락된다.
- 디자인시스템은 `packages/ui`(shadcn+Tailwind v4)를 그대로 쓴다. `vite.config.ts`에 `@tailwindcss/vite` 플러그인이 등록되어 있고, `main.tsx`에서 `@ai-character-chat/ui/globals.css` 한 번만 import하면 전체 앱에 토큰/유틸리티가 적용된다(이 앱 자체는 별도 `tailwind.config`/전역 css를 갖지 않는다). 컴포넌트는 `@ai-character-chat/ui/components/{name}`에서 가져온다. 자세한 내용은 `packages/ui/CLAUDE.md` 참고.
- 모든 API 호출은 `shared/lib/api/client.ts`가 export하는 단일 `apiClient` axios 인스턴스를 거친다(직접 `axios.create` 금지). 인증은 httpOnly 세션 쿠키 + `withCredentials: true`로 처리되므로 요청 인터셉터에서 토큰을 붙이지 않는다. 응답 인터셉터가 모든 에러를 `@ai-character-chat/api-types`의 `ApiError`로 정규화해 reject하므로, 호출부의 `catch`/`onError`는 axios 원본 에러가 아니라 이 포맷을 받는다. 401 시 로그인 리다이렉트는 아직 미연결 — 로그인 라우트가 생기면 `setUnauthorizedHandler(() => router.navigate(...))`를 앱 초기화 시점(`app/providers.tsx` 등)에 한 번 등록한다.
- **`ApiError`는 FastAPI가 실제로 내려주는 `{"detail": ...}` 형태를 그대로 반영한다** (US-028에서 수정 — 이전 버전은 `{code, message, fields}`를 가정했는데 apps/api의 실제 에러 바디와 전혀 맞지 않았고, 그때까지 어떤 FE 코드도 실제 에러를 소비한 적이 없어 발견되지 않은 채로 있었다). `detail`이 string이면 HTTPException 메시지 그대로, dict면 구조화된 값(예: 429 응답의 `retryAfterSeconds`), 422 배열이면 `fields`로 필드명→메시지 매핑까지 펼쳐진다. 새 화면에서 서버 에러 메시지를 그대로 노출하기보다, `apiError.status`로 분기해 한국어 카피를 직접 작성하는 편이 일관된 UX를 준다(BE의 `detail` 문자열은 영어 디버그 메시지라 사용자 노출용이 아님).
- **`entities/session`**(`sessionKeys`, `useSessionQuery`)가 이 레이어의 첫 entity다 — `GET /me`를 `staleTime: Infinity`/`retry: false`로 캐싱한다(techspec-auth-onboarding.md §1). 로그인/회원가입/로그아웃 뮤테이션은 세션이 바뀔 때마다 `queryClient.invalidateQueries({queryKey: sessionKeys.current()})`만 호출하면 되고, 세션 갱신 로직을 직접 구현하지 않는다.
- **멀티스텝 위저드 폼(첫 사례: `features/sign-up`)은 스텝마다 별도 `useForm` 인스턴스를 쓰지 않고, 하나의 `useForm` + 하나의 zod 스키마를 전체 스텝에 걸쳐 공유**한다(techspec-overview.md §8). 스텝별 필드만 검증하려면 `form.trigger(['필드1', '필드2'])`로 해당 필드만 트리거한다 — zod resolver는 스키마 전체를 파싱하지만 RHF의 `trigger(names)`는 요청한 필드의 에러만 `formState.errors`에 반영하므로, 아직 도달하지 않은 다음 스텝의 필수 필드(예: 이메일 인증 코드) 때문에 현재 스텝 제출이 막히지 않는다. `form.handleSubmit()`은 스키마 전체를 검증하므로 스텝별 제출에는 쓰지 않는다.
- **shadcn `Checkbox`(`packages/ui`)는 네이티브 `<input>`이 아니라 Radix `checked`/`onCheckedChange` API**라 RHF `register()`로 못 묶는다 — `Controller`로 감싸거나(단일 필드), 두 필드를 동시에 다뤄야 하면(예: "전체 동의" 마스터 체크박스) `form.watch([...])`로 현재 값을 읽고 `form.setValue(name, value, { shouldValidate: true })`로 갱신하는 편이 중첩 `Controller`보다 간단하다.
- **(US-029) 라우터 컨텍스트에 `queryClient`가 실려있다**: `routes/__root.tsx`는 `createRootRoute` 대신 `createRootRouteWithContext<{ queryClient: QueryClient }>()`를 쓰고, `app/router.tsx`가 `createRouter({ routeTree, context: { queryClient } })`로 넘긴다(`queryClient`는 `app/providers.tsx`가 export하는 단일 인스턴스 — `QueryClientProvider`와 라우터 컨텍스트가 반드시 같은 인스턴스를 공유해야 캐시가 맞는다). **인증이 필요한 라우트는 `entities/session`의 `requireSession(queryClient, href)`를 `beforeLoad: ({ context, location }) => requireSession(context.queryClient, location.href)`로 호출**하면 된다(techspec-auth-onboarding.md §1) — 세션이 없으면(`GET /me` 401) `/login`으로 리다이렉트하고 원래 목적지를 `search.redirect`에 보존한다. `shared/lib/api/client.ts`의 `setUnauthorizedHandler`(US-005)는 이 용도로 쓰지 않는다 — 세션 체크 자체가 항상 401 없이 성공하는 게 아니라서(비로그인 방문자의 홈 화면 등) 전역으로 걸면 모든 게스트 방문이 로그인으로 튕기는 회귀가 생긴다. 이 훅은 "이미 로드된 화면에서 세션이 만료된 채 뮤테이션을 호출" 같은 별개 시나리오를 위해 미배선 상태로 남겨둔다.
- **세션 쿼리 옵션은 `entities/session/api/session-query-options.ts`의 `sessionQueryOptions`(`queryOptions()`로 생성) 하나를 `useSessionQuery`(컴포넌트용 `useQuery`)와 `requireSession`(라우터 가드용 `ensureQueryData`) 양쪽이 공유한다** — 쿼리키/함수/`staleTime`/`retry`가 어긋나면 캐시가 갈라지므로 새로 세션을 참조하는 코드는 이 옵션 객체를 그대로 재사용할 것.
- **(US-030) TanStack Router 플랫 파일명은 `.`으로 경로 세그먼트를 구분한다**: `routes/onboarding.google.tsx` → `/onboarding/google`. 새 라우트를 추가한 뒤에는 항상 `vite build`(또는 `vite dev` 1회)로 `routeTree.gen.ts`를 갱신할 것(위 커밋 정책과 동일).
- **(US-031) 라우트 진입 자체에 서버 검증 데이터가 필요하면 `beforeLoad`가 아니라 `loader`/`loaderDeps`를 쓴다**: `routes/reset-password.tsx`가 `loaderDeps: ({ search }) => ({ token: search.token })` + `loader: async ({ deps }) => ({ isTokenValid: await validatePasswordResetToken(deps.token) })`로 토큰을 검증한다. `requireSession`(beforeLoad, US-029)과 동일한 원칙을 따른다 — 실제 API 호출/에러 처리는 라우트 파일이 아니라 해당 `features/*`의 순수 async 함수에 두고, 라우트는 훅에 배선만 한다. 컴포넌트에서는 `Route.useLoaderData()`로 결과를 읽는다.
- **(US-030) 두 위저드가 완전히 같은 스텝 컴포넌트를 공유해야 하면(techspec이 "동일 컴포넌트 재사용"을 명시하는 경우) `features/*` 슬라이스 간 직접 import를 허용한다** — `features/onboarding-google`가 `features/sign-up`의 `GuardianConsentStep`/`useGuardianConsentMutation`/`SignUpFormValues`를 그대로 가져다 쓴다(이 저장소 첫 feature-to-feature import). 이 파일 최상단 레이어 규칙("역방향 import 금지")은 방향성만 금지할 뿐 동일 레이어 슬라이스 간 재사용까지 막지는 않는다 — 단, 재사용할 컴포넌트가 상대 feature에 구조적으로 결합되지 않고 폼 타입에 대해 완전히 제네릭일 때만 이 패턴을 쓸 것(그렇지 않다면 `entities/`로 끌어올릴 것). 새 `useForm` 인스턴스는 위저드마다 별도로 만들되(다른 페이지라 상태 공유가 불가능/불필요) 재사용 컴포넌트가 기대하는 타입은 그대로 import해 구조적 호환을 보장하고, jotai 스텝 atom도 위저드마다 새로 만들 것(모듈 전역 싱글턴이라 공유하면 라우트 간 스텝 상태가 샌다).
- **(US-033) 전역 `Header`는 `widgets/header`에 있고 `routes/__root.tsx`의 `RootComponent`(`<Header /><Outlet /></>`)에 한 번만 마운트된다** — 개별 라우트/페이지가 각자 헤더를 렌더링하지 않는다. 로그인 여부는 `useSessionQuery()`의 `data` 유무로 분기(`me`가 있으면 알림 벨+프로필 드롭다운, 없으면 로그인 버튼)하며, "로그인 사용자 전용" 하위 컴포넌트(`ProfileMenu` 등)는 `me: MeResponse`를 props로 받아 내부에서 세션을 다시 조회하지 않는다.
- **(US-033) 로그아웃처럼 "이 뮤테이션 성공 시 이미 마운트된 모든 컴포넌트가 세션 소실을 즉시 반영해야 하는" 경우엔 `queryClient.invalidateQueries`가 아니라 `resetQueries({ queryKey: sessionKeys.current() })`를 쓴다** — `invalidateQueries`는 스테일 표시 후 백그라운드 리페치가 끝날 때까지 기존(로그인) `data`를 그대로 유지해 헤더가 한 박자 늦게 바뀌고, `setQueryData(key, undefined)`는 TanStack Query가 "새 값이 `undefined`면 문서화된 no-op"으로 스킵해버려 아예 안 먹힌다. `resetQueries`만 살아있는 Query 객체의 `state.data`를 실제로 비우고 옵저버에 동기적으로 알린다(`features/logout/api/mutations.ts` 참고). 세션 관련 다른 뮤테이션(로그인/회원가입 등)은 기존 `invalidateQueries` 그대로 — 그쪽은 "없음→있음"이라 리페치 지연이 체감되지 않는다.
- **(US-033) 헤더의 프로필 드롭다운이 가리키는 라우트 중 아직 자기 스토리가 구현되지 않은 화면은 `shared/ui/ComingSoonPage.tsx`(제목/설명 props만 받는 범용 placeholder)로 임시 연결한다** — 빈 라우트나 404 대신 최소한의 안내 화면을 두어 헤더 자체는 완전한 상태로 유지하고, 실제 화면이 완성되는 스토리(예: 마이페이지=US-034, 프로필=US-035/036)에서 `ComingSoonPage` 호출부만 실제 컴포넌트로 교체하면 된다. 라우트 파일(`routes/{name}.tsx`)은 이미 그 스토리의 최종 형태(예: `beforeLoad: requireSession`)로 만들어두어 나중에 다시 손댈 필요가 없게 한다.
- **(US-034) 같은 ComingSoonPage 패턴을 마이페이지 밖에서도 쓴다**: 초안 카드가 이동하는 `/builder/$type/$draftId`(`routes/builder.$type.$draftId.tsx`, `pages/builder`)는 아직 빌더 스토리(US-100/US-106)가 없어 `ComingSoonPage`로 연결해뒀다 — 그 두 스토리에서 `pages/builder/ui/BuilderPage.tsx` 내부만 실제 빌더로 교체하면 되고, 라우트 파일(파라미터 파싱, `requireSession`)은 이미 최종 형태다.
- **(US-034) `DraftSummary`(`GET /me/drafts`)는 `thumbnailAssetId`(자산 UUID)만 주고 실제로 렌더링 가능한 URL을 주지 않는다** — 코드베이스 전체에 asset → 공개 URL로 변환하는 엔드포인트/유틸이 아직 하나도 없다(`apps/api`의 자산 API는 presigned PUT 업로드/완료 확인만 제공, GET/공개 read 경로 없음). `techspec-builder-common.md`의 `Draft` 예시 타입은 `thumbnailUrl`을 가정하지만 실제 구현은 다르다. 마이페이지 초안 카드는 그래서 이미지 없이 타입 아이콘(`lucide-react`의 `UserRound`/`BookOpen`)만 보여준다 — 홈/프로필/콘텐츠 상세처럼 실제 썸네일 이미지를 그려야 하는 다음 스토리(US-036 이후)에서 이 gap을 먼저 해결해야 한다(예: presigned GET 엔드포인트 추가, 또는 버킷을 공개 read로 설정하고 `storage_key`로 직접 URL을 구성).
- **(US-034) 파괴적 확인 모달의 첫 사례(회원탈퇴)는 `techspec-overview.md` §9가 지정한 `react-call`이 아니라 `packages/ui`에 새로 추가한 shadcn `alert-dialog`(Radix `AlertDialog`, 비제어 상태)를 그대로 썼다** — react-call은 이 저장소에 아직 의존성으로 없고, 단일 확인/취소 다이얼로그 하나에 새 라이브러리를 들이는 것보다 이미 있는 Radix 컴포넌트로 충분했다(`features/withdraw-account/ui/WithdrawAccountDialog.tsx`). `techspec-overview.md` §9 표에 나열된 다른 액션형 모달(신고 사유 선택=US-018, 삭제 확인=US-049 등)에 착수할 때 이 저장소에 react-call을 실제로 도입할지, 아니면 이 AlertDialog 패턴을 계속 재사용할지 먼저 판단할 것 — 지금은 둘 다 가능한 미확정 상태로 남겨둔다.
- **(US-035) 데이터 입력 폼 모달의 첫 사례(프로필 수정)도 `react-call` 없이 `packages/ui`의 평범한 shadcn `Dialog`(`open`/`onOpenChange`로 제어)를 그대로 썼다** — 비동기 저장 성공 시 프로그램적으로 닫아야 해서(단순 확인/취소가 아니라 "저장 중... → 성공 시 닫기") uncontrolled `DialogClose` 트리거만으로는 부족했다. `open` state를 열 때마다 `form.reset(defaultValues)`로 최신 서버 데이터로 되돌리는 것도 이 패턴에서 함께 처리한다(`features/edit-profile/ui/EditProfileDialog.tsx`의 `handleOpenChange` 참고). US-034의 react-call 미확정 메모와 마찬가지로, 다음 폼형 모달에서도 이 Dialog-직접-제어 패턴을 재사용할지 react-call을 들여올지는 그때 다시 판단한다.
- **(US-035) 자산 → 렌더링 가능한 URL 변환 갭(US-034가 남긴 이슈)은 BE가 해결했다**: `GET /users/{id}/profile`/`PATCH /me/profile`의 `UserProfileResponse`에 `profileImageUrl`(presigned GET URL, 매 조회마다 새로 서명됨 — 캐시하지 말 것)이 추가됐다. `DraftSummary`/`ContentSummary`의 `thumbnailAssetId`는 아직 이 필드가 없다 — 그 화면들이 실제 썸네일을 그려야 할 때 동일한 BE 패턴(`apps/api/CLAUDE.md`의 `generate_presigned_get_url` 참고)을 요청할 것.
- **(US-035) 첫 자산 업로드 플로우: `shared/lib/asset/uploadAsset.ts`의 `uploadAsset(file, purpose)`**가 presigned URL 발급(`POST /assets/presigned-upload`) → S3 직접 PUT(`fetch`, `apiClient` 아님 — 쿠키/baseURL이 없는 외부 절대 URL이라 인터셉터를 태우면 안 된다) → 완료 확인(`POST /assets/{id}/complete`) 3단계를 감싸고 최종 `assetId`를 반환한다. 다음에 이미지를 업로드하는 기능(상황별 이미지 등)은 이 유틸을 그대로 재사용할 것 — `purpose`만 새 `AssetPurpose` 값으로 바꾸면 된다.
- **(US-035) 라우트 동적 파라미터(`$userId`)도 검색 파라미터(US-031의 `loaderDeps`/`token`)와 동일한 원칙을 따른다**: 페이지 컴포넌트가 `routes/*.tsx`를 다시 import(`Route.useParams()`)하면 `routes → pages → routes` 순환 참조가 생기므로, 라우트 파일 안의 `RouteComponent`가 `Route.useParams()`로 값을 읽어 페이지에 **props로** 넘긴다(`routes/profile.$userId.tsx` 참고). `component: PageComponent`를 바로 넘기던 이전의 단순 라우트(파라미터가 없거나 페이지가 직접 `Route.useParams()`를 호출해도 순환이 없는 경우, 예: US-034 이전 라우트들)와 달리, 파라미터가 있고 페이지를 재사용/테스트 가능하게 두려면 이 wrapper 패턴이 필요하다.
- **(US-035) TanStack Query의 기본 `retry`(3회, 지수 백오프)는 4xx처럼 재시도해도 절대 성공하지 않는 에러에는 맞지 않는다** — `useProfileQuery`(`entities/profile`)는 `retry: (failureCount, error) => (error.status === 0 || error.status >= 500) && failureCount < 3`로 커스텀해 404(존재하지 않는 사용자) 같은 결정적 에러는 즉시 에러 상태로 넘어가게 했다(안 그러면 에러 UI가 뜨기까지 여러 초가 걸린다). 쿼리 결과의 `status`로 에러 화면을 분기하는 다음 read-쿼리도 이 패턴을 재사용할 것 — `QueryClient`(`app/providers.tsx`) 자체에는 아직 전역 기본값이 없다.
