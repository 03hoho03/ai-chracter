# apps/web

- FSD 레이어 의존 방향: `app → pages → widgets → features → entities → shared` (역방향 import 금지). `routes/*`는 로직 없이 `pages/{page}`를 렌더링만 하는 얇은 어댑터로 유지한다.
- `src/routeTree.gen.ts`는 TanStack Router의 `@tanstack/router-plugin` Vite 플러그인이 `vite dev`/`vite build` 실행 시 자동 생성하는 파일이며, `tsc --noEmit`만으로는 fresh checkout에서 생성되지 않으므로 **git에 커밋**한다. 라우트를 추가/변경했다면 typecheck·커밋 전에 `vite build`(또는 `vite dev` 1회)를 먼저 실행해 이 파일을 최신 상태로 갱신해야 한다. 갱신을 빼먹어도 typecheck는 통과하지만(오래된 트리 기준으로만 검사) 새 라우트가 검증에서 누락된다.
- 디자인시스템은 `packages/ui`(shadcn+Tailwind v4)를 그대로 쓴다. `vite.config.ts`에 `@tailwindcss/vite` 플러그인이 등록되어 있고, `main.tsx`에서 `@ai-character-chat/ui/globals.css` 한 번만 import하면 전체 앱에 토큰/유틸리티가 적용된다(이 앱 자체는 별도 `tailwind.config`/전역 css를 갖지 않는다). 컴포넌트는 `@ai-character-chat/ui/components/{name}`에서 가져온다. 자세한 내용은 `packages/ui/CLAUDE.md` 참고.
- 모든 API 호출은 `shared/lib/api/client.ts`가 export하는 단일 `apiClient` axios 인스턴스를 거친다(직접 `axios.create` 금지). 인증은 httpOnly 세션 쿠키 + `withCredentials: true`로 처리되므로 요청 인터셉터에서 토큰을 붙이지 않는다. 응답 인터셉터가 모든 에러를 `@ai-character-chat/api-types`의 `ApiError`로 정규화해 reject하므로, 호출부의 `catch`/`onError`는 axios 원본 에러가 아니라 이 포맷을 받는다. 401 시 로그인 리다이렉트는 아직 미연결 — 로그인 라우트가 생기면 `setUnauthorizedHandler(() => router.navigate(...))`를 앱 초기화 시점(`app/providers.tsx` 등)에 한 번 등록한다.
- **`ApiError`는 FastAPI가 실제로 내려주는 `{"detail": ...}` 형태를 그대로 반영한다** (US-028에서 수정 — 이전 버전은 `{code, message, fields}`를 가정했는데 apps/api의 실제 에러 바디와 전혀 맞지 않았고, 그때까지 어떤 FE 코드도 실제 에러를 소비한 적이 없어 발견되지 않은 채로 있었다). `detail`이 string이면 HTTPException 메시지 그대로, dict면 구조화된 값(예: 429 응답의 `retryAfterSeconds`), 422 배열이면 `fields`로 필드명→메시지 매핑까지 펼쳐진다. 새 화면에서 서버 에러 메시지를 그대로 노출하기보다, `apiError.status`로 분기해 한국어 카피를 직접 작성하는 편이 일관된 UX를 준다(BE의 `detail` 문자열은 영어 디버그 메시지라 사용자 노출용이 아님).
- **`entities/session`**(`sessionKeys`, `useSessionQuery`)가 이 레이어의 첫 entity다 — `GET /me`를 `staleTime: Infinity`/`retry: false`로 캐싱한다(techspec-auth-onboarding.md §1). 로그인/회원가입/로그아웃 뮤테이션은 세션이 바뀔 때마다 `queryClient.invalidateQueries({queryKey: sessionKeys.current()})`만 호출하면 되고, 세션 갱신 로직을 직접 구현하지 않는다.
- **멀티스텝 위저드 폼(첫 사례: `features/sign-up`)은 스텝마다 별도 `useForm` 인스턴스를 쓰지 않고, 하나의 `useForm` + 하나의 zod 스키마를 전체 스텝에 걸쳐 공유**한다(techspec-overview.md §8). 스텝별 필드만 검증하려면 `form.trigger(['필드1', '필드2'])`로 해당 필드만 트리거한다 — zod resolver는 스키마 전체를 파싱하지만 RHF의 `trigger(names)`는 요청한 필드의 에러만 `formState.errors`에 반영하므로, 아직 도달하지 않은 다음 스텝의 필수 필드(예: 이메일 인증 코드) 때문에 현재 스텝 제출이 막히지 않는다. `form.handleSubmit()`은 스키마 전체를 검증하므로 스텝별 제출에는 쓰지 않는다.
- **shadcn `Checkbox`(`packages/ui`)는 네이티브 `<input>`이 아니라 Radix `checked`/`onCheckedChange` API**라 RHF `register()`로 못 묶는다 — `Controller`로 감싸거나(단일 필드), 두 필드를 동시에 다뤄야 하면(예: "전체 동의" 마스터 체크박스) `form.watch([...])`로 현재 값을 읽고 `form.setValue(name, value, { shouldValidate: true })`로 갱신하는 편이 중첩 `Controller`보다 간단하다.
- **(US-029) 라우터 컨텍스트에 `queryClient`가 실려있다**: `routes/__root.tsx`는 `createRootRoute` 대신 `createRootRouteWithContext<{ queryClient: QueryClient }>()`를 쓰고, `app/router.tsx`가 `createRouter({ routeTree, context: { queryClient } })`로 넘긴다(`queryClient`는 `app/providers.tsx`가 export하는 단일 인스턴스 — `QueryClientProvider`와 라우터 컨텍스트가 반드시 같은 인스턴스를 공유해야 캐시가 맞는다). **인증이 필요한 라우트는 `entities/session`의 `requireSession(queryClient, href)`를 `beforeLoad: ({ context, location }) => requireSession(context.queryClient, location.href)`로 호출**하면 된다(techspec-auth-onboarding.md §1) — 세션이 없으면(`GET /me` 401) `/login`으로 리다이렉트하고 원래 목적지를 `search.redirect`에 보존한다. `shared/lib/api/client.ts`의 `setUnauthorizedHandler`(US-005)는 이 용도로 쓰지 않는다 — 세션 체크 자체가 항상 401 없이 성공하는 게 아니라서(비로그인 방문자의 홈 화면 등) 전역으로 걸면 모든 게스트 방문이 로그인으로 튕기는 회귀가 생긴다. 이 훅은 "이미 로드된 화면에서 세션이 만료된 채 뮤테이션을 호출" 같은 별개 시나리오를 위해 미배선 상태로 남겨둔다.
- **세션 쿼리 옵션은 `entities/session/api/session-query-options.ts`의 `sessionQueryOptions`(`queryOptions()`로 생성) 하나를 `useSessionQuery`(컴포넌트용 `useQuery`)와 `requireSession`(라우터 가드용 `ensureQueryData`) 양쪽이 공유한다** — 쿼리키/함수/`staleTime`/`retry`가 어긋나면 캐시가 갈라지므로 새로 세션을 참조하는 코드는 이 옵션 객체를 그대로 재사용할 것.
