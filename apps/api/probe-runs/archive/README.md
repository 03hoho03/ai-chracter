# 채팅 품질 실험 아카이브 (2026-08)

이 디렉터리만 git 이 추적한다. 상위 `probe-runs/` 는 매 실행마다 쌓이는 스크래치라 gitignore 다.

**왜 커밋하는가.** Gemini 무료 티어는 **모델당 하루 20요청**이고 1턴이 LLM 2회라, 한 회차를 다시 모으는 데 며칠이 걸린다. 게다가 여기 담긴 조건 일부는 **재현이 불가능하다** — `gemini-2.5-flash-lite` 는 이후 `404 no longer available to new users` 로 막혔고, `2026-08-10` 회차의 프롬프트 조합은 코드에서 이미 사라졌다. 예전에 대화록을 `/tmp` 에 뒀다가 정리되면서 베이스라인 원본을 잃은 적이 있어(수치만 남고 재분석 불가) 같은 실수를 막으려고 남긴다.

## 무엇을 잰 실험인가

스토리 챗 응답 품질(되받기·길이·한국어 깨짐)을 **한 세트로 고정해 반복 측정**한다. 사용자 발화는 `chat_probe.py` 의 고정 대본이라 모든 런에서 글자 하나까지 같고, 달라지는 것은 모델과 설정뿐이다.

- **1라운드(08-11)** — 스토리 `romance-lockedwith` 하나, 시작설정 2개 × 5턴, 모델 7종. 프롬프트 고정, `GEMINI_MODEL_NAME` 만 교체.
- **2라운드(08-14)** — 같은 스토리, 시작설정 1개 × 5턴. 출력 상한 8192 고정 후 **사고(thinking) 켬/끔**만 가름.
- **3라운드(09-08)** — 모델·설정을 `gemini-3.5-flash-lite` 로 고정하고 **바닥 시스템 지시문만** 가른다. 기준 스토리 2종(주 `daily-lastorder` + 대조 `wuxia-oneform`) × 5턴을 같은 날 세 조건으로 연달아 돌렸다: 지시문 없음 / 지시문(금지 라벨을 예시로 나열) / 지시문(예시 제거).
- **4라운드(09-09)** — `[턴을 열어 둔다]` 블록의 효과. 모델을 `gemini-2.5-flash`(프로덕션과 같은 값)로 고정하고 **`GEMINI_SEED` 42/43/44 로 짝지어** 커밋 두 개(`10feef9` 없음 / `33b2588` 있음)에서 각각 A세트(밥집 재현 4턴)·B세트(기준 스토리 2종 ×5턴)를 돌렸다. 12회차 336요청.
- **08-10** — 별개 실험(시스템 지시문, 스토리 18종 90턴). 회귀 확인용 기준선으로만 쓴다.

## 이 실험이 찾은 것

1·2라운드에서는 버그 두 개가 나왔고 **둘 다 모델이 아니라 계측 쪽이었다.**

1. **출력 상한이 사고 토큰과 응답이 나눠 쓰는 예산이었다.** 사고형 모델의 응답이 문장 중간에서 잘렸다(`gemini-3.5-flash` 8턴 중 5턴). 상한을 8192 로 올려 해결 — 커밋 `ed4a61c`.
2. **분석기가 유실 턴 뒤의 턴 번호를 밀어서 셌다.** 되받기율이 25%→62% 로 뒤집혔다 — 커밋 `0be3cb8`. **이 아카이브의 수치를 인용할 때는 반드시 그 커밋 이후의 분석기로 다시 낼 것.**

3라운드에서는 처음으로 **모델이 아니라 프롬프트 쪽에서** 두 개가 나왔다.

3. **길이 −35% 를 "되받기 금지 문장이 초점을 좁힌 부수효과"로 본 가설이 기각됐다.** 그 문장을 뺀 3블록 지시문으로 같은 날 OFF/ON 을 연달아 돌렸더니 628자→402자(−36%)로 감소 폭이 거의 같았다. 길이를 줄이는 것은 그 문장이 아니라 **지시문의 존재 자체 또는 나머지 블록**이다 — 어느 쪽인지는 아직 절제하지 않았다.
4. **금지 대상을 예시로 나열하면 그 토큰이 출력에 유도된다.** `라벨(예: "진행자:", "서술자:")을 붙이지 않는다` 로 적은 회차에서, 지시문 없는 회차에는 없던 `(서술자: …)` 가 응답 첫 줄에 나왔다(10턴 중 1건 / OFF 0건). 예시를 지운 회차는 0건이다. 표본이 얇아 0건이 수정의 증거는 아니지만, **예시를 빼는 근거는 측정이 아니라 관찰 자체다.**

수치와 정독 결과 전문은 `reports/` 의 HTML 을 볼 것 — 다만 그 리더는 08-14 까지만 담고 있다(`tools/build_reader.py` 의 `FILES` 가 명시 목록이라 3라운드는 들어 있지 않다).

## 구성

| 경로 | 내용 |
|---|---|
| `transcripts/` | 대화록 원본 JSON. 이것만이 대체 불가능한 1차 자료다. |
| `reports/` | 사람이 읽는 산출물. `2026-08-14_transcripts.html` 은 대화록을 절단 지점·자기복제 구간·되받기 표지까지 표시해 보여주는 리더다. |
| `tools/` | 그 리더를 대화록에서 다시 만드는 일회성 생성기. |

`transcripts/` 파일명이 곧 조건이다: `<날짜>_<모델>[_max<상한>][_think-on|off][_가른 조건][_상태].json`. `partial`/`failed` 가 붙은 것은 중간에 깨진 런인데, **실패 자체가 데이터라서** 지우지 않았다 — `..._failed-400-invalid-argument.json` 은 `gemini-3.6-flash` 가 `thinking_budget=0` 을 거부한다는 증거다.

모델 이름은 파일명이 아니라 **파일 안 `model` 필드**가 정본이다(파일명은 옮기는 순간 증거가 사라진다).

## 다시 분석하려면

```sh
cd apps/api
uv run python scripts/analyze_chat_probe.py \
  probe-runs/archive/transcripts/2026-08-11_gemini-3.5-flash-lite.json \
  probe-runs/archive/transcripts/2026-08-11_gemini-3.5-flash.json     # 파일을 나열한 순서대로 열이 선다
```

`--json` 을 붙이면 표 대신 기계가 읽는 형태로 나온다. 리더를 다시 만들려면 `python tools/build_reader.py`.

**LLM 호출이 전혀 없으므로 재분석은 쿼터를 쓰지 않는다.** 지표를 고친 뒤에는 항상 `2026-08-10_flash-lite_with-system-instruction.json` 으로 회귀를 확인할 것 — 유실 턴이 0 이라 수치가 변하면 안 되는 파일이고, 실제로 턴 인덱스 버그를 고칠 때 이 파일이 기준선 역할을 했다.

## 새 회차를 돌릴 때 주의

- **쿼터**: 비-lite 는 하루 20요청 / 분당 5. lite 계열은 훨씬 넉넉하다. 리셋은 KST 자정이 아니라 **태평양 자정(≈16:00 KST)** 이다.
- 비-lite 모델은 `--interval 24` 를 써야 429 로 턴을 잃지 않는다(기본 10초는 분당 15 전제).
- **503 에 재시도를 걸지 말 것** — 재시도 한 번이 곧 일일 요청 한 건이라 예산을 통째로 태운 적이 있다.
- 모델 교체는 `GEMINI_MODEL_NAME` env + **uvicorn 재기동**이 필요하다(서버 프로세스 env 로만 먹는다). 반면 **코드로 가른 조건(지시문 등)은 브랜치 체크아웃만으로 갈린다** — uvicorn `--reload` 가 집어가므로 토글을 코드에 남길 필요가 없다.
- **2스토리×5턴(10턴)으로는 되받기를 판정하지 못한다.** 3라운드에서 라벨 예시 한 줄만 다른 두 회차가 앞250자 기준 40% 와 80% 로 갈렸다(대조 `wuxia-oneform` 이 0/5 → 3/5). 그 한 줄이 되받기를 2배로 만들 인과 경로가 없으니 회차 간 변동으로 읽어야 한다. 같은 표본에서 **길이는 안정적이었다** — 10턴은 길이용이지 되받기용이 아니다.

## 아직 안 푼 것

대화 품질 자체는 손대지 않았다. 정독에서 드러난 것들인데 **모델을 바꿔도 사고를 꺼도 변하지 않아, 원인이 모델이 아니라 프롬프트 구조로 보인다**:

- 서술자가 사용자의 표정·감정·말투를 대신 쓴다(플레이어 주도권 침해).
- 매 턴이 같은 골격이다 — `지문 → 되뇜(따옴표+말줄임표) → 지문 → 대사`.
- 클리셰 재고가 모델 간에 거의 동일하다.
- 질문에 답하지 않고 되묻는다.


## 4라운드에서 배운 것 (09-09)

**~~`GEMINI_SEED` 가 실제로 결정성을 준다`~~ — 이 주장은 틀렸다(2026-09-09 09-09 회차에서 반증).** 당시 "같은 조건 2회차가 글자 단위로 동일했다"고 적었으나, 같은 날 오후에 다시 재면 성립하지 않는다. 확인 방법과 결과:

- 같은 서버 프로세스·`GEMINI_SEED=42`·같은 대본으로 한 스토리를 연달아 두 번 → **3턴 전부 다름**(히스토리가 없는 t1 포함).
- 프로브를 빼고 `GeminiLLMClient.generate()` 를 같은 프롬프트로 두 번 → **다름**. 이때 `settings.gemini_seed == 42` 이고 `gemini.py` 가 `config.seed` 에 넣는 것도 확인했다. **설정은 도달하는데 모델이 안 지킨다.** Google 문서의 "best effort, 보장 없음" 그대로다.

따라서 **seed 를 바꾼 여러 회차는 '짝지은 비교'가 아니라 그냥 독립 반복이다.** 방향 일관성으로 읽는 설계 자체는 유효하지만, "seed 가 표본을 고정하므로 처치만 다르다"는 근거는 못 쓴다. 이 주장을 인용한 문서를 고칠 때 이 문단을 근거로 삼을 것.

**seed 하나로 판정하면 오독한다.** B세트의 `의문·청유` 가 seed 42 에서 −5, 43 에서 +3, 44 에서 +5 로 방향이 갈렸다. 42 만 봤으면 "회귀"로 결론냈을 것이다.

**`의문·청유 어미` 지표는 "묻는 형태"의 열기만 센다.** 기준선이 `"당신은 어떤 선택을 하시겠습니까?"` 처럼 서술자가 극 밖으로 나와 묻고 있었고, 처방이 그것을 장면 상태로 바꾸자 지표가 떨어졌다 — 나빠진 게 아닌데 나빠졌다고 셌다. **정답지(밥집 닫힘 vs 이도윤 열림)에서 이도윤이 사연 받는 DJ 라 질문 형태에 쏠린 것이 원인이다.** 장면 이동형 열기를 세는 지표가 따로 필요하다.
