# apps/api

- `uv`로 관리되는 독립 Python 프로젝트. pnpm workspace/turborepo 범위 밖이므로 루트 `pnpm run typecheck` 등에 걸리지 않는다 — 이 앱의 quality check(`uv run mypy src migrations scripts`, `uv run pytest` 등)는 항상 `apps/api` 안에서 별도로 실행해야 한다.
- `scripts/`는 `src/api` 패키지 밖의 1회성 CLI 스크립트 모음(현재 `export_openapi.py`뿐)이다 — `mypy` 대상 경로 목록(`src migrations scripts`, `.github/workflows/api.yml`과 로컬 명령 동일하게 유지)에 반드시 포함시킬 것. FE 타입 코드젠 파이프라인 전체 설명은 `packages/api-types/CLAUDE.md` 참고.
- src-layout: 패키지명은 `api`(`src/api/`), 모듈 경로는 `api.main`/`api.core.config`/`api.db.session` 식으로 임포트한다. `uv sync`가 이 패키지를 editable로 설치하므로 `uv run` 안에서는 항상 `import api...`가 그대로 동작한다.
- DB 연결 문자열은 `api.core.config.settings.database_url` (pydantic-settings, `.env`/`DATABASE_URL` env var)이 유일한 source of truth다. `alembic.ini`의 `sqlalchemy.url`은 플레이스홀더일 뿐이며 `migrations/env.py`가 기동 시점에 `config.set_main_option`으로 덮어쓴다 — 마이그레이션용 DB URL을 따로 관리하지 않는다.
- `migrations/env.py`의 `target_metadata`는 `api.db.base.Base.metadata`를 가리킨다. 새 모델은 반드시 이 `Base`를 상속해야 `alembic revision --autogenerate`가 인식한다.
- mypy는 `pyproject.toml`의 `[tool.mypy]`에서 `strict = true`로 설정되어 있다. 새 모듈 추가 시 타입 힌트 누락이 있으면 바로 실패한다.
- 모델은 `src/api/db/models/{domain}.py`(예: `auth.py`, `media.py`)로 techspec-overview-backend.md §6의 기능별 BE 문서 경계를 그대로 도메인 파일 경계로 삼는다. `src/api/db/models/__init__.py`가 모든 서브모듈을 import해 `Base.metadata`를 채우고, `migrations/env.py`도 `from api.db import models`로 그 패키지를 import해야 `alembic revision --autogenerate`가 새 테이블을 인식한다(모델만 추가하고 이 import를 빼먹으면 autogenerate가 빈 diff를 낸다).
- **순환 FK(예: users.profile_image_asset_id -> assets.id 와 assets.owner_user_id -> users.id)**: 모델 쪽은 `ForeignKey(..., use_alter=True, name=...)`로 선언하면 되지만, `alembic revision --autogenerate`가 생성하는 마이그레이션은 이 FK를 여전히 `op.create_table`의 인라인 `ForeignKeyConstraint`로 렌더링한다 — `use_alter`는 `MetaData.create_all()`에서만 자동으로 지켜지고 `op.create_table`은 존중하지 않는다. 그대로 두면 아직 존재하지 않는 테이블을 참조하는 인라인 FK라 즉시 실패(또는 조용히 무시)한다. **autogenerate 직후 항상 수동으로** 그 인라인 FK를 지우고 두 테이블이 모두 생긴 뒤 `op.create_foreign_key(...)` 호출로, downgrade에는 테이블 drop 전에 `op.drop_constraint(..., type_='foreignkey')`를 넣어야 한다.
- **Postgres ENUM 컬럼과 `op.drop_table`**: autogenerate가 만드는 `op.drop_table('assets')`는 테이블명만 담고 컬럼 정보가 없어서, `sa.Enum` 컬럼에 연결된 타입의 DROP TYPE 이벤트가 발생하지 않는다 — enum 타입이 DB에 남아 다음 upgrade에서 `DuplicateObjectError: type "X" already exists`로 실패한다. downgrade 마지막에 `sa.Enum(name='asset_kind').drop(op.get_bind(), checkfirst=True)`를 수동으로 추가해야 한다.
- `uv run alembic check`로 모델과 마이그레이션이 정확히 일치하는지(추가 diff 없음) 확인할 수 있다 — 마이그레이션을 손으로 고친 뒤 반드시 재실행해서 검증할 것.
- **자동생성 마이그레이션은 반드시 첫 `alembic upgrade head` 실행 전에 손으로 고칠 것** (순환 FK 등). 이미 그 리비전이 적용된 로컬 DB에 대해 나중에 `downgrade()`를 고치면, Alembic은 리비전 ID만 추적하고 실제로 실행됐던 SQL은 추적하지 않으므로 `UndefinedObjectError: constraint ... does not exist` 같은 불일치가 난다 — 이 경우 DB를 새로 만들고(`DROP DATABASE`/`CREATE DATABASE`) 처음부터 다시 적용해야 한다.
- **시드 데이터가 필요한 마이그레이션**(예: `genres` 10종)은 `upgrade()`에서 `op.execute("INSERT INTO ...")`로 넣되, PK는 마이그레이션 실행 시점에 `uuid.uuid4()`를 호출하지 말고 작성 시점에 하드코딩한 리터럴 UUID를 쓴다 — 그래야 dev/CI/prod 어느 환경에서 실행하든 같은 ID가 재현된다. 해당 테이블 자체를 `downgrade()`에서 `op.drop_table`하면 시드 로우도 함께 사라지므로 별도 DELETE는 불필요.
- **pytest 설정**: `pyproject.toml`의 `[tool.pytest.ini_options]`에 `asyncio_mode = "auto"` 외에 `asyncio_default_fixture_loop_scope`/`asyncio_default_test_loop_scope`를 `"session"`으로 명시해야 한다 — 기본값(함수 스코프)이면 테스트마다 새 이벤트 루프가 생기는데, 모듈 전역 `engine`(asyncpg 커넥션 풀)은 최초 생성 시점의 루프에 묶여 있어 두 번째 테스트부터 `InterfaceError: cannot perform operation: another operation is in progress`로 깨진다.
- **테스트 DB 인프라**: `tests/conftest.py`의 세션 스코프 `_migrated_schema` 픽스처가 세션 시작 전 `alembic upgrade head`, 종료 후 `downgrade base`를 실행해 마이그레이션 자체를 실행 가능한 테스트로 검증한다. 개별 테스트는 `db_session` 픽스처(커넥션 단위 트랜잭션을 열고 테스트 후 롤백)로 격리된다. 로컬에서 테스트를 돌리려면 `DATABASE_URL`이 실제 PostgreSQL(예: `docker run -d -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=ai_character_chat -p 5432:5432 postgres:16-alpine`)을 가리켜야 한다 — sqlite 등으로 대체하면 INET/ENUM 등 Postgres 전용 타입이 깨진다. `.github/workflows/api.yml`(US-016)은 `apps/api/**` 변경 시 `mypy`/`docker build`만 실행하며, `pytest`는 CI에 아직 붙어 있지 않다(Postgres/Redis 서비스 컨테이너가 필요한데 아직 없음) — 테스트를 CI에 태우는 작업은 이후 별도 스토리에서 다룬다.
- **순환 FK는 "같은 리비전 안에서 새 테이블 두 개가 서로 참조할 때만" 발생한다**: `content_versions`/`assets`처럼 이전 리비전에서 이미 만들어진 테이블을 새 테이블이 참조하기만 하면(예: US-009의 `character_version_details`/`situational_images`) autogenerate가 손댈 것 없이 깨끗하게 나온다. `use_alter`/`op.create_foreign_key` 수동 처리는 진짜로 두 신규 테이블이 서로를 가리킬 때만 필요하다.
- **`entity_id` 패턴 코드 형태**(techspec-db-schema.md §1 원칙 4, 최초 구현은 `character.py`의 `SituationalImage`): 물리적 PK `id`(`Uuid, primary_key=True, default=uuid.uuid4`)와 별개로 `entity_id`(`Uuid`, default 없음, 이 레이어에서는 유니크 제약도 없음 — 앱 레이어가 업서트/재발행 복제 흐름에서 값을 유지)를 분리한 컬럼으로 둔다. 앞으로 같은 패턴을 쓰는 테이블(starting_setups, stat_defs, keyword_notes, shortcuts, endings, ending_rule_groups, ending_rules)도 이 모양을 그대로 따른다.
- 순서가 중요한 목록(§1 원칙 2)은 `order`라는 이름 그대로 `Integer` 컬럼으로 선언해도 된다 — Postgres 예약어지만 SQLAlchemy가 렌더링하는 모든 DDL/DML에서 자동으로 따옴표 처리하므로 모델/마이그레이션 코드에서 별도 이스케이프가 필요 없다.
- **entity_id 패턴 자식이 다른 entity_id 패턴 부모를 참조하는 경우**(예: `stat_defs.starting_setup_id -> starting_setups.id`): 같은 리비전 안에서 부모 테이블이 먼저 `op.create_table`되기만 하면(자식이 부모를 참조하는 단방향 체인일 뿐 순환은 아님) autogenerate가 손댈 것 없이 그대로 통과한다 — 순환 FK 수동 처리는 두 신규 테이블이 "서로" 참조할 때만 필요하다는 규칙(위 항목)의 연장선. `ending_rules.stat_def_entity_id`처럼 FK가 아니라 `entity_id`를 참조하는(버전 넘어 안정적으로 참조, §1 원칙 4) 컬럼은 애초에 제약이 없으니 이 문제와 무관하다.
- **같은 ENUM 이름을 한 리비전 안에서 여러 테이블 컬럼에 재사용해도 안전하다**(예: `ending_rule_groups.next_op`/`ending_rules.next_op`가 동일한 `Enum(LogicalOp, name="logical_op")`): `op.create_table`을 여러 번 호출해도 Postgres `CREATE TYPE`은 한 번만 실행되고 두 번째 테이블 생성 시 "already exists" 에러가 나지 않는다 — 실제로 upgrade/downgrade/upgrade 반복 테스트로 확인함. 다만 downgrade에서는 그 이름을 사용하는 모든 테이블이 drop된 뒤 **단 한 번만** `sa.Enum(name=...).drop(...)`을 호출해야 한다(여러 번 호출은 `checkfirst=True`가 있으면 안전하지만 어차피 한 번으로 충분).
- **애플리케이션 레벨에서 "정확히 하나만 not null" 같은 상호배타 제약**(예: `ending_rules.ending_id`/`rule_group_id`)은 `CheckConstraint("(a IS NOT NULL) <> (b IS NOT NULL)", name=...)`를 모델의 `__table_args__`에 선언하면 DB 레벨에서 강제된다 — autogenerate가 `sa.CheckConstraint`로 그대로 인식하고 마이그레이션에 렌더링하므로 손으로 고칠 필요가 없다(순환 FK/ENUM downgrade와 달리 이 패턴은 autogenerate가 완벽히 처리하는 케이스).
- **복합(다중 컬럼) PK 테이블**(최초 구현은 `chat.py`의 `ChatRoomStat`/`StoryEndingUnlock`/`CharacterImageExposure`, 서로 다른 사용자+엔티티 조합이 계속 누적되는 로그/집계성 테이블): 대리 `id` 없이, PK를 구성하는 각 `mapped_column`에 그냥 `primary_key=True`를 개별로 붙이면 된다 — 별도 `PrimaryKeyConstraint`/`__table_args__` 선언이 필요 없고, autogenerate가 선언 순서대로 `sa.PrimaryKeyConstraint('col_a', 'col_b', ...)`를 첫 시도에 정확히 렌더링한다. 테스트에서 이 모양을 검증하려면 `sa.inspect(conn).get_pk_constraint(table)["constrained_columns"]`를 쓴다(FK/체크제약과는 다른 inspector 메서드). `favorites`/`likes`(§7, `PRIMARY KEY (user_id, content_id)`)도 이 모양을 그대로 따랐다(구현은 `content.py`, techspec-backend-content.md 도메인 경계와 맞춤 — `contents`/`content_versions`/`genres`와 같은 파일).
- **다형(polymorphic) 참조 컬럼**(최초 구현은 `moderation.py`의 `Appeal.target_id`, techspec-db-schema.md §8: `target_kind`에 따라 발행거부 이력 또는 `moderation_actions.id`를 가리킴): 대상 테이블이 `target_kind` 값마다 달라 DB `ForeignKey`를 걸 수 없다. 그냥 `Uuid` 컬럼(FK 없음)으로 선언하고, docstring에 왜 FK가 없는지 이유를 남긴다. 참조 무결성은 애플리케이션 레벨(신고/조치 처리 API)에서 보장해야 한다 — DB는 강제하지 않는다.
- **FastAPI `TestClient`를 쓰는 테스트에서 모듈 전역(import 시점) 커넥션 풀을 가진 async 클라이언트(예: `core/redis.py`의 `redis_client`)를 쓰면, `db_session`/`_migrated_schema` 픽스처와 별개의 새로운 event-loop 이슈가 난다**: `TestClient(app)`는 `with` 블록에 진입할 때마다 자체 백그라운드 스레드에 새 event loop(anyio blocking portal)를 띄우고 블록을 벗어나면 그 loop를 닫는다. pytest-asyncio의 `asyncio_default_fixture_loop_scope="session"`은 이 portal의 loop에는 적용되지 않으므로, 서로 다른 테스트 함수마다 매번 새 `with TestClient(app) as client:`를 열면 이전 블록에서 만들어진 pooled connection(=이제는 닫힌 loop에 묶여 있음)을 재사용하려다 `RuntimeError: Event loop is closed`로 깨진다. 해결: `tests/conftest.py`의 세션 스코프 `api_client` 픽스처처럼 **테스트 세션 전체에서 `TestClient`를 한 번만 열어(`with`) 공유**한다(`db_engine`이 세션 스코프 loop를 공유하는 것과 같은 이유). 테스트 간 쿠키 오염을 막으려면 각 테스트 시작 시 `api_client.cookies.clear()`를 호출할 것. 같은 세션 안에서 서로 다른 "세션"을 동시에 흉내내야 한다면 두 번째 `TestClient` 인스턴스를 열지 말고, 응답의 `Set-Cookie` 값을 직접 캡처해 `api_client.cookies.set(name, value)`로 스위칭하며 순차 호출한다(per-request `cookies=` kwarg는 starlette에서 deprecated).
- **인증이 필요한 라우터의 "현재 사용자" 의존성**: `src/api/session/dependencies.py`의 `get_current_user_id`(FastAPI `Depends`)가 세션 쿠키 → Redis 세션 데이터의 `user_id` 키를 읽어 반환한다. 실제 `/auth/login`(US-021)이 아직 없어도, 세션에 `{"user_id": "..."}`를 넣기만 하면(예: 기존 `/dev/session-echo` 또는 향후 로그인 라우트) 이 의존성을 만족한다 — 로그인이 필요한 새 라우터는 이 파일을 그대로 재사용할 것.
- **camelCase JSON API 응답/요청 스키마**: `src/api/core/schema.py`의 `CamelModel`(pydantic `BaseModel` + `alias_generator=to_camel, populate_by_name=True`)을 상속하면 Python 필드는 snake_case, JSON은 camelCase로 나간다 — techspec 문서들이 전부 camelCase JSON 필드명을 쓰므로, 요청/응답 바디가 있는 새 엔드포인트의 Pydantic 모델은 항상 이 베이스를 상속할 것(현재 `api/assets/schemas.py`가 유일한 사용처).
- **`op.add_column`으로 새 Postgres ENUM 컬럼을 추가할 때는 autogenerate 결과에 `CREATE TYPE`이 빠져있다**: `op.create_table`은 컬럼에 딸린 `sa.Enum`의 `CREATE TYPE`을 암묵적으로 먼저 실행하지만, 기존 테이블에 `op.add_column`으로 enum 컬럼을 추가하는 경우엔 그 이벤트가 발생하지 않아 `UndefinedObjectError: type "x" does not exist`로 실패한다(`e64d71eaa642_assets_status_column.py`에서 최초 발견). `upgrade()` 맨 앞에 `sa.Enum(...).create(op.get_bind(), checkfirst=True)`를 수동으로 추가해야 한다 — downgrade의 `sa.Enum(...).drop(...)` 패턴과 대칭.
- **테스트에서 S3를 흉내낼 땐 `moto`의 `mock_aws()` 데코레이터/컨텍스트매니저가 아니라 `moto.server.ThreadedMotoServer`(실제 로컬 HTTP 서버)를 쓴다**: `object_exists`/`generate_presigned_put_url`(`core/s3.py`)은 FastAPI의 `run_in_threadpool`(anyio 워커 스레드)에서 실행되는데, `api.main`(따라서 `core/s3.py`의 모듈 전역 `s3_client`)을 이미 import한 프로세스에서는 `mock_aws()`의 `botocore.client.BaseClient._make_api_call` 패치가 그 워커 스레드에는 실제로 적용되지 않는 경우가 실측으로 확인됐다(HeadObject가 조용히 진짜 AWS로 나가서 403을 받음 — 네트워크 접근이 되는 샌드박스라 hang이 아니라 빠르게 실패해서 알아챌 수 있었음. 근본 원인은 못 밝혔고, 재현되는 최소 사례도 못 만듦 — `api.main` import 여부만 갈랐다). `tests/conftest.py`가 세션 시작 시(즉 `api.main` import **이전**) `ThreadedMotoServer(port=0)`를 띄우고 `S3_ENDPOINT_URL` env var로 `settings.s3_endpoint_url`을 그 서버로 고정한다 — 실제 소켓 통신이라 스레드/컨텍스트 전파 이슈 자체가 없다. 새로 만드는 `boto3.client(...)`(테스트 셋업용)도 항상 `endpoint_url=settings.s3_endpoint_url`을 명시할 것.
- **테스트 API 클라이언트는 `TestClient`가 아니라 `httpx.AsyncClient(transport=ASGITransport(app=app))`를 쓴다**(`tests/conftest.py`의 `api_client`/`db_client`): `TestClient`는 호출마다 자체 백그라운드 스레드에 새 이벤트루프("portal")를 띄우는데, 이는 `pytest-asyncio`의 세션 스코프 루프와 **다른** 루프다. `redis_client`/DB `engine`처럼 커넥션 풀을 가진 모듈 전역 싱글턴은 최초 사용 시점의 루프에 묶이므로, 한 세션 안에서 이 두 종류의 루프를 섞어 쓰면(예: 일부 테스트는 `TestClient`로, 다른 테스트는 직접 `await`로 Redis/DB를 건드리면) "Future attached to a different loop" 에러가 테스트 실행 순서에 따라 산발적으로 난다(실제로 이 순서 의존성 때문에 처음엔 재현이 안 됐다). `ASGITransport`는 ASGI 앱을 호출자의 현재 루프에서 코루틴으로 직접 실행하므로 이 문제가 없다 — 새 테스트 클라이언트가 필요하면 이 패턴을 그대로 따를 것, `TestClient`를 다시 들여오지 말 것.
- **API 레벨 테스트에서 DB 시딩(예: 로그인용 유저 생성)과 실제 라우터 호출이 같은 트랜잭션을 공유하게 하려면** `get_db_session` FastAPI 의존성을 테스트의 `db_session` 픽스처로 오버라이드한다(`tests/conftest.py`의 `db_client` 픽스처). `AsyncSession`의 기본 `join_transaction_mode="conditional_savepoint"` 덕분에, 이미 외부 트랜잭션이 걸린 커넥션에 바인딩된 세션에서 애플리케이션 코드가 `commit()`을 호출해도 SAVEPOINT만 해제될 뿐 바깥 트랜잭션은 끝나지 않는다 — 실제로 커밋 후 별도 커넥션에서 조회해 데이터가 안 보이는 것까지 확인함(가정이 아니라 실측). `db_session`을 요구하는 새 API 테스트는 `db_client`(DB 오버라이드가 걸린 `api_client`)를 함께 쓸 것.
- **Dockerfile**은 uv 공식 멀티스테이지 패턴(`ghcr.io/astral-sh/uv:<version> ` 이미지에서 `/uv`/`/uvx` 바이너리만 COPY, `python:3.11-slim-bookworm` 베이스)을 따른다 — `uv:` 이미지 태그는 `pyproject.toml`의 `[build-system] requires = ["uv_build>=0.11.15,<0.12.0"]`와 맞춰 `0.11.15`로 고정했다(버전이 어긋나면 `uv_build` 백엔드 호환성 문제가 생길 수 있음). 빌더 스테이지에서 `uv sync --locked --no-install-project --no-dev`(의존성만, 캐시 레이어 분리) → `COPY . /app` → `uv sync --locked --no-dev`(프로젝트 자체 설치) 순으로 실행해 소스 변경이 의존성 레이어 캐시를 깨지 않게 한다. 런타임 스테이지는 non-root `appuser`로 `/app`(가상환경 포함) 전체를 복사하고 `PATH`에 `.venv/bin`을 추가해 `uvicorn api.main:app`을 직접 실행한다(entrypoint 스크립트 없음, `/health`가 DB/Redis 의존이 없어 마이그레이션 실행 단계도 필요 없음). `.dockerignore`가 `tests/`/`.venv/`/`.mypy_cache/` 등을 제외한다.
- **이메일 발송은 아직 실제 프로바이더가 없다(techspec-backend-auth.md §5가 명시적으로 open item으로 남겨둠)**: `api/core/email.py`의 `send_email(to, subject, body)`가 유일한 진입점이며 지금은 `print`로 대체한다(주의: `logging.info`를 쓰면 uvicorn이 root logger에 핸들러를 안 붙여서 조용히 사라진다 — 실제로 이 문제로 한 번 고침). 실제 프로바이더(SES/SMTP)가 정해지면 이 함수 본문만 바꾸면 되고, 호출부(`api/auth/emails.py`)는 그대로 둔다.
- **이메일 인증 코드/재전송 쿨다운은 새 DB 테이블이 아니라 Redis에 저장한다**(`api/auth/verification.py`, 키 `email_verification:{email}`, 값 `{code, sent_at}` JSON, TTL=`settings.email_verification_code_ttl_seconds`) — 세션과 동일하게 본질적으로 휘발성 데이터라 `techspec-db-schema.md`에도 별도 테이블이 없다. 쿨다운 판정(`seconds_until_resend_allowed`)은 Redis 없이 단위테스트 가능한 순수함수로 분리했다 — 시간 관련 로직을 추가할 때 이 패턴(순수함수로 뽑아서 `datetime`을 인자로 받게 하기)을 재사용할 것.
- **비밀번호 해시**: `api/core/security.py`의 `hash_password`/`verify_password`(`bcrypt` 패키지, `passlib` 아님 — 의존성 하나로 충분). `users.password_hash`/`admin_users.password_hash`를 다루는 모든 코드는 평문 비교 대신 이 두 함수를 거칠 것.
- **`pydantic.EmailStr`을 쓰려면 `email-validator` 패키지가 별도로 필요하다**(pydantic 자체엔 안 포함, import 시점에야 `ImportError`로 드러남) — `auth/schemas.py`가 최초 사용처.
- **실제 로그인을 완료시키는 엔드포인트(첫 사례: `POST /auth/guardian-consent`)는 `api/session/store.create_session({"user_id": str(user.id)})` 다음 `api/session/cookies.set_session_cookie(response, session_id)` 두 호출로 세션을 발급한다** — US-014의 `/dev/session-echo` 스켈레톤과 동일한 함수를 그대로 재사용한 것. 향후 로그인/OAuth 콜백(US-021, US-022)도 이 두 호출로 통일할 것. `users` 테이블엔 "가입 완료" 플래그가 따로 없다 — 성인은 `email_verified_at`만으로, 미성년자는 그에 더해 `guardian_consents`에 해당 `user_id` 행이 존재하는지로 판정해야 한다(로그인 API가 이 조합 검사를 구현해야 함).
