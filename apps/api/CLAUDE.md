# apps/api

- `uv`로 관리되는 독립 Python 프로젝트. pnpm workspace/turborepo 범위 밖이므로 루트 `pnpm run typecheck` 등에 걸리지 않는다 — 이 앱의 quality check(`uv run mypy src migrations scripts`, `uv run pytest` 등)는 항상 `apps/api` 안에서 별도로 실행해야 한다.
- `scripts/`는 `src/api` 패키지 밖의 1회성 CLI 스크립트 모음(현재 `export_openapi.py`뿐)이다 — `mypy` 대상 경로 목록(`src migrations scripts`, `.github/workflows/api.yml`과 로컬 명령 동일하게 유지)에 반드시 포함시킬 것. FE 타입 코드젠 파이프라인 전체 설명은 `packages/api-types/CLAUDE.md` 참고.
- src-layout: 패키지명은 `api`(`src/api/`), 모듈 경로는 `api.main`/`api.core.config`/`api.db.session` 식으로 임포트한다. `uv sync`가 이 패키지를 editable로 설치하므로 `uv run` 안에서는 항상 `import api...`가 그대로 동작한다.
- DB 연결 문자열은 `api.core.config.settings.database_url` (pydantic-settings, `.env`/`DATABASE_URL` env var)이 유일한 source of truth다. `alembic.ini`의 `sqlalchemy.url`은 플레이스홀더일 뿐이며 `migrations/env.py`가 기동 시점에 `config.set_main_option`으로 덮어쓴다 — 마이그레이션용 DB URL을 따로 관리하지 않는다.
- `migrations/env.py`의 `target_metadata`는 `api.db.base.Base.metadata`를 가리킨다. 새 모델은 반드시 이 `Base`를 상속해야 `alembic revision --autogenerate`가 인식한다.
- mypy는 `pyproject.toml`의 `[tool.mypy]`에서 `strict = true`로 설정되어 있다. 새 모듈 추가 시 타입 힌트 누락이 있으면 바로 실패한다.
- 모델은 `src/api/db/models/{domain}.py`(예: `auth.py`, `media.py`)로 techspec-overview-backend.md §6의 기능별 BE 문서 경계를 그대로 도메인 파일 경계로 삼는다. `src/api/db/models/__init__.py`가 모든 서브모듈을 import해 `Base.metadata`를 채우고, `migrations/env.py`도 `from api.db import models`로 그 패키지를 import해야 `alembic revision --autogenerate`가 새 테이블을 인식한다(모델만 추가하고 이 import를 빼먹으면 autogenerate가 빈 diff를 낸다).
- **순환 FK(예: users.profile_image_asset_id -> assets.id 와 assets.owner_user_id -> users.id)**: 모델 쪽은 `ForeignKey(..., use_alter=True, name=...)`로 선언하면 되지만, `alembic revision --autogenerate`가 생성하는 마이그레이션은 이 FK를 여전히 `op.create_table`의 인라인 `ForeignKeyConstraint`로 렌더링한다 — `use_alter`는 `MetaData.create_all()`에서만 자동으로 지켜지고 `op.create_table`은 존중하지 않는다. 그대로 두면 아직 존재하지 않는 테이블을 참조하는 인라인 FK라 즉시 실패(또는 조용히 무시)한다. **autogenerate 직후 항상 수동으로** 그 인라인 FK를 지우고 두 테이블이 모두 생긴 뒤 `op.create_foreign_key(...)` 호출로, downgrade에는 테이블 drop 전에 `op.drop_constraint(..., type_='foreignkey')`를 넣어야 한다.
- **Postgres ENUM 컬럼과 `op.drop_table`**: autogenerate가 만드는 `op.drop_table('assets')`는 테이블명만 담고 컬럼 정보가 없어서, `sa.Enum` 컬럼에 연결된 타입의 DROP TYPE 이벤트가 발생하지 않는다 — enum 타입이 DB에 남아 다음 upgrade에서 `DuplicateObjectError: type "X" already exists`로 실패한다. downgrade 마지막에 `sa.Enum(name='asset_kind').drop(op.get_bind(), checkfirst=True)`를 수동으로 추가해야 한다.
- `uv run alembic check`로 모델과 마이그레이션이 정확히 일치하는지(추가 diff 없음) 확인할 수 있다 — 마이그레이션을 손으로 고친 뒤 반드시 재실행해서 검증할 것.
- **자동생성 마이그레이션은 반드시 첫 `alembic upgrade head` 실행 전에 손으로 고칠 것** (순환 FK 등). 이미 그 리비전이 적용된 로컬 DB에 대해 나중에 `downgrade()`를 고치면, Alembic은 리비전 ID만 추적하고 실제로 실행됐던 SQL은 추적하지 않으므로 `UndefinedObjectError: constraint ... does not exist` 같은 불일치가 난다 — 이 경우 DB를 새로 만들고(`DROP DATABASE`/`CREATE DATABASE`) 처음부터 다시 적용해야 한다.
- **시드 데이터가 필요한 마이그레이션**(예: `genres` 10종)은 `upgrade()`에서 `op.execute("INSERT INTO ...")`로 넣되, PK는 마이그레이션 실행 시점에 `uuid.uuid4()`를 호출하지 말고 작성 시점에 하드코딩한 리터럴 UUID를 쓴다 — 그래야 dev/CI/prod 어느 환경에서 실행하든 같은 ID가 재현된다. 해당 테이블 자체를 `downgrade()`에서 `op.drop_table`하면 시드 로우도 함께 사라지므로 별도 DELETE는 불필요.
- **pytest 설정**: `pyproject.toml`의 `[tool.pytest.ini_options]`에 `asyncio_mode = "auto"` 외에 `asyncio_default_fixture_loop_scope`/`asyncio_default_test_loop_scope`를 `"session"`으로 명시해야 한다 — 기본값(함수 스코프)이면 테스트마다 새 이벤트 루프가 생기는데, 모듈 전역 `engine`(asyncpg 커넥션 풀)은 최초 생성 시점의 루프에 묶여 있어 두 번째 테스트부터 `InterfaceError: cannot perform operation: another operation is in progress`로 깨진다.
- **테스트 DB 인프라**: `tests/conftest.py`의 세션 스코프 `_migrated_schema` 픽스처가 세션 시작 전 `alembic upgrade head`, 종료 후 `downgrade base`를 실행해 마이그레이션 자체를 실행 가능한 테스트로 검증한다. 개별 테스트는 `db_session` 픽스처(커넥션 단위 트랜잭션을 열고 테스트 후 롤백)로 격리된다. 로컬에서 테스트를 돌리려면 `DATABASE_URL`이 실제 PostgreSQL(예: `docker run -d -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=ai_character_chat -p 5432:5432 postgres:16-alpine`)을 가리켜야 한다 — sqlite 등으로 대체하면 INET/ENUM 등 Postgres 전용 타입이 깨진다. `.github/workflows/api.yml`(US-016)은 `apps/api/**` 변경 시 `mypy`/`docker build`만 실행하며, `pytest`는 CI에 아직 붙어 있지 않다(Postgres/Redis 서비스 컨테이너가 필요한데 아직 없음) — 테스트를 CI에 태우는 작업은 이후 별도 스토리에서 다룬다.
- **순환 FK는 "같은 리비전 안에서 새 테이블 두 개가 서로 참조할 때만" 발생한다**: `content_versions`/`assets`처럼 이전 리비전에서 이미 만들어진 테이블을 새 테이블이 참조하기만 하면(예: US-009의 `character_version_details`/`situational_images`) autogenerate가 손댈 것 없이 깨끗하게 나온다. `use_alter`/`op.create_foreign_key` 수동 처리는 진짜로 두 신규 테이블이 서로를 가리킬 때만 필요하다.
- **`entity_id` 패턴 코드 형태**(techspec-db-schema.md §1 원칙 4, 최초 구현은 `character.py`의 `SituationalImage`): 물리적 PK `id`(`Uuid, primary_key=True, default=uuid.uuid4`)와 별개로 `entity_id`(`Uuid`, default 없음, 이 레이어에서는 유니크 제약도 없음 — 앱 레이어가 업서트/재발행 복제 흐름에서 값을 유지)를 분리한 컬럼으로 둔다. 앞으로 같은 패턴을 쓰는 테이블(starting_setups, stat_defs, keyword_notes, shortcuts, endings, ending_rule_groups, ending_rules)도 이 모양을 그대로 따른다.
- 순서가 중요한 목록(§1 원칙 2)은 `order`라는 이름 그대로 `Integer` 컬럼으로 선언해도 된다 — Postgres 예약어지만 SQLAlchemy가 렌더링하는 모든 DDL/DML에서 자동으로 따옴표 처리하므로 모델/마이그레이션 코드에서 별도 이스케이프가 필요 없다.
- **entity_id 패턴 자식이 다른 entity_id 패턴 부모를 참조하는 경우**(예: `stat_defs.starting_setup_id -> starting_setups.id`): 같은 리비전 안에서 부모 테이블이 먼저 `op.create_table`되기만 하면(자식이 부모를 참조하는 단방향 체인일 뿐 순환은 아님) autogenerate가 손댈 것 없이 그대로 통과한다 — 순환 FK 수동 처리는 두 신규 테이블이 "서로" 참조할 때만 필요하다는 규칙(위 항목)의 연장선. `ending_rules.stat_def_entity_id`처럼 FK가 아니라 `entity_id`를 참조하는(버전 넘어 안정적으로 참조, §1 원칙 4) 컬럼은 애초에 제약이 없으니 이 문제와 무관하다.
- **같은 ENUM 이름을 한 리비전 안에서 여러 테이블 컬럼에 재사용해도 안전하다**(예: `ending_rule_groups.next_op`/`ending_rules.next_op`가 동일한 `Enum(LogicalOp, name="logical_op")`): `op.create_table`을 여러 번 호출해도 Postgres `CREATE TYPE`은 한 번만 실행되고 두 번째 테이블 생성 시 "already exists" 에러가 나지 않는다 — 실제로 upgrade/downgrade/upgrade 반복 테스트로 확인함. 다만 downgrade에서는 그 이름을 사용하는 모든 테이블이 drop된 뒤 **단 한 번만** `sa.Enum(name=...).drop(...)`을 호출해야 한다(여러 번 호출은 `checkfirst=True`가 있으면 안전하지만 어차피 한 번으로 충분).
- **애플리케이션 레벨에서 "정확히 하나만 not null" 같은 상호배타 제약**(예: `ending_rules.ending_id`/`rule_group_id`)은 `CheckConstraint("(a IS NOT NULL) <> (b IS NOT NULL)", name=...)`를 모델의 `__table_args__`에 선언하면 DB 레벨에서 강제된다 — autogenerate가 `sa.CheckConstraint`로 그대로 인식하고 마이그레이션에 렌더링하므로 손으로 고칠 필요가 없다(순환 FK/ENUM downgrade와 달리 이 패턴은 autogenerate가 완벽히 처리하는 케이스).
- **복합(다중 컬럼) PK 테이블**(최초 구현은 `chat.py`의 `ChatRoomStat`/`StoryEndingUnlock`/`CharacterImageExposure`, 서로 다른 사용자+엔티티 조합이 계속 누적되는 로그/집계성 테이블): 대리 `id` 없이, PK를 구성하는 각 `mapped_column`에 그냥 `primary_key=True`를 개별로 붙이면 된다 — 별도 `PrimaryKeyConstraint`/`__table_args__` 선언이 필요 없고, autogenerate가 선언 순서대로 `sa.PrimaryKeyConstraint('col_a', 'col_b', ...)`를 첫 시도에 정확히 렌더링한다. 테스트에서 이 모양을 검증하려면 `sa.inspect(conn).get_pk_constraint(table)["constrained_columns"]`를 쓴다(FK/체크제약과는 다른 inspector 메서드). `favorites`/`likes`(§7, `PRIMARY KEY (user_id, content_id)`)도 이 모양을 그대로 따랐다(구현은 `content.py`, techspec-backend-content.md 도메인 경계와 맞춤 — `contents`/`content_versions`/`genres`와 같은 파일).
- **다형(polymorphic) 참조 컬럼**(최초 구현은 `moderation.py`의 `Appeal.target_id`, techspec-db-schema.md §8: `target_kind`에 따라 발행거부 이력 또는 `moderation_actions.id`를 가리킴): 대상 테이블이 `target_kind` 값마다 달라 DB `ForeignKey`를 걸 수 없다. 그냥 `Uuid` 컬럼(FK 없음)으로 선언하고, docstring에 왜 FK가 없는지 이유를 남긴다. 참조 무결성은 애플리케이션 레벨(신고/조치 처리 API)에서 보장해야 한다 — DB는 강제하지 않는다.
  - **`POST /appeals`(US-087, `api/moderation/router.py`)는 실제로는 이 무결성을 검증하지 않는다** — "발행거부 이력"이라는 별도 엔티티가 애초에 존재하지 않아(`target_kind='publish-rejection'`이면 그냥 contentId), `target_kind`별로 다른 테이블 존재를 확인하는 분기를 추가하지 않고 클라이언트가 보낸 `target_id`를 그대로 저장한다(`report_content`가 신고 사유 진위를 검증하지 않는 것과 같은 신뢰 수준). "애플리케이션 레벨에서 보장" 항목은 향후 관리자 조치 처리 API(`POST /admin/reports/{id}/action` 등)가 실제 대상에 조치를 반영하는 시점을 가리키는 것이지, 접수 시점의 존재 검증을 요구하는 게 아니다.
- **FastAPI `TestClient`를 쓰는 테스트에서 모듈 전역(import 시점) 커넥션 풀을 가진 async 클라이언트(예: `core/redis.py`의 `redis_client`)를 쓰면, `db_session`/`_migrated_schema` 픽스처와 별개의 새로운 event-loop 이슈가 난다**: `TestClient(app)`는 `with` 블록에 진입할 때마다 자체 백그라운드 스레드에 새 event loop(anyio blocking portal)를 띄우고 블록을 벗어나면 그 loop를 닫는다. pytest-asyncio의 `asyncio_default_fixture_loop_scope="session"`은 이 portal의 loop에는 적용되지 않으므로, 서로 다른 테스트 함수마다 매번 새 `with TestClient(app) as client:`를 열면 이전 블록에서 만들어진 pooled connection(=이제는 닫힌 loop에 묶여 있음)을 재사용하려다 `RuntimeError: Event loop is closed`로 깨진다. 해결: `tests/conftest.py`의 세션 스코프 `api_client` 픽스처처럼 **테스트 세션 전체에서 `TestClient`를 한 번만 열어(`with`) 공유**한다(`db_engine`이 세션 스코프 loop를 공유하는 것과 같은 이유). 테스트 간 쿠키 오염을 막으려면 각 테스트 시작 시 `api_client.cookies.clear()`를 호출할 것. 같은 세션 안에서 서로 다른 "세션"을 동시에 흉내내야 한다면 두 번째 `TestClient` 인스턴스를 열지 말고, 응답의 `Set-Cookie` 값을 직접 캡처해 `api_client.cookies.set(name, value)`로 스위칭하며 순차 호출한다(per-request `cookies=` kwarg는 starlette에서 deprecated).
- **인증이 필요한 라우터의 "현재 사용자" 의존성**: `src/api/session/dependencies.py`의 `get_current_user_id`(FastAPI `Depends`)가 세션 쿠키 → Redis 세션 데이터의 `user_id` 키를 읽어 반환한다. 실제 `/auth/login`(US-021)이 아직 없어도, 세션에 `{"user_id": "..."}`를 넣기만 하면(예: 기존 `/dev/session-echo` 또는 향후 로그인 라우트) 이 의존성을 만족한다 — 로그인이 필요한 새 라우터는 이 파일을 그대로 재사용할 것.
- **camelCase JSON API 응답/요청 스키마**: `src/api/core/schema.py`의 `CamelModel`(pydantic `BaseModel` + `alias_generator=to_camel, populate_by_name=True`)을 상속하면 Python 필드는 snake_case, JSON은 camelCase로 나간다 — techspec 문서들이 전부 camelCase JSON 필드명을 쓰므로, 요청/응답 바디가 있는 새 엔드포인트의 Pydantic 모델은 항상 이 베이스를 상속할 것(현재 `api/assets/schemas.py`가 유일한 사용처).
- **`op.add_column`으로 새 Postgres ENUM 컬럼을 추가할 때는 autogenerate 결과에 `CREATE TYPE`이 빠져있다**: `op.create_table`은 컬럼에 딸린 `sa.Enum`의 `CREATE TYPE`을 암묵적으로 먼저 실행하지만, 기존 테이블에 `op.add_column`으로 enum 컬럼을 추가하는 경우엔 그 이벤트가 발생하지 않아 `UndefinedObjectError: type "x" does not exist`로 실패한다(`e64d71eaa642_assets_status_column.py`에서 최초 발견). `upgrade()` 맨 앞에 `sa.Enum(...).create(op.get_bind(), checkfirst=True)`를 수동으로 추가해야 한다 — downgrade의 `sa.Enum(...).drop(...)` 패턴과 대칭.
- **테스트에서 S3를 흉내낼 땐 `moto`의 `mock_aws()` 데코레이터/컨텍스트매니저가 아니라 `moto.server.ThreadedMotoServer`(실제 로컬 HTTP 서버)를 쓴다**: `object_exists`/`generate_presigned_put_url`(`core/s3.py`)은 FastAPI의 `run_in_threadpool`(anyio 워커 스레드)에서 실행되는데, `api.main`(따라서 `core/s3.py`의 모듈 전역 `s3_client`)을 이미 import한 프로세스에서는 `mock_aws()`의 `botocore.client.BaseClient._make_api_call` 패치가 그 워커 스레드에는 실제로 적용되지 않는 경우가 실측으로 확인됐다(HeadObject가 조용히 진짜 AWS로 나가서 403을 받음 — 네트워크 접근이 되는 샌드박스라 hang이 아니라 빠르게 실패해서 알아챌 수 있었음. 근본 원인은 못 밝혔고, 재현되는 최소 사례도 못 만듦 — `api.main` import 여부만 갈랐다). `tests/conftest.py`가 세션 시작 시(즉 `api.main` import **이전**) `ThreadedMotoServer(port=0)`를 띄우고 `S3_ENDPOINT_URL` env var로 `settings.s3_endpoint_url`을 그 서버로 고정한다 — 실제 소켓 통신이라 스레드/컨텍스트 전파 이슈 자체가 없다. 새로 만드는 `boto3.client(...)`(테스트 셋업용)도 항상 `endpoint_url=settings.s3_endpoint_url`을 명시할 것.
- **테스트 API 클라이언트는 `TestClient`가 아니라 `httpx.AsyncClient(transport=ASGITransport(app=app))`를 쓴다**(`tests/conftest.py`의 `api_client`/`db_client`): `TestClient`는 호출마다 자체 백그라운드 스레드에 새 이벤트루프("portal")를 띄우는데, 이는 `pytest-asyncio`의 세션 스코프 루프와 **다른** 루프다. `redis_client`/DB `engine`처럼 커넥션 풀을 가진 모듈 전역 싱글턴은 최초 사용 시점의 루프에 묶이므로, 한 세션 안에서 이 두 종류의 루프를 섞어 쓰면(예: 일부 테스트는 `TestClient`로, 다른 테스트는 직접 `await`로 Redis/DB를 건드리면) "Future attached to a different loop" 에러가 테스트 실행 순서에 따라 산발적으로 난다(실제로 이 순서 의존성 때문에 처음엔 재현이 안 됐다). `ASGITransport`는 ASGI 앱을 호출자의 현재 루프에서 코루틴으로 직접 실행하므로 이 문제가 없다 — 새 테스트 클라이언트가 필요하면 이 패턴을 그대로 따를 것, `TestClient`를 다시 들여오지 말 것.
- **API 레벨 테스트에서 DB 시딩(예: 로그인용 유저 생성)과 실제 라우터 호출이 같은 트랜잭션을 공유하게 하려면** `get_db_session` FastAPI 의존성을 테스트의 `db_session` 픽스처로 오버라이드한다(`tests/conftest.py`의 `db_client` 픽스처). `AsyncSession`의 기본 `join_transaction_mode="conditional_savepoint"` 덕분에, 이미 외부 트랜잭션이 걸린 커넥션에 바인딩된 세션에서 애플리케이션 코드가 `commit()`을 호출해도 SAVEPOINT만 해제될 뿐 바깥 트랜잭션은 끝나지 않는다 — 실제로 커밋 후 별도 커넥션에서 조회해 데이터가 안 보이는 것까지 확인함(가정이 아니라 실측). `db_session`을 요구하는 새 API 테스트는 `db_client`(DB 오버라이드가 걸린 `api_client`)를 함께 쓸 것.

- **실제 로그인을 완료시키는 엔드포인트(첫 사례: `POST /auth/guardian-consent`, 이제 `POST /auth/login`도 동일)는 `api/session/store.create_session({"user_id": str(user.id)})` 다음 `api/session/cookies.set_session_cookie(response, session_id)` 두 호출로 세션을 발급한다** — US-014의 `/dev/session-echo` 스켈레톤과 동일한 함수를 그대로 재사용한 것. 향후 OAuth 콜백(US-022)도 이 두 호출로 통일할 것. `users` 테이블엔 "가입 완료" 플래그가 따로 없다 — 성인은 `email_verified_at`만으로, 미성년자는 그에 더해 `guardian_consents`에 해당 `user_id` 행이 존재하는지로 판정한다(`POST /auth/login`이 `is_guardian_consent_required` + `guardian_consents` 조회 조합 검사를 구현한 첫 사례, `api/auth/router.py`의 `login` 참고).

- **외부 HTTP API(Google OAuth 토큰교환/유저인포 등)를 호출하는 코드는 그 호출 자체를 FastAPI `Depends`로 감싼다**(`api/auth/google_oauth.py`의 `get_google_profile`) — `get_db_session`과 동일한 이유로, 테스트에서 `app.dependency_overrides[get_google_profile] = lambda: {...}`로 실제 네트워크 호출 없이 오버라이드할 수 있다(`tests/test_auth_google_api.py`). 평범한 함수 호출로 바디 안에서 부르면 이 오버라이드 메커니즘을 못 쓴다.
- **`Depends` 여러 개를 한 경로 함수에 선언하면 시그니처에 적힌 순서대로 순차 resolve된다**(먼저 선언된 것이 raise하면 뒤에 선언된 의존성은 아예 호출되지 않음) — `google_callback`에서 `state` 검증(`_get_oauth_redirect_target`)을 `profile`(Google 네트워크 호출) 의존성보다 앞에 선언해, 위조/만료된 `state`는 Google에 실제 요청을 보내기 전에 400으로 즉시 막는다. 검증 로직을 경로 함수 바디 첫 줄에 두는 것과 겉보기엔 같아 보이지만, 다른 파라미터가 `Depends`로 선언돼 있으면 바디는 모든 `Depends`가 이미 resolve된 뒤에야 실행되므로 순서가 틀리기 쉽다 — 순서가 중요한 검증은 반드시 앞선 `Depends`로 뽑아낼 것.
- **토큰이 API 응답이 아니라 순수 이메일(아웃오브밴드 채널)로만 전달되는 흐름은 email-keyed Redis 조회로 테스트할 수 없다**(비밀번호 재설정, `api/auth/password_reset.py`): 이메일 인증 코드는 `email_verification:{email}` 식으로 email이 키라 테스트가 `get_verification_code(email)`로 바로 값을 읽을 수 있었고, Google OAuth 토큰은 redirect의 Location 헤더에 실려 응답 자체에서 추출 가능했다. 반면 비밀번호 재설정 토큰은 `password_reset:{token}`처럼 무작위 토큰 자체가 키라(생성 전에는 알 수 없음) 이 두 수단 다 못 쓴다. 해결: `send_password_reset_email`을 `auth/router.py`에 이름으로 import해두고, 테스트에서 `monkeypatch.setattr("api.auth.router.send_password_reset_email", capture_fn)`로 실제 전달된 `reset_link`(따라서 token)를 가로챈다 — 이 코드베이스 최초의 monkeypatch 사용처. 토큰이 키 그 자체이고 사전에 알 수 없는 아웃오브밴드 전달 흐름을 새로 추가할 때는 이 패턴을 재사용할 것.
- **회원탈퇴(`DELETE /me`, US-024)는 소프트 삭제**(`users.deleted_at` 세팅)**일 뿐 user row는 그대로 남는다** — 그래서 `guardian_consents`/`favorites`/`likes`/`story_ending_unlocks`/`character_image_exposures`처럼 `users.id`를 참조하는 다른 테이블은 FK가 깨질 일이 없어 손댈 필요가 없다. 명세상 명시적으로 처리해야 하는 건 딱 두 가지뿐: (1) 본인이 `creator_user_id`인 `contents`를 전부 `visibility='private'`로 일괄 UPDATE, (2) 본인이 `user_id`인 `chat_rooms`(+거기 딸린 `chat_messages`/`chat_room_stats`)를 실제로 DELETE. `content_versions`(초안 포함)는 절대 건드리지 않는다 — "보존되지만 접근 불가"는 계정 자체가 로그인 불가능해지는 것만으로 충족된다.
- **`chat_rooms`/`chat_messages`/`chat_room_stats`에는 `ON DELETE CASCADE`가 없다** (`migrations/versions/b8e8af497520_..._chat.py` 참고, 전부 plain `ForeignKeyConstraint`) — `chat_rooms` 행을 지우려면 그걸 참조하는 `chat_messages`/`chat_room_stats`를 **먼저** 지워야 FK 위반이 안 난다. 앞으로 채팅방을 삭제하는 모든 흐름(관리자 강제 삭제, 신고 처리 등)은 `api/auth/router.py`의 `withdraw`가 하는 순서(`chat_room_stats` → `chat_messages` → `chat_rooms`)를 그대로 따를 것.
- **소프트 삭제된(`deleted_at IS NOT NULL`) 계정은 로그인 자체를 막아야 한다** — `GET /me`는 US-021부터 이미 `deleted_at` 체크가 있었지만, `POST /auth/login`(비밀번호 로그인)은 US-024에서야 `deleted_at is not None`을 "Invalid email or password"(401)와 같은 조건절에 추가해 자격증명 실패와 구분 안 되게 했다(탈퇴 여부를 오라클로 노출하지 않기 위함). **`GET /auth/google/callback`(구글 로그인)은 아직 이 체크가 없다** — 탈퇴한 계정이 구글 로그인으로는 재로그인 가능한 상태로 남아있는 기존 갭이니, 구글 로그인 관련 스토리를 다시 만질 때 같이 고칠 것.
- **`/me/*` 라우트가 전부 auth 도메인은 아니다** — `GET /me`, `PATCH /me/password`, `DELETE /me`(US-021/024)는 `techspec-backend-auth.md` 경계라 `api/auth/router.py`의 prefix 없는 `me_router`에 있지만, `GET /me/drafts`(US-025)는 `techspec-backend-content.md` §1.1 경계다. 새 `api/content/router.py`(prefix 없는 `APIRouter(tags=["content"])`, `main.py`에 별도 `include_router`)를 만들어 여기 추가했다 — 앞으로 이 경계에 속하는 `PATCH /me/profile`(US-026), `GET /me/favorites`(US-039)도 auth의 `me_router`가 아니라 이 `api/content/router.py`에 추가할 것. 라우터를 어느 파일에 둘지는 URL prefix가 아니라 techspec-overview-backend.md §6의 BE 문서 경계를 기준으로 결정한다(모델 파일 배치와 동일한 원칙, US-013 학습 참고).
- **Postgres ENUM 컬럼은 SQLAlchemy가 기본적으로 Python enum의 `.name`(대문자)을 저장하지, `.value`(소문자, JSON에 나가는 값)를 저장하지 않는다** — 예: `ContentType.CHARACTER`(`value="character"`)는 실제 DB에 `'CHARACTER'`로 들어간다(`\dT+ content_type`으로 확인 가능). ORM/테스트 코드는 항상 Python enum 멤버를 다루므로 이 사실이 드러나지 않지만, `psql`로 직접 raw INSERT를 만들어 수동 스모크테스트할 때 소문자 값(`'character'`)을 쓰면 `invalid input value for enum` 에러가 난다 — raw SQL에서는 반드시 대문자 멤버 이름을 쓸 것.
- **`assetId`를 자산 도메인 밖(예: `PATCH /me/profile`의 `profileImageAssetId`, US-026)에서 참조로 받는 첫 사례**: 그냥 FK로 저장하지 않고, 반드시 `Asset`을 조회해 `owner_user_id`가 요청자 본인인지 + `status == AssetStatus.READY`인지 둘 다 확인한 뒤에만 반영한다(둘 중 하나라도 아니면 400) — 타인의 자산이나 아직 업로드 완료되지 않은(`pending`) 자산을 참조로 심는 것을 막기 위함. techspec에는 이 검증이 명시돼 있지 않지만 정합성상 필요해서 추가했다(US-020/022의 "AC에 없는 필드 추가"와 같은 종류의 판단). 앞으로 빌더 스토리에서 `thumbnailAssetId`/situational image 등 다른 도메인이 `assetId`를 받을 때도 이 소유권+ready 체크를 재사용할 것.
- **로그인 여부에 따라 동작이 달라지지만 비로그인 호출도 허용해야 하는 엔드포인트**(첫 사례: `GET /users/{id}/contents`, US-027 — 본인 조회면 비공개 필터를 추가로 허용, 타인/비로그인이면 public만)는 기존 `get_current_user_id`(세션 없으면 401 raise)를 못 쓴다. `session/dependencies.py`에 공통 로직을 `_session_user_id(request) -> uuid.UUID | None`으로 뽑고, `get_current_user_id`는 그 결과가 `None`이면 401을 raise, 새로 추가한 `get_current_user_id_optional`은 raise 없이 그대로 반환한다 — 라우트는 `viewer_user_id: uuid.UUID | None = Depends(get_current_user_id_optional)` 후 `is_owner = viewer_user_id == id` 식으로 분기할 것. 앞으로 "타인 조회 가능 + 본인이면 추가 정보/필터"류 엔드포인트는 이 의존성을 재사용한다.
- **"발행된 콘텐츠"를 판정할 때는 `content_versions.published_at`을 직접 뒤지지 말고 `contents.current_published_version_id IS NOT NULL`을 쓴다**(첫 사례: `GET /users/{id}/contents`, US-027) — 이 컬럼은 발행 시점에만 갱신되는 "최신 발행 버전" 포인터라 그 자체가 "발행된 적 있음"의 단일 진실 공급원이다. 이름/썸네일 등 표시용 필드도 반드시 이 버전의 `character_version_details`/`story_version_details`에서 읽어야 한다(초안이 아니라 발행본 기준) — 아직 발행 API(`POST /contents/{id}/publish`)가 없어 테스트/수동 스모크는 이 컬럼과 하위 detail 로우를 직접 INSERT/UPDATE해서 만든다(`GET /me/drafts`의 US-025 노트가 같은 이유로 raw insert를 썼던 것과 동일한 제약).
- **자산 → 렌더링 가능한 URL 변환(US-034가 남긴 갭)은 `content/router.py`의 `_resolve_asset_url(db, asset_id)`(내부적으로 `core/s3.py`의 `generate_presigned_get_url(key)` 호출)로 해결한다**(US-035에서 `profileImageUrl`로 처음 쓰였고, US-036에서 `ContentSummary.thumbnailUrl`에 재사용하며 이름을 `_resolve_profile_image_url` → `_resolve_asset_url`로 일반화했다) — 별도 `GET /assets/{id}` 엔드포인트나 공개 read 버킷 전환 대신, 매 조회마다 저장된 `storage_key`로 presigned GET URL을 즉석에서 서명한다(`generate_presigned_put_url`과 대칭, 네트워크 호출 없는 로컬 서명이라 `run_in_threadpool`이 필요하지만 부담은 미미). `DraftSummary.thumbnailAssetId`는 아직 이 헬퍼를 안 쓴다 — 마이페이지 초안 카드가 실제 썸네일을 그려야 할 때 같은 패턴을 적용하면 된다. **(US-116) `DraftSummary.thumbnailUrl` 추가 완료** — `list_my_drafts`(`content/router.py`)가 이제 이 헬퍼로 채운다.
- **S3 버킷에 CORS 설정이 어디에도 없다** — presigned PUT 업로드(US-018)는 브라우저가 발급받은 URL로 직접 PUT하는 구조라 실제 배포 환경에서는 버킷에 CORS 정책(허용 오리진/메서드)이 없으면 브라우저가 preflight에서 요청을 막는다. techspec-infra.md/techspec-backend-media.md 어디에도 이 설정이 명시돼 있지 않은 실제 인프라 갭이다 — 로컬에서 `apps/web`의 업로드 플로우를 브라우저로 검증하려면 `moto.server.ThreadedMotoServer`를 띄우고 `put_bucket_cors`로 `AllowedOrigins:["*"], AllowedMethods:["GET","PUT","POST","HEAD"]`를 수동으로 걸어야 한다(pytest의 `ThreadedMotoServer` picture는 브라우저를 거치지 않아 이 문제 자체가 없다). 실제 S3 버킷 프로비저닝을 다루는 인프라 스토리에서 반드시 CORS 정책을 함께 구성할 것.
- **첫 커서(keyset) 페이지네이션 구현**(`GET /contents`, US-037, `content/router.py`): offset이 아니라 정렬 키의 마지막 값을 커서로 들고 다닌다 — `_encode_cursor`/`_decode_cursor`가 정렬 키 튜플을 JSON→base64url로 인코딩하고, WHERE 절은 `sqlalchemy.tuple_(컬럼들) < (마지막값들의 평범한 Python 튜플)`로 다음 페이지를 자른다(행 단위 사전식 비교, Postgres가 네이티브로 지원). `has_more` 판정은 `LIMIT PAGE_SIZE + 1`로 한 행 더 가져와서 페이지 크기 초과 여부만 보고, 실제 응답에는 그 한 행을 다시 잘라낸다. 정렬 방향이 섞이는 경우(`sort=genre`: 장르 `sort_order` ASC + 생성일 DESC)는 단일 `tuple_(...)` 비교로 표현 불가능해 `or_(1순위컬럼 > 마지막값, and_(1순위컬럼 == 마지막값, tuple_(나머지) < (나머지 마지막값)))` 형태로 수동 전개해야 한다.
  - **mypy 함정**: `tuple_(a, b) < (x, y)`처럼 오른쪽은 평범한 Python 튜플이어야 한다 — `tuple_(a, b) < tuple_(x, y)`로 양쪽 다 `tuple_()`로 감싸면 mypy가 `tuple_`의 인자 타입(컬럼 표현식 기대)이 안 맞는다고 에러 낸다(오른쪽은 SQLAlchemy가 바인드 파라미터로 자동 강제 변환해주므로 굳이 감쌀 필요가 없다).
  - **`ARRAY` 컬럼 "포함 여부"(`hashtags`) 비교는 연산자 순서가 mypy 결과를 가른다**: `any_(Content.hashtags) == value`는 SQLAlchemy의 오버로드된 `__eq__`를 타서 정상적으로 타입체크되지만, `value == any_(Content.hashtags)`(`str.__eq__`가 먼저 호출됨)는 런타임에는 동일하게 동작해도 mypy가 정적으로 `bool`로 추론해버려 `.where()`에 못 넘긴다 — 항상 SQLAlchemy 표현식을 좌변에 둘 것.
  - 캐릭터/스토리처럼 타입에 따라 다른 모델을 쓰는 쿼리는 `type[CharacterVersionDetail] | type[StoryVersionDetail]`을 반환하는 헬퍼로 한 번만 분기하고 나머지 쿼리는 공유해도 된다(US-027의 `if type == ContentType.CHARACTER: ... else: ...` 전체 중복 패턴과 달리, 이번엔 mypy strict가 union 타입의 클래스 속성 접근(`detail_model.name`, `.ilike()` 등)을 그대로 통과시켰다) — 두 방식 다 유효하니, 분기 이후 로직이 짧으면 헬퍼+공유 쿼리를, 완전히 다른 처리(별도 dict 조립 등)가 필요하면 US-027처럼 명시적 분기를 쓰면 된다.
- **`GET /contents/{id}`(US-038, 상세화면)의 접근 제어는 403/404 게이트가 아니라 "쿼리 응답에 담아 FE가 렌더링 여부를 결정"하는 방식이다**(techspec-content-detail.md §2가 명시). 존재하고 발행된 콘텐츠라면 비공개/이용제한/삭제 여부와 무관하게 항상 200과 전체 메타를 반환하고, `_resolve_access_status(visibility, moderation_status)`(`content/router.py`)로 계산한 `accessStatus: {kind, visibility?}`와 `isOwner`를 함께 실어 보낸다 — FE의 `canViewDetailPage`가 이 두 값만 보고 정상 렌더링/접근불가 안내를 분기한다(BE가 로직을 중복 구현하지 않음). 404는 오직 "id 자체가 없거나 발행된 버전이 없을 때"에만 쓴다. 좋아요/즐겨찾기/신고(US-039/040)처럼 이 콘텐츠를 대상으로 하는 다른 액션 엔드포인트도 접근 불가 콘텐츠에 어떤 정책을 적용할지 정할 때 이 비대칭(조회는 항상 열림, 액션은 별도 판단 필요)을 참고할 것.
- **발행된 `content_versions` 로우는 `version_number`/`published_at`이 모델 타입상 `int | None`/`datetime | None`이지만 실질적으로는 not-null이 보장된 애플리케이션 불변식이다**(발행 시점에 반드시 채워짐, techspec-backend-content.md §2) — `Content.current_published_version_id`가 가리키는 버전이나 `published_at IS NOT NULL`로 필터링한 버전을 다룰 때는 `assert version.version_number is not None`처럼 단언해서 mypy strict를 통과시킨다(별도 예외 처리가 아니라 불변식 문서화 목적의 assert).
- **US-038의 "액션 엔드포인트는 접근 제어 정책을 별도로 정해야 한다" 메모(위 항목)는 US-039(좋아요/즐겨찾기)에서 이렇게 풀었다**: `POST/DELETE /contents/{id}/like`·`/favorite`는 콘텐츠가 아예 없을 때만 404이고, 비공개/이용제한 여부는 따로 막지 않는다(AC가 멱등성만 요구했고, `GET /contents/{id}`의 "조회는 항상 열림" 원칙과 같은 결로 판단). 반대로 `GET /me/favorites`는 `moderation_status == deleted`인 콘텐츠만 목록에서 제외한다 — US-027의 본인 프로필 "all" 필터와 동일한 판단(삭제는 완전 비존재와 동급 취급, restricted는 여전히 노출). 신고(US-040) 등 다음 액션형 엔드포인트도 이 두 판단(액션 자체는 존재 여부만 체크, 목록 조회는 deleted만 제외)을 기본값으로 재사용하되, AC가 다른 걸 요구하면 그쪽을 따를 것.
- **멱등 토글(좋아요/즐겨찾기)은 `select(...).where(...)`로 존재 확인 후 insert/delete하는 단순한 check-then-act로 충분하다** — `ON CONFLICT`/unique-violation catch 같은 동시성 안전장치는 AC에 없으면 추가하지 않는다(이 라우터의 다른 코드들과 동일한 단순성 수준 유지). 두 토글 다 응답은 `204 No Content`: `techspec-content-detail.md` §4가 이 두 상호작용을 FE 낙관적 업데이트로 명시해 응답 바디를 읽지 않기 때문(반대로 `PATCH /notifications/{id}/read`는 호출부가 낙관적이지 않아 갱신된 리소스를 그대로 반환한다).
- **`db_client`(또는 `db_session`)를 쓰는 테스트에서 같은 테스트 안에 여러 번 살아있는 API 호출(라이브 POST 등)로 `created_at` server-default(`func.now()`) 순서를 검증하려 하면 안 된다** — 테스트 전체가 하나의 바깥 Postgres 트랜잭션 안에서 실행되고(`tests/conftest.py`의 `db_session` 픽스처), SQL `now()`는 "트랜잭션 시작 시각"으로 고정되어 그 트랜잭션 안의 모든 statement에서 완전히 동일한 값을 반환한다 — "거의 같은 시각"이 아니라 "정확히 같은 시각"이라 정렬이 다음 tiebreak 컬럼(예: PK) 기준으로 결정되어 기대와 달라진다(US-039에서 실측: 좋아요 순서 테스트가 `content_id` 역순으로 나와 실패). 순서를 검증해야 하면 라이브 호출 대신 모델 로우를 직접 `db_session.add`하며 `created_at`을 명시적으로 다르게(예: `now - timedelta(minutes=i)`) 지정할 것 — `test_content_list_api.py`의 커서 페이지네이션 테스트가 이미 쓰던 패턴과 동일하다.
- **모델 파일의 도메인 경계와 라우터 파일의 도메인 경계가 항상 같지는 않다** (첫 어긋난 사례: `POST /contents/{id}/report`, US-040) — `Report`는 `db/models/moderation.py`(techspec-backend-admin-moderation.md 도메인, US-013)에 있지만, 이 엔드포인트 자체는 `techspec-backend-content.md` §1.1의 표에 나열돼 있어 `api/content/router.py`(like/favorite와 같은 파일)에 구현했다. 새 엔드포인트를 어느 라우터 파일에 둘지는 그 모델이 정의된 파일이 아니라, **그 엔드포인트가 실제로 나열된 techspec-backend-*.md 문서**를 기준으로 판단할 것 — 관리자용 `GET/POST /admin/reports*`(같은 `Report` 모델을 다루지만 techspec-backend-admin-moderation.md에 나열됨, 아직 미구현)는 반대로 `api/moderation/router.py`에 들어가야 한다.

- **SSE 스트리밍 엔드포인트(`POST /chat-rooms/{id}/messages`, US-053)는 설치된 FastAPI(0.139)의 네이티브 SSE 지원을 쓴다** — 라우트 함수 자체를 `async def ...() -> AsyncIterator[SomeUnion]:`(`yield`가 있는 async generator)로 정의하고 `@router.post(..., response_class=EventSourceResponse)`(`fastapi.sse`에서 import)를 붙이면, FastAPI가 각 `yield`된 값을 `data: <json>\n\n` SSE 프레임으로 자동 직렬화한다(`StreamingResponse`를 직접 만들 필요 없음). `AsyncIterator[Annotated[UnionOfCamelModels, Field(discriminator="type")]]`처럼 반환 타입을 판별 유니언으로 선언하면 각 이벤트가 올바른 서브타입으로 검증·직렬화된다(camelCase는 `CamelModel` 그대로 적용됨).

Gemini 호출 실패처럼 "스트림은 이미 정상적으로 시작됐고 이제 중간에 실패를 알려야 하는" 경우는 반대로 제너레이터 본문에서 `try/except`로 잡아 `error`/`policyWarning` 이벤트를 `yield`하고 `return`하는 게 맞다(그래야 커넥션이 정상 종료되지, 예외가 새 나가면 안 된다).

- **`POST /chat-rooms/{id}/messages`가 캐릭터/스토리 공용 파이프라인이 된 것(US-059)**: 라우트 맨 앞에서 `setup = await _resolve_starting_setup(db, room)`(US-057이 만든 헬퍼)로 한 번만 분기해, `setup is None`이면 캐릭터 경로(`build_generation_prompt`), 아니면 스토리 경로(`build_story_generation_prompt` — `story_version_details.prompt_template`이 `custom`이면 `custom_prompt`만, 아니면 `setting_text`(+선택적 `development_example`)와 시작설정 `prologue`를 조립)를 탄다. 스토리 경로는 생성(`llm_client.generate`) 스트리밍이 끝난 뒤 **같은 턴 안에서** `build_stat_judgment_prompt()` + `llm_client.generate_structured(prompt, StatJudgmentResult)`(이 코드베이스에서 `generate_structured`가 실제로 호출되는 첫 사례, US-050이 만들어만 두고 US-051~058 내내 미사용이었다)를 추가로 호출해 스탯 변경을 판단한다. `StatJudgmentResult`/`StatChangeJudgment`(`api/chat/prompt_builder.py`)는 LLM 구조화 출력 전용 pydantic 모델이고, `api/chat/stats.py`의 `StatChange`(frozen dataclass)는 순수함수 `apply_stat_changes`의 입력 타입이라 서로 다른 타입이다 — 라우터가 `StatChange(stat_id=c.stat_id, new_value=c.new_value)`로 매 턴 변환하는 어댑터 역할을 한다(US-058 노트가 미리 예견해둔 지점).
  - **판단 실패에 대한 방어적 try/except를 의도적으로 넣지 않았다**: `llm_client.generate()`(생성) 실패만 `LLMPolicyViolationError`/`LLMClientError`로 감싸 SSE `policyWarning`/`error` 이벤트로 변환한다(US-053부터 있던 기존 동작). 그 뒤에 오는 판단 호출/스탯 갱신/`db.commit()`은 감싸지 않는다 — 이미 어시스턴트 메시지가 스트리밍된 뒤(SSE 제너레이터가 이미 응답을 흘려보낸 뒤)라 실패해도 "정상 JSON 에러 응답"으로 되돌릴 방법이 없는 건 기존 `db.flush()`/`db.commit()` 실패도 마찬가지고, 이 스토리의 AC도 판단 실패 시나리오를 요구하지 않았다 — 새로운 비대칭을 만들지 않고 기존 위험 수준에 맞췄다.
  - **`chat_room_stats.current_value`(Numeric/Decimal 컬럼)에 판단 결과(float)를 대입할 때는 `Decimal(str(new_value))`를 쓴다** — `row.current_value = 70.0`처럼 float를 직접 대입하면 mypy strict가 `Mapped[Decimal]` 디스크립터 타입 불일치로 막는다(반대로 ORM 생성자 kwarg로 `current_value=stat_def.initial_value`(int)를 넘기는 건 `__init__(self, **kw: Any)`라 mypy가 체크하지 않아 통과한다 — 생성자 vs 속성 대입의 타입체크 엄격도가 다르다는 걸 이번에 실측). `test_chat_room_api.py`의 `room_stat.current_value = Decimal(5)`가 이미 쓰던 패턴과 동일.
  - **변경된 스탯만 이벤트/DB 갱신 대상**: `apply_stat_changes()`가 반환한 `updated_stats`를 갱신 전 `current_stats`와 값 비교해서 실제로 바뀐 stat_id만 `ChatStatChangeEvent`를 yield하고 해당 `ChatRoomStat` 행을 갱신한다 — LLM이 변화 없는 스탯까지 `statChanges`에 포함해 응답해도(판단 프롬프트에서 "변화 없으면 포함하지 않아도 됨"이라고 안내하지만 강제는 아님) 클램프 후 같은 값이면 조용히 무시된다.
- **엔딩 규칙 평가 엔진(`api/chat/ending_rules.py`, US-061)**: `evaluate_item`/`evaluate_rule_list`는 techspec-builder-story.md §1.5의 TS 의사코드를 그대로 포팅한 순수 함수다. 새 dataclass를 만들지 않고, US-057이 `contentSnapshot` 응답용으로 이미 만들어 둔 pydantic 모델(`schemas.py`의 `EndingRuleItem`/`EndingRuleGroupItem`/`EndingRuleListItem`)을 `items` 타입으로 그대로 재사용한다 — `kind`/`statId`/`operator`/`threshold`/`nextOp` 필드가 techspec의 `SingleRule`/`RuleGroup`과 이미 1:1 대응해서 나란히 두 번째 트리 타입을 둘 이유가 없었다. `stat_values`는 `apply_stat_changes`(US-058)와 동일하게 entity_id의 `str` 키 `dict[str, float]`. 그룹(`EndingRuleGroupItem.rules: list[EndingRuleItem]`)이 섞인 리스트를 변수에 담을 때는 `list[EndingRuleListItem]`으로 명시 타입annotate해야 한다 — 그냥 리터럴로 두면 mypy가 원소 타입을 공통 베이스인 `CamelModel`로 widen해버려 `evaluate_rule_list` 인자 타입 체크에서 막힌다(`test_chat_ending_rules.py`에서 실측).
- **엔딩 판정 파이프라인(`POST /chat-rooms/{id}/messages`가 스탯 판단 뒤에 이어서 호출, US-062, FR-58/FR-61)**: `is_ending_check_due(turn_count, turn_count_gate)`(`ending_rules.py`, 순수 함수 — `turn_count >= gate and (turn_count - gate) % 5 == 0`)가 엔딩별 턴게이트+5턴 주기를 판정한다. 라우터는 `Ending.starting_setup_id == setup.id`인 엔딩을 **`order` 오름차순**으로 순회하며 각 엔딩마다: (1) 이번 턴에 판정 대상이 아니면 `continue`(LLM 호출 자체를 스킵), (2) 대상이면 `build_ending_judgment_prompt(ending.judgment_prompt, ...)` + `generate_structured(_, EndingJudgmentResult)`로 그 엔딩만의 판정을 받고, (3) `triggered`가 아니면 `continue`, (4) `triggered`면 `_ending_rule_items(db, ending)`(§ 위 항목의 `_ending_snapshot`에서 뽑아낸 공용 헬퍼)로 규칙 트리를 가져와 `evaluate_rule_list(rule_items, updated_stats)`와 **AND** 결합 — 규칙이 비어있으면 `evaluate_rule_list([], ...)`이 항상 `True`라 판정프롬프트 결과만으로 결정된다(US-061이 이미 보장). 이 AND가 참인 **첫 번째**(= `order`가 가장 낮은) 엔딩에서 `break`한다 — 그래서 1순위 엔딩이 이미 발동하면 2순위 이후 엔딩은 LLM 호출조차 발생하지 않는다(불필요한 비용 방지, `test_chat_ending_pipeline_api.py`의 `generate_structured_calls` 개수로 검증).

FastAPI는 같은 이름·타입의 Pydantic 바디 파라미터가 의존성 트리 여러 곳(서브 `Depends()` + 라우트 본문)에 선언돼 있으면 파싱을 한 번만 하고 동일 인스턴스를 공유한다 — 실제로 `test_chat_story_message_send_api.py`의 shortcut 관련 테스트로 이 공유가 깨지지 않음을 확인했다. 이 패턴을 앞으로도 "body 필드 검증을 제너레이터 밖으로 빼야 하는" 모든 SSE 라우트에 재사용할 것.

- **상황별 이미지 블러 변형 생성(`POST /assets/{id}/register-situational-image`, US-071, `api/assets/`)**: `core/s3.py`에 `download_object`/`upload_object`(둘 다 blocking, `run_in_threadpool`로 호출)를 추가해 presigned URL 없이 서버가 직접 원본을 내려받고 결과물을 올린다. 실제 픽셀 변형(`api/assets/image_processing.py`의 `generate_blurred_image`, DB/S3 I/O 없는 순수 함수)은 원본 포맷을 보존하려 하지 않고 **항상 RGBA로 변환 후 PNG로 저장** — 팔레트 모드(GIF 등)에 `ImageFilter.GaussianBlur`를 바로 적용하면 깨지고, 포맷별 저장 옵션(JPEG는 알파 불가 등)을 다룰 이유가 애초에 없어서(블러 미리보기는 원본과 같은 포맷일 필요가 없음) 가장 단순한 단일 경로로 통일했다. Pillow 호출 자체도 CPU-bound라 이벤트루프를 막지 않도록 `run_in_threadpool`을 거친다("동기 생성"은 큐를 안 쓴다는 뜻이지, 이벤트루프를 막아도 된다는 뜻이 아님).
  - **자산 참조 시 소유권+ready 체크 재사용**(`PATCH /me/profile`의 US-026 노트가 예견해둔 대로): path의 `{asset_id}`(원본)에 대해 `owner_user_id == 현재유저` + `status == READY`를 검사한다. 다만 이 라우터는 기존 형제 엔드포인트(`/complete`)의 관례를 따라 `content/router.py`의 400 통합 체크가 아니라 **404(없음)/403(소유자 아님)/409(아직 ready 아님 — `/complete`의 "storage에 아직 없음" 409와 같은 의미)로 분리**했다 — 같은 파일 안의 기존 스타일이 다르면 그 파일의 관례를 우선한다.
  - **`content_version_id`를 받아 그 자식 테이블에 쓰는 첫 엔드포인트**(아직 초안 CRUD API 자체(US-082)가 없다) — `ContentVersion` 존재 확인(404) 후 반드시 `Content.creator_user_id == 현재유저`까지 확인한다(403, AC에 명시돼 있진 않지만 타인의 초안에 하위 리소스를 심는 걸 막기 위함, 자산 소유권 체크와 같은 종류의 판단). 앞으로 초안의 하위 리소스(스탯/엔딩/키워드북/단축어/시작설정 등, US-082 이후)를 다루는 모든 엔드포인트도 이 두 체크(버전 존재 + creator 일치)를 재사용할 것.
  - `situational_images`는 entity_id 패턴 업서트: `(content_version_id, entity_id)`로 기존 행을 조회해 있으면 필드만 갱신, 없으면 새로 insert(선택된 `Existing` 없이 SELECT 결과가 `None`일 때만 `db.add`) — `contents.md`의 like/favorite 멱등 토글과 동일한 select-then-act, 별도 unique 제약/ON CONFLICT 없음.
- **상황별 이미지 매칭 판단(`_match_situational_image`, `POST /chat-rooms/{id}/messages`, US-072, 캐릭터 챗 전용)**: 엔딩 판정(US-062, 엔딩마다 각자의 `judgment_prompt`로 한 번씩 개별 `generate_structured` 호출)과 달리, 이미지는 `situational_images`에 엔딩의 `judgment_prompt` 같은 항목별 필드가 없고 response_schema(`{ matchedImageEntityId: string | null }`, techspec-backend-chat.md §3.1)도 애초에 단수라 **등록된 이미지 전체를 한 프롬프트에 나열해 단 한 번만 호출**한다(스탯 판단이 모든 `stat_defs`를 한 프롬프트에 담아 한 번에 판단받는 것과 같은 모양, 엔딩과는 다른 모양). "동시 매칭 시 order 최상위 하나만 발동"(techspec-chat-character.md §1.1)은 코드가 후보를 걸러내는 게 아니라 **프롬프트가 order 오름차순으로 나열 + "여러 개 동시 충족 시 더 앞의 것 하나만" 지시**로 유도한다 — `_match_situational_image`는 응답으로 온 `matchedImageEntityId`가 실제 후보 목록의 `entity_id` 중 하나인지만 방어적으로 재확인한다(할루시네이션 방어, 없으면 매칭 없음으로 취급). 등록된 이미지가 하나도 없으면 판단 호출 자체를 생략한다(비용 절감, `test_send_message_no_situational_images_skips_judgment_call`로 검증) — 새로운 "여러 후보 중 단일 응답" 판단이 필요하면 엔딩(항목별 개별 호출)이 아니라 이 패턴(단일 호출+프롬프트 우선순위 지시)을 기본으로 고려할 것.
  - `character_image_exposures` upsert는 `story_ending_unlocks`(US-062)와 동일한 select-then-insert(이미 있으면 손대지 않음 — "최초 노출 시각만 기록"이 불변식) 패턴이다.
  - `ChatMessageResponse.imageId`는 `chat_messages` 테이블에 컬럼이 없는 **세션 한정 필드**다 — `endingId`/`epilogue`(US-057/063)와 같은 처지로, `send_message`가 그 턴의 `ChatDoneEvent.finalMessage`에만 채워 넣고 `_to_response`(`GET /chat-rooms/{id}`)가 만드는 과거 메시지 목록에서는 항상 `null`이다(새로고침하면 사라짐, 별도 영속 기능 없음 — AC도 "done 이벤트 수신 시"로 범위를 한정).
- **`ChatMessageResponse.imageUrl`(US-073)는 이미지 보관함(US-074, `GET /characters/{id}/image-archive`류)이 아직 없어도 FE가 그 턴의 메시지에 이미지를 바로 인라인 렌더링할 수 있게, `image_id`가 채워지는 시점에 같이 presigned GET URL을 서명해 함께 내려준다** — `_match_situational_image`의 반환 타입을 `entity_id`(uuid)에서 `SituationalImage` ORM 객체 자체로 바꿔, 호출부(`send_message`)가 그 객체의 `image_asset_id`로 `Asset`을 조회 후 `content/router.py`의 `_resolve_asset_url`과 동일한 패턴(`generate_presigned_get_url` + `run_in_threadpool`)으로 URL을 서명한다. AC에는 없는 필드지만 US-020/022/030/042가 이미 여러 번 쓴 "FE가 다른 방법으로 얻을 수 없는 값이면 응답에 필드를 추가한다" 판단과 같은 종류다 — `image_id`와 완전히 같은 세션 한정/최초-매칭-시점-한정 처지이므로 별도 테이블 컬럼도 필요 없다.
- **이미지 보관함(`GET /characters/{id}/image-archive`, US-074, `api/chat/router.py`의 세 번째 prefix 라우터 `characters_router`)**: `id`는 캐릭터 콘텐츠의 물리적 PK(`GET /contents/{id}`와 동일 관례), 404 조건도 그 엔드포인트와 동일하게 "존재하지 않거나 발행된 버전이 없을 때"(`content.current_published_version_id is None`)로 통일했다. 등록된 이미지 전체는 그 **현재 발행 버전**(`content.current_published_version_id`)에 속한 `situational_images`를 `order` 오름차순으로 가져온다 — 방이 고정(pin)한 버전이 아니라 콘텐츠의 최신 발행 버전 기준인 이유는 이 엔드포인트가 `characterId`(콘텐츠 물리 PK)만으로 조회되고 특정 대화방/버전과 무관하기 때문(FE 쿼리 키가 `characterId`뿐, techspec-chat-character.md §1 참고). 노출 여부는 AC3대로 방과 무관하게 `character_image_exposures(user_id, content_id, image_entity_id)`(entity_id로 조인, 버전 안정)만으로 판정하고, `exposed=false`인 항목은 원본이 아니라 `blurred_asset_id`를 서명해 내려준다(원본 바이트는 이 엔드포인트에서도 노출 전까지 응답에 안 실린다, techspec-backend-media.md §21). 이미지 URL 서명은 `_match_situational_image`(US-072/073)와 동일하게 `generate_presigned_get_url` + `run_in_threadpool`을 인라인으로 쓴다(`content/router.py`의 `_resolve_asset_url`은 그 파일 전용 private 헬퍼라 import하지 않고, 같은 패턴만 재사용).
- **메시지 재생성/수정/삭제(US-076, `api/chat/router.py`)**: `send_message`의 "프롬프트 조립 → 생성 스트리밍 → 판단(스탯/엔딩 또는 이미지매칭) → turn_count 증가" 전체를 `_stream_new_turn(db, room, llm_client, setup, history, user_content, shortcut)` 공용 async 제너레이터로 뽑아냈다 — `send_message`(새 사용자 메시지)와 `PATCH .../messages/{message_id}`(`edit_message`, 수정된 메시지부터 이어서 생성)가 이 헬퍼를 공유한다. 둘 다 실제로는 동일한 "새 턴"이라서다. 프롬프트 조립 자체도 `_build_prompt(db, room, setup, history, user_content, shortcut)`로 더 분리해 `POST .../regenerate`(`regenerate_message`)도 재사용한다.
  - **`regenerate_message`는 의도적으로 `_stream_new_turn`을 쓰지 않는다** — 새 턴이 아니라 "같은 턴의 응답만 교체"이므로 turn_count를 증가시키지 않고, 스탯/엔딩 판단·이미지 매칭도 재실행하지 않는다(원 응답 생성 시 이미 한 번 반영됐고, 그 반영분을 되돌릴 턴별 변경 이력이 스키마에 없어 재실행하면 오히려 중복 적용된다). 마지막 메시지가 AI 응답인지(그리고 그 앞에 사용자 메시지가 있는지, 즉 오프닝 메시지만 있는 방이 아닌지)는 `_regeneratable_last_message_dependency`(Depends, SSE 제너레이터 밖)에서 검증한다. **DB 변경 순서가 중요**: 새 응답이 완전히 스트리밍되어 `assistant_content`가 확정된 **뒤에만** 기존 메시지를 `delete`하고 새 메시지를 `add`한다 — 그래야 생성 실패(policyWarning/error) 시 DB를 전혀 건드리지 않아 기존 응답이 그대로 남는다(트랜잭션 롤백에 의존하지 않고 실패 시점 이전에 아예 변경을 만들지 않는 방식).
  - **`edit_message`는 반대로 `_stream_new_turn`을 그대로 재사용한다** — "수정된 내용부터 이어서 생성"은 완전히 새 턴이기 때문. 수정 대상은 반드시 `role == USER`(AI 메시지 수정 미지원, `_editable_user_message_dependency`가 400/404 검증)여야 하고, 그 메시지 이후의 모든 메시지를 삭제한 뒤 그 메시지의 `content`만 갱신한다. **삭제되는 trailing 메시지 중 ASSISTANT 개수만큼 `room.turn_count`를 먼저 빼둔다** — 그래야 `_stream_new_turn`이 새 턴에서 `+= 1`한 뒤의 최종값이 "실제 남은 대화 길이"와 일치해 이후 엔딩 턴게이트(`is_ending_check_due`) 판정이 어긋나지 않는다. **알려진 한계**: trailing 삭제로 되돌아가야 할 `chat_room_stats`/`ending_reached`/`ending_entity_id`/`ending_reached_at_turn` 값은 되돌리지 않는다 — 턴별 스탯 변경 이력 자체가 저장되지 않아 정확한 undo가 불가능하고, US-023 AC도 이 롤백을 요구하지 않는다. 스토리 챗 방을 편집 대상으로 삼는 새 기능을 추가할 때는 이 한계를 먼저 확인할 것.
  - `DELETE .../messages/{message_id}`(`delete_message`)는 SSE가 아닌 평범한 JSON 엔드포인트라 소유권 검증을 `_get_owned_room`으로 라우트 본문에서 직접 처리한다(스트리밍이 아니므로 `_owned_room_dependency`로 분리할 필요가 없음, `delete_chat_room`과 동일한 스타일). `turn_count`는 건드리지 않는다 — 개별 메시지 삭제가 "몇 번째 턴"인지 지역적으로 판단할 근거가 없고 AC도 요구하지 않는다(알려진 한계, edit의 trailing-turn_count 보정과는 별개 판단).
- **캐릭터 초안 CRUD(`POST /contents`, `GET`/`PATCH /contents/{id}/draft`, US-082)가 드러낸 스키마 갭**: US-009가 만든 `contents.genre_id`/`target`, `character_version_details.thumbnail_asset_id`, `situational_images.image_asset_id`/`blurred_asset_id`는 전부 원래 `NOT NULL`이었지만, 이 값들은 실제로는 **발행 시점에야(US-083 publish validation) 채워지는 게 보장되는 값**이지 초안 생성 시점엔 존재할 수 없다(장르 미선택, 대표이미지 미업로드 등). `a638f002826b_character_draft_nullable_columns` 마이그레이션이 이 5개 컬럼을 전부 nullable로 바꿨다 — **다음에 스토리 초안 API(US-084)를 만들 때도 `story_version_details.thumbnail_asset_id` 등 동일한 패턴의 컬럼을 반드시 nullable로 바꿔야 한다**(아직 안 바뀜). 반대로 텍스트 컬럼(`character_version_details.name`/`one_liner`/`intro`/`character_prompt`, `content_versions.detail_description`)은 nullable로 바꾸지 않고 그냥 빈 문자열 `""`을 초안 기본값으로 썼다 — FK가 아니라 "빈 문자열도 유효한 값"인 텍스트 컬럼은 이렇게 하는 편이 `str | None` 전파를 훨씬 덜 일으킨다(SQLAlchemy 2.0 typed `select()`가 7개 넘는 컬럼을 한 번에 select하면 정밀 타입추론을 포기하고 `Any`로 fall back하는 경우가 있어 — `get_content_detail`처럼 — nullable 전파가 어디서 mypy 에러로 튀어나올지 일관되지 않는다는 것도 실측함). 발행된(published) 버전을 읽는 코드는 이 nullable들에 대해 `assert x is not None`으로 "발행 시점엔 반드시 채워져 있다"는 불변식을 문서화하고 통과시킨다(`version_number`/`published_at`과 동일 패턴) — 초안을 읽는 코드(`GET /me/drafts`, `GET/PATCH /contents/{id}/draft`)만 실제로 `None`을 다룬다.
- **`PATCH /contents/{id}/draft`의 `situationalImages` 항목은 `id`(entity_id)와 `triggerCondition`만 받는다 — `imageAssetId`는 이 엔드포인트가 절대 쓰지 않는다.** 이미지 파일 자체(`image_asset_id`/`blurred_asset_id`)는 여전히 `POST /assets/{id}/register-situational-image`(US-071) 전용이다. 이 자동저장 엔드포인트는 entity_id가 아직 없으면 (image 필드는 비워둔 채) 새로 insert하고, 있으면 `trigger_condition`/`order`만 갱신하며 image 필드는 절대 건드리지 않는다 — 그래서 사용자가 "상황별 이미지 슬롯"을 이미지 업로드보다 먼저 추가해도 자동저장이 깨지지 않고, 나중에 업로드가 register-situational-image를 통해 같은 entity_id 행에 이미지만 채워 넣는다. 새 자식 리소스 PATCH를 만들 때 "이 필드는 다른 엔드포인트가 소유한다"는 경계가 있다면 이 분리 패턴을 재사용할 것.
- **`content_version_id`로 스코프되는 초안 자식 리소스 엔드포인트의 404/403 게이트**(`_get_owned_draft_version`, `content/router.py`)는 매번 새로 안 짜고 헬퍼로 뽑아 재사용할 것 — `Content` 존재 + `type` 일치 확인(404) → `creator_user_id` 일치 확인(403) → `published_at IS NULL`인 `ContentVersion` 조회(404, "초안 없음"). 스토리 빌더(US-084)와 그 하위 리소스들(시작설정/스탯/키워드북/단축어/엔딩 등, US-091~095)도 같은 게이트가 필요하면 이 함수를 확장하거나 그대로 재사용할 것.
- **버전 전환(`POST /chat-rooms/{id}/pin-latest-version`/`.../acknowledge-version-upgrade`, US-078, techspec-content-versioning.md §3/§4)**: `pin-latest-version`은 `room.content_version_id`를 `content.current_published_version_id`로 바꿔 끼우기만 한다 — `messages`/`chat_room_stats`/`ending_reached` 등은 전혀 건드리지 않는다(entity_id가 버전 넘어 안정적이라는 §1 원칙 4 덕분에 스탯/엔딩 조인이 새 버전에서도 그대로 맞는다는 전제). **techspec §4가 같은 절에서 설명하는 "관리자가 이용제한을 해제할 때 그 콘텐츠의 모든 대화방을 동기적으로 일괄 마이그레이션(`content_version_id` 갱신 + `version_auto_upgraded=true` 세팅)"은 이 스토리 범위가 아니다** — 그 UPDATE 문 자체는 아직 어디에도 구현되지 않았고, US-121(신고 조치 처리 API, `moderationStatus: restricted → normal`)이 구현할 때 여기 추가할 것. 이번 스토리가 만든 건 그 결과로 세팅된 플래그를 사용자가 "확인"하는 소비측(`acknowledge-version-upgrade`, 단순히 `version_auto_upgraded`를 `false`로 되돌림)뿐이다 — `GET /chat-rooms/{id}`는 순수 조회라 스스로 끄지 않는다(회귀 테스트로 고정: `test_acknowledge_version_upgrade_get_does_not_reset_flag`).
- **캐릭터 발행(`POST /contents/{id}/publish`, US-083)이 드러낸 두 번째 스키마 갭**: US-082의 `PATCH /contents/{id}/draft`는 5개 탭 중 프로필/인트로/프롬프트/고급설정(상황별이미지)만 다뤘고 **등록 탭(설명/장르/타겟/해시태그/공개범위)은 의도적으로 범위 밖이었다** — 그런데 이 필드들이 실제로 채워질 수 있는 유일한 API 경로가 바로 이 draft PATCH뿐이라, 그대로 두면 발행 검증(장르/타겟 필수)이 영원히 통과 불가능했다. `CharacterDraftPayload`/`CharacterDraftResponse`(`content/schemas.py`)에 `description`(→ `ContentVersion.detail_description`)/`genreId`/`target`/`hashtags`/`visibility`(→ `Content`의 해당 컬럼들)를 이번 스토리에서 추가했다 — US-020/022/030/042가 이미 반복한 "다음 스토리가 실제로 필요로 하는 필드를 그 시점에 추가한다" 판단과 동일한 종류다. 이 필드들이 `Content`/`ContentVersion`(버전을 감싸는 공통 헤더)에 있지 `character_version_details`(버전별 스냅샷)에 없는 이유: 장르/타겟/공개범위/해시태그는 재발행해도 콘텐츠 전체에 적용되는 값이지 버전마다 스냅샷되는 값이 아니기 때문(§3 발행 트랜잭션이 이 컬럼들을 전혀 복제하지 않는 이유도 동일) — `_get_owned_draft_version`이 이제 `tuple[Content, ContentVersion]`을 반환하도록 시그니처를 바꿔 두 테이블 모두에 접근한다. `PATCH .../draft`를 다시 만지는 다음 스토리(스토리 빌더, US-084)도 story_version_details 쪽에서 이 등록 탭 필드를 따로 또 빼먹지 않도록 주의할 것.
- **`LLMClient.generate_structured()`가 멀티모달(이미지 첨부) 판단을 처음 지원하게 됨(US-083)**: 시그니처에 `images: list[tuple[bytes, str]] | None = None`(바이트+MIME타입 쌍) 파라미터를 추가했다 — 기존 3개 호출부(스탯/엔딩/이미지매칭 판단, 전부 텍스트만)는 인자를 안 넘기므로 하위호환. `GeminiLLMClient` 구현은 `images`가 있으면 `contents`를 `[prompt, *Part.from_bytes(data=.., mime_type=..) ...]` 리스트로 바꿔서 넘긴다 — google-genai SDK의 `t_contents()`가 문자열/Part가 섞인 리스트를 "한 턴의 여러 파트"로 자동 합쳐주므로(`_transformers.py`) 별도 `Content`/`UserContent` 래핑이 불필요하다. mypy strict 우회 포인트: `contents` 지역변수를 SDK의 복잡한 `ContentListUnion` 유니언 타입 그대로 맞추려 하면 통과 못 시키므로 `str | list[Any]`로 선언해 Any로 흡수시켰다(SDK 타입이 딱 이 형태의 리스트를 실제로 받아들이는 건 `_transformers.py` 직접 확인으로 검증). **`LLMClient`를 상속하는 모든 페이크(테스트)의 `generate_structured` 시그니처도 `images` 파라미터를 받아야 한다** — 안 받으면 `[override]` mypy 에러(서브클래스가 슈퍼클래스보다 좁은 시그니처를 가질 수 없음)가 기존 채팅 테스트 4개 파일에서 즉시 난다.
- **발행 자동 필터가 넘길 이미지의 MIME 타입은 `Asset` 테이블에 저장돼 있지 않다** — `build_object_key`(US-018)가 `storage_key`에 확장자를 이미 박아뒀으므로(`assets/{purpose}/{id}{ext}`), 읽어올 때는 별도 컬럼 대신 `mimetypes.guess_type(asset.storage_key)`로 역산한다(`content/router.py`의 `_load_publish_filter_images`). 새로 자산의 MIME 타입이 필요해지는 곳(예: 다른 멀티모달 판단)도 이 역산 패턴을 재사용하면 되고, 굳이 `Asset`에 `content_type` 컬럼을 추가할 필요는 없다.
- **발행 검증/필터 실패 응답은 `{"missingFields": [...]}` 또는 `{"reason": "..."}`를 담은 400** — 둘 다 FastAPI `HTTPException(detail=dict)`로 던진다(기존 429의 `{"retryAfterSeconds": ...}`와 같은 관례, 필드별 에러 스키마를 새로 만들지 않았다). 실제 프로덕트의 정확한 판정 기준(금칙어 목록, 이미지 임계값)은 PRD상 미확정 열린 질문(techspec-overview.md §15)이라, `build_character_publish_filter_prompt`(`content/publish.py`)의 지시문 자체는 이 스토리의 판단으로 작성한 잠정 버전 — 이후 실제 기준이 확정되면 이 프롬프트만 교체하면 된다(호출부/스키마는 변경 불필요).
- **스토리 초안 CRUD(`POST /contents` type='story', `GET`/`PATCH /contents/{id}/draft`, US-084)**: `_get_owned_draft_version`이 이제 `allowed_types: tuple[ContentType, ...]`를 받는다(캐릭터/스토리 draft가 같은 URL을 공유하므로) — 발행처럼 한 타입 전용 엔드포인트는 `(ContentType.CHARACTER,)`처럼 단일 원소 튜플을 넘긴다. `PATCH /contents/{id}/draft`의 request body는 `CharacterDraftPayload | StoryDraftPayload`(판별자 필드 없는 bare union) — 두 스키마의 필수 필드 집합이 겹치지 않아(캐릭터엔 `intro`/`characterPrompt`, 스토리엔 `promptTemplate`/`startingSetups`가 각각 필수) pydantic v2의 기본 스마트 유니온이 구조만으로 정확히 하나를 고른다. 라우터 바디에서 `isinstance(payload, CharacterDraftPayload)`로 분기 후 `content.type`과 일치하는지 한 번 더 확인(불일치 시 422) — `story_version_details.thumbnail_asset_id`도 US-082의 character 패턴을 그대로 따라 nullable로 바꿨다(`ec416a217f5d` 마이그레이션).
- **엔딩 규칙 트리(`ending_rules`+`ending_rule_groups`)를 CRUD로 왕복시키는 스키마**: `chat/schemas.py`의 읽기전용 `EndingRuleItem`/`EndingRuleGroupItem`(`kind` 판별 유니언, US-057)을 그대로 import하지 않고 `content/schemas.py`에 쓰기 가능한 대응 쌍 `EndingRuleDraftItem`/`EndingRuleGroupDraftItem`을 새로 선언했다(다른 라우터 파일 간 헬퍼 비공유 관례, 위 `_resolve_asset_url` 항목과 동일 판단). 두 테이블은 techspec-db-schema.md §5대로 `order` 컬럼 하나를 공유하는 시퀀스라, PATCH가 받는 `statRules` 배열의 인덱스가 곧 그 공유 order다(그룹 안의 `rules` 배열은 별도의 독립된 order 시퀀스). 읽는 쪽 헬퍼(`_ending_rule_draft_items`)는 `chat/router.py`의 `_ending_rule_items`와 병합 로직이 완전히 동일하다 — 둘 중 하나를 고치면 다른 쪽도 같이 봐야 한다(현재는 의도적으로 중복, 세 번째 소비처가 생기기 전까진 공용 헬퍼로 뽑지 않는다).
- **`keyword_notes.starting_setup_id`는 물리적 FK(`starting_setups.id`)이지만, draft API가 노출하는 `KeywordNoteDraftItem.startingSetupId`는 다른 모든 draft-level id와 마찬가지로 entity_id다** — 읽을 때(`_story_draft_response`)는 그 버전의 `{물리id: entity_id}` 맵으로 역변환하고, 쓸 때(`_update_story_draft`)는 같은 PATCH 요청 안에서 막 upsert한 `{entity_id: 물리id}` 맵(`setup_physical_id`)으로 정변환한다 — 순서상 반드시 `starting_setups` upsert 루프가 끝난 뒤에 `keyword_notes` upsert를 처리해야 이 맵이 완성돼 있다. 참조하는 entity_id가 그 PATCH 페이로드의 `startingSetups`에 없으면(검증 없음 원칙) 조용히 `None`(전체 적용)으로 떨어뜨린다 — 에러를 던지지 않는다.
- **`relationship()`을 선언하지 않는 이 코드베이스의 관례(순수 FK 컬럼만 사용)는 INSERT 순서뿐 아니라 DELETE 순서에도 그대로 적용된다** — `ending_rules`/`ending_rule_groups`/`endings`/`starting_setups`처럼 3~4단계로 얽힌 자식을 부모보다 먼저 지워야 하는 캐스케이드 삭제(ON DELETE CASCADE 없음, 위 chat_rooms 항목과 동일 이유)에서, 같은 이유로 자식 `db.delete()` 호출과 부모 `db.delete()` 호출 사이에 반드시 `await db.flush()`를 넣어야 한다 — 넣지 않으면 SQLAlchemy가 한 flush 안에서 여러 테이블의 DELETE를 그냥 세션에 추가된 순서(우리가 의도한 자식-먼저 순서)가 아니라 자체적으로 재정렬할 수 있어 `ForeignKeyViolationError`가 난다(`content/router.py`의 `_delete_ending_subtree`/`_delete_starting_setup_subtree`/`_reconcile_ending_rules`가 각 계층 사이에 `flush()`를 명시적으로 끼워 넣은 이유). US-082의 situational_images처럼 "부모-자식이 한 테이블 쌍뿐"인 얕은 삭제는 이 문제가 드러나지 않았다 — 3단 이상 깊이의 새 캐스케이드 삭제를 짤 때는 항상 계층마다 flush를 넣을 것.
- **스토리 발행(`POST /contents/{id}/publish`, US-085)은 캐릭터 발행(US-083)과 URL/메서드가 완전히 같다** — `GET`/`PATCH /contents/{id}/draft`(US-084)와 동일하게, 라우트 함수 하나(`publish_content`)가 `_get_owned_draft_version`으로 두 타입 모두를 허용해 로드한 뒤 `content.type`으로 `_publish_character_content`/`_publish_story_content` 두 private 헬퍼에 위임한다 — 캐릭터 전용이던 `_get_owned_draft_version(..., (ContentType.CHARACTER,))` 호출은 이제 두 타입을 모두 받도록 넓혔다. 함수명이 바뀌면 FastAPI가 자동 생성하는 `operationId`(함수명 기반)도 같이 바뀌어 `openapi.json`/`packages/api-types`의 codegen 결과 함수명이 변하니, 이런 "기존 캐릭터 전용 엔드포인트를 스토리와 공유하도록 넓히는" 리팩터 뒤에는 항상 OpenAPI export + api-types codegen을 재실행할 것.
- **스토리 발행의 하위 리소스 복제(`_publish_story_content`)는 `ending_rules.stat_def_entity_id`가 entity_id(§1 원칙 4, 버전 넘어 안정) 참조라는 점 덕분에 캐릭터보다 한 단계 더 얕게 끝난다** — 룰이 참조하는 스탯의 entity_id는 새 버전에서도 그대로 유지되므로 클론 시 별도 remap 테이블이 필요 없다(그냥 `rule.stat_def_entity_id`를 그대로 복사). 반면 `keyword_notes.starting_setup_id`는 물리적 FK라 반드시 remap이 필요하다 — `{old_setup_id: entity_id}`와 `{entity_id: new_setup_id}` 두 맵을 만들어 `old→entity_id→new`로 우회 변환한다(`_update_story_draft`의 `setup_physical_id` 정변환과 방향만 반대인 역변환). 새로운 "발행 시 복제해야 하는 물리적 FK"가 생기면 이 두 갈래(entity_id 참조는 그대로 복사, 물리적 FK는 반드시 remap)를 먼저 구분할 것.
- **미리보기 세션(`POST /preview-sessions`, US-088, techspec-builder-common.md §3)은 Postgres를 전혀 거치지 않는 첫 엔드포인트다** — `content/schemas.py`의 `CharacterDraftPayload | StoryDraftPayload`(이미 `PATCH /contents/{id}/draft`가 쓰는 바로 그 union, 도메인 파일을 가로질러 그대로 import)를 검증 없이 그대로 요청 바디로 받아, DB 조회 없이 그 payload만으로 오프닝 메시지/스탯 초기값을 계산해 `PreviewSessionState`(`chat/schemas.py`)로 Redis에 저장한다(`api/chat/preview_session.py`, `session/store.py`와 동일한 `create_session`/`get_session` 모양이지만 auth 세션과 키 프리픽스·TTL 설정(`preview_session_ttl_seconds`, 24시간)이 달라 별도 모듈로 분리했다). 값이 `str`뿐인 auth 세션과 달리 상태가 중첩 객체라 `json.dumps(dict)`가 아니라 `PreviewSessionState.model_dump_json()`/`model_validate_json()`으로 직렬화한다(pydantic이 UUID/datetime을 알아서 JSON 왕복시켜준다).
  - 스토리는 여러 `startingSetups`를 가질 수 있지만 payload에 "미리보기할 시작설정"을 고르는 필드가 없다(AC가 formToServer 결과 그대로만 받으라고 명시) — `startingSetups[0]`을 결정적으로 선택한다(`_build_preview_start_state`, `chat/router.py`). 여러 시작설정을 각각 미리보기해야 하는 요구가 나오면 이 지점(그리고 AC)부터 다시 볼 것.
  - `PATCH /contents/{id}/draft`용 스키마를 그대로 재사용했기 때문에, 그 draft 스키마가 바뀌면(예: 새 탭 필드 추가) 이 엔드포인트의 요청 계약도 자동으로 같이 바뀐다 — 별도 동기화가 필요 없다는 뜻이지만, draft 스키마를 고칠 때 미리보기가 여전히 말이 되는지 함께 확인할 것.
- **`POST /preview-sessions/{id}/messages`(US-089)는 실제 `POST /chat-rooms/{id}/messages`의 오케스트레이션 함수(`_stream_new_turn`)를 그대로 재사용하지 않는다** — 그 함수는 `StatDef`/`ChatRoomStat`/`Ending`/`StoryEndingUnlock` DB 조회·insert·commit에 깊이 결합돼 있어, Redis뿐인 `PreviewSessionState`로는 억지로 끼워 맞추면 오히려 두 경로 다 읽기 어려워진다. 대신 **순수 엔진과 SSE 이벤트 스키마만** 재사용하는 병렬 `_stream_preview_turn`을 새로 뒀다: `_stream_generated_tokens`(토큰 릴레이), `build_generation_prompt`/`build_story_generation_prompt`/`build_stat_judgment_prompt`/`build_ending_judgment_prompt`(프롬프트 조립), `apply_stat_changes`(클램핑), `evaluate_rule_list`(엔딩 규칙 평가), `is_ending_check_due`(턴게이트), `match_keyword_notes`(키워드 매칭), 그리고 `ChatTokenEvent`/`ChatStatChangeEvent`/`ChatEndingReachedEvent`/`ChatPolicyWarningEvent`/`ChatDoneEvent`/`ChatErrorEvent` 전부 동일 타입 그대로. 이 함수들이 받는 ORM 모델(`ChatMessage`/`StatDef`/`EndingRuleItem`류)은 draft payload 필드로부터 **DB 세션 없이 생성자로만 채운 인메모리 인스턴스**(`_preview_chat_message`/`_preview_stat_def`/`_preview_ending_rule_item`/`_preview_ending_rule_list_item`/`_preview_keyword_notes`, US-058/US-064 테스트가 이미 쓰던 패턴을 프로덕션 코드에도 적용한 첫 사례)로 어댑팅한다.
  - `EndingRuleDraftItem`/`EndingRuleGroupDraftItem`(`content/schemas.py`, 쓰기용)과 `EndingRuleItem`/`EndingRuleGroupItem`(`chat/schemas.py`, `evaluate_rule_list`가 기대하는 읽기용)은 필드 shape이 완전히 같아도 별개 pydantic 클래스라 `isinstance`/타입체크가 서로 호환되지 않는다 — `_preview_ending_rule_list_item`이 매 호출마다 변환한다(US-084 노트가 "세 번째 소비처가 생기기 전엔 공용 헬퍼로 뽑지 않는다"고 남겨둔 것과 별개로, 이건 판정 엔진에 넣기 위한 타입 변환이라 다른 종류의 중복이다).
  - **`PreviewSessionState`엔 저장된 `user_id`가 없다**(US-088) — `POST /preview-sessions/{id}/messages`도 로그인만 요구하고 세션 소유자 대조는 하지 않는다(추측 불가능한 세션 id + 로그인 요구가 곧 접근 통제, 비밀번호 재설정 토큰과 같은 처지). 세션이 없으면(만료/오타) `_owned_preview_session_dependency`가 404.
  - **TTL 갱신(`update_preview_session`, `preview_session.py`)은 US-088이 만든 `create_preview_session`과 별개 함수다** — techspec-builder-common.md §3의 "마지막 활동 기준 24시간 TTL"을 satisfy하려면 매 턴 종료 시 같은 세션 id에 다시 `SET ... EX`해야 한다(새 id를 발급하는 `create_preview_session`을 재사용하면 세션 id가 바뀌어버려 FE가 들고 있는 `previewSessionId`와 어긋난다).
  - AC의 "스탯 증감/키워드북/단축어/엔딩 판정"은 전부 스토리 전용이라(techspec-db-schema.md §5) 캐릭터 미리보기는 `isinstance(state.payload, CharacterDraftPayload)`일 때 판단 단계 전체를 건너뛴다 — 상황별 이미지 매칭(`_match_situational_image`, US-072)도 이번 스토리 AC에 없고 애초에 draft 단계엔 매칭 가능한 원본 자산이 없어(register-situational-image는 `content_version_id`가 있어야 호출 가능) 미리보기에 포함하지 않았다.
- **`GET /me/generated-images`(US-097, `api/assets/router.py`의 두 번째 라우터 `me_router`, prefix `/me`)는 techspec-backend-media.md §3이 명시한 그대로 항상 빈 배열을 반환하는 스텁이다** — AI 이미지 생성 자체(제공업체/과금/비동기 처리)가 별도 세션 범위라, `Asset` 모델에 "이 자산이 AI로 생성됐다"를 표시할 컬럼조차 아직 없다(`AssetKind`는 original/blurred/thumbnail뿐). 로그인만 확인하고 DB 조회 없이 `[]`를 반환한다 — 실제 생성 파이프라인이 생기면 이 함수 본문만 실제 쿼리로 교체하면 된다(`api/core/email.py`의 `send_email`과 같은 "나중에 본문만 바꾸는 단일 진입점" 패턴). `me_router`라는 이름이 `api/auth/router.py`/`api/content/router.py`가 이미 쓰는 이름과 겹치므로, `main.py`에서 import할 때 반드시 별칭(`me_router as assets_me_router`)을 줄 것 — 그대로 import하면 나중에 import된 것이 앞의 것을 덮어써 조용히 라우트가 사라진다.
- **`CharacterDraftResponse.id`는 콘텐츠의 물리적 id이지, `POST /assets/{id}/register-situational-image`(US-071)가 요구하는 `content_version_id`가 아니다** — 이 두 id를 헷갈리지 않도록 FE 빌더(US-103)가 그 등록 엔드포인트를 호출해야 하는 시점에서야 이 갭이 드러났다. `CharacterDraftResponse`에 `content_version_id`(`_character_draft_response`의 `version.id`)를 추가해 해결 — US-020/022/030/042와 같은 "FE가 다른 방법으로 얻을 수 없는 값이면 응답에 필드를 추가" 판단. `StoryDraftResponse`는 상황별 이미지 같은 content_version_id-스코프 자식 리소스가 없어 이 필드를 추가하지 않았다 — 스토리 쪽에 그런 리소스가 생기면 그때 같은 패턴으로 추가할 것.
